# 웹서비스 — IPv4 HTTPS 공개 및 모바일 스케줄

스케줄 상단의 `웹` 버튼에서 웹서비스를 관리합니다. 현재 단계에서는
같은 PC에서 실제 스케줄을 조회하며, 별도 `외부 공개` 체크로 HTTPS 직접 공개를 준비합니다.
기본 주소는 `http://127.0.0.1:8765`입니다. 실제 연결된 주소는 설정창에 표시합니다.

## 디코송출과 웹실행 — 독립 운영

스케줄 상단의 **디코송출**과 **웹실행**은 각각 음성 송출과 웹 공개를 시작합니다.
연결 후에는 **송출종료**, **웹종료**로 표시하며 한쪽을 종료해도 다른 쪽은 유지합니다.
웹은 Discord 음성 송출권한이나 음성 입장 완료를 기다리지 않습니다. 관리자 간 통신용 봇 연결은 공용입니다.
웹 버튼만 눌렀을 때 다른 웹 담당자가 있으면 승계 여부를 한 번 묻습니다.

디코 설정의 **디코 송출 시 웹 동시 실행**은 기본 체크이며 PC의 서버별 봇 설정에 저장합니다.
체크된 상태에서 디코 승계를 확인하면 웹도 함께 요청한다고 안내하고, 두 작업을 각각 시작합니다.
웹에서는 추가로 묻지 않습니다. 디코 승계를 거절하면 웹도 시작하지 않습니다.
체크를 끄면 디코 버튼은 음성 송출만 처리하며 기존 웹 담당자는 그대로 유지됩니다.
내부 음성 재접속은 웹을 새로 승계하지 않습니다.

`web_independent_controller.py`가 실제 웹 수명을 관리합니다. 이전 Discord 권한 기반 자동 웹 승계 루프는 실행하지 않습니다.
웹 담당·진행 중인 웹 요청·웹 세대는 별도 기록으로 검증하며, 디코 권한 세대나 디코 승계 단계가 바뀌어도 웹 요청을 취소하지 않습니다.
일반 웹 실행과 기존 **웹 단독 강제 실행**은 별도 진입점입니다. 두 경로 모두 이전 웹의 실제 공개 중지 확인은 생략하지 않습니다.
일반 승계 후 새 공개가 실패하면 기존 웹 담당자를 자동 복구합니다. 공개와 DNS 갱신이 확인되면 복구 자료를 정리합니다.

디코 담당과 웹 담당이 다른 PC일 때 마지막 수정 1분 30초 후 조회용 스케줄을 전달하는 기존 기능도 유지합니다.
웹 PC의 로컬 스케줄은 덮어쓰지 않으며 웹 표시 자료만 전달합니다. 자료 전달은 웹 연결·종료를 결정하지 않습니다.
이하의 Discord 권한 기반 승계 설명은 이전 연결 방식의 기록이며 현재 버튼 동작은 이 절을 따릅니다.

## 본체 없이 웹서버 종료 — 오른쪽 아래 시스템 트레이

독립 웹서버가 실행되면 Windows 시계 옆 알림 영역에 **보스타이머 웹서버** 아이콘이 표시됩니다.
숨겨진 아이콘은 `^`에서 확인할 수 있습니다. 아이콘을 우클릭하고 **웹서버 종료**를 누르면
본체가 꺼져 있어도 이 PC의 웹서버를 정상 종료합니다. 정리 중에는 **웹서버 종료 중…**으로 표시되며 완료 후 아이콘이 사라집니다.
메뉴를 닫거나 본체만 종료하는 동작은 웹을 종료하지 않습니다. Discord 연결·송출과 저장된 스케줄·인증 정보는 유지합니다.

본체가 켜져 있으면 종료 상태를 반영하며, 나중에 본체를 다시 켜도 자동으로 웹을 되살리지 않습니다.
다시 공개하려면 본체의 **웹실행**을 누릅니다. 네트워크 오류로 공동 담당 기록의 종료 반영이 실패해도 로컬 웹은 종료하며,
미확인 상태는 진단 로그에 남깁니다. 다른 PC의 새 담당 기록을 이전 종료 결과로 덮어쓰지 않습니다.

이 기능은 새 웹 프로세스 코드에 포함됩니다. 기존에 실행 중인 구형 웹은 명시적으로 종료한 뒤 새 코드로 실행해야 하며,
정적 화면 파일만 바꾸는 웹 업데이트로 아이콘이 추가되지는 않습니다. 배포 EXE의 실제 동작은 수동 빌드 후 확인 대상입니다.

새 설정의 웹서비스 사용·외부 공개·무료 주소 자동 갱신은 기본 ON입니다.
무료 주소 설정을 저장하면 저장된 OFF 상태도 사용·공개 ON으로 준비합니다.
기존 웹을 인계받는 관리자는 같은 DuckDNS 주소·Token만 입력하고 저장하면 됩니다.
비밀번호·인증서·기존 약관 동의 기록을 인계받고 로컬 HTTPS 확인을 자동 수행합니다.
HTTPS 화면의 약관 체크도 기본 선택이며, 실제 발급 동의 기록은 발급 또는 검증된 인계로 저장합니다.
송출권한 또는 별도 웹 담당 권한을 얻기 전에는 외부 공개·주소 갱신을 하지 않습니다.
공동 운영에서 기존 웹 유지를 명시적으로 선택한 경우에는 주소 저장만으로 웹 담당을 옮기지 않습니다.

## 설정창

- **서비스**: ON/OFF, 상태, 주소 복사·브라우저 열기, 포트 충돌 시 재시도.
  스케줄 자료 연결 여부·일정 개수·갱신 지연도 표시합니다.
- **비밀번호**: 네 자리 비밀번호 저장·변경, 자동 생성, 모든 브라우저 로그인 해제.
  최초 한 번 설정한 비밀번호를 길드원에게 알려주는 방식입니다.
- **접속 관리**: 브라우저별 최근 접속·IP·로그인 실패 횟수, 브라우저/IP 차단과 해제.
- **네트워크**: 처음 탭을 열 때 자동 진단. PC·기본 공유기·공인 IP·IPv6·UPnP·NAT-PMP와
  상위 NAT 가능성을 표시합니다. `다시 진단`, `진단 결과 복사`를 제공합니다.
- **무료 주소**: DuckDNS 최초 등록 안내·주소 이름·Token 저장, 자동 갱신 ON/OFF,
  지금 갱신·DNS 확인, 준비한 도메인 복사. 외부 접속 완료로 표시하지 않습니다.
- **HTTPS**: 약관 동의, 무료 인증서 발급·재사용, 만료/자동 갱신 예정 표시,
  인증서 이름을 검증하는 로컬 HTTPS 확인.
- **외부 공개**: IPv4·UPnP 자동 포트 연결, Windows HTTPS 허용 규칙, 공개 URL 복사/열기,
  해제·재시도. 외부 접속의 실제 성공은 별도 확인합니다.
- **진단 로그**: 웹 전용 로그 표시·복사. 모든 로그에 단계와 시각, 이벤트를 기록합니다.

로컬 조회의 필수 입력은 최초 네 자리 비밀번호뿐입니다. 미설정 상태에서는 스케줄과 조회 API가
공개되지 않고 설정 안내를 표시합니다. 체크 상태와 포트는 AppData의 웹 전용 설정에 저장하며,
켜진 상태에서 본체를 종료해도 독립 웹서버는 유지하며 다음 본체 실행에서 기존 웹에 다시 연결합니다.
웹 설정창을 닫아도 웹서버는 계속 실행됩니다. 사용 OFF·웹종료·트레이의 웹서버 종료로 명시적으로 종료합니다.
포트가 사용 중이면 다른 프로그램을 종료하거나 설정을 덮어쓰지 않고 오류를 표시합니다.
`다른 포트로 재시도`로 다음 포트를 선택할 수 있습니다.

## 소스 분리

- `web_service_common.py`: 웹 전용 설정·상태 문서와 회전 진단 로그.
- `web_service_manager.py`: 자식 프로세스 시작·종료·응답 감시. Tk 의존성 없음.
- `web_service_worker.py`: 로컬 HTTP 처리. GUI·OCR·Discord·음성 의존성 없음.
- `web_worker_tray.py`: 독립 웹 프로세스의 Windows 트레이 아이콘·종료 메뉴와 메시지 루프.
- `web_manual_stop.py`: 실행 세션·PID별 명시적 종료 기록과 자동 재실행 차단.
- `web_service_ui.py`: 전용 관리창. 통신·프로세스 작업은 관리자에 위임.
- `web_schedule_snapshot.py`: 기존 공유용 수집 경로를 재사용하는 조회 전용 변환·공개 필드 검사.
- `web_schedule_cache.py`: 워커의 자료 캐시·갱신 지연 감지·이전/다음 보스 요약.
- `web_service_page.py`, `web_schedule_frontend.py`: 모바일 HTML/CSS와 브라우저 동작. 외부 라이브러리나 별도 웹 빌드 없음.
- `web_service_login.py`: 네 자리 비밀번호 입장 화면.
- `web_access_settings.py`: 프로그램에서만 변경하는 비밀번호 검증값·로그인 세대·차단 정책.
- `web_access_runtime.py`: 워커의 인증·로그인 제한·접속 기록. GUI 의존성 없음.
- `web_network_diagnostics.py`: 독립 작업 스레드의 읽기 전용 네트워크 진단.
  웹서버 코디네이터·Tk·Discord 이벤트 루프와 분리합니다.
- `web_ddns_service.py`: 독립 스레드의 DDNS 설정 저장·IP 조회·갱신·DNS 확인.
- `web_secret_store.py`: Windows 사용자 계정의 DPAPI로 DDNS Token을 암호화·복호화.
- `web_acme_client.py`: Let’s Encrypt ACME와 DuckDNS DNS-01 인증.
- `web_certificate_store.py`: 인증서 검증·세대별 저장. 개인 키 암호화와 원자적 교체.
- `web_certificate_service.py`: 독립 스레드의 인증서 발급·갱신과 로컬 TLS 진단.
- `web_https_app.py`: 조회 전용 HTTPS WSGI API와 Secure 쿠키.
- `web_https_server.py`: 워커 내부의 별도 Cheroot HTTPS 리스너.
- `web_direct_hosting.py`: 독립 스레드의 외부 공개·임대 유지·자체 규칙 정리.
- `web_port_mapping.py`: UPnP TCP 매핑 생성·조회·갱신·소유권 확인 후 삭제.
- `web_firewall.py`: 정적 PowerShell의 프로그램·LAN 주소·HTTPS 포트별 Windows 방화벽 규칙.

일반 프로그램에 연결한 부분은 초기화·상단 버튼·3초 간격 자료 수집·종료 처리입니다.
EXE에서는 동일 실행 파일의 `--boss-timer-web-worker` 모드를 사용합니다.
이 분기는 GUI 중복 실행 검사와 무거운 모듈 import 전에 실행되므로 두 번째
관리자 화면이나 Discord 봇을 만들지 않습니다. 소스 실행에서는 같은 Python
환경으로 워커 파일만 실행합니다. 별도 웹 EXE를 빌드하거나 설치할 필요가 없습니다.

배포 분석에 보이는 정적 import를 사용합니다. 자식 프로세스에서 PyInstaller
로딩 화면을 억제하도록 환경 변수를 지정합니다.
[PyInstaller의 워커·로딩 화면 설명](https://pyinstaller.org/en/latest/advanced-topics.html)
실제 EXE 동작은 사용자 빌드 후 확인 대상입니다.

## 현재 서버 범위

- IPv4 loopback(`127.0.0.1`)에만 바인딩합니다.
- `GET /`: 비밀번호 입장 화면. 인증 후 현재 시간·지난 두 보스 취소선·다음/다다음 보스·전체 일정·미확정 항목.
- `GET /api/status`: online, server_time, updated_at, 단계·프로토콜 정보.
- `GET /api/schedule`: 조회용 일정·요약·자료 시각·버전·갱신 지연 상태.
- `GET /schedule.js`, `GET /style.css`: EXE에 포함되는 페이지 동작과 최소 스타일.
- `GET /login.js`, `GET /api/session`: 입장 화면 동작과 비밀번호 설정·로그인 여부만 반환.
- `POST /api/login`, `POST /api/logout`: 로그인 쿠키 발급·해제만 수행. 스케줄·설정 수정 경로 없음.
  Origin과 JSON 본문을 검사하며 본문은 최대 128바이트입니다.
- 등록되지 않은 경로는 404, 그 외 POST는 405. 파일 경로나 디렉터리 조회 경로 없음.
- 로컬 Host 검사, HTML·API 응답 no-store, 정적 파일 ETag 재검증, 프레임 삽입 차단. 최대 요청 스레드 8개.
- 종료 요청은 사설 파일로 전달하며 웹에 종료·관리 API를 노출하지 않습니다.
- 방화벽·공유기 변경이나 외부 공개는 아직 하지 않습니다. DDNS는 별도 데스크톱 모듈에서 처리합니다.

Python 기본 HTTP 서버는 이 단계의 로컬 확인에만 사용합니다. 외부 공개 전에
운영용 HTTP/HTTPS 처리로 확장해야 합니다. 현재 인증도 외부 HTTP 공개 용도로 사용하지 않습니다.
[Python HTTP 서버의 운영용 제한](https://docs.python.org/3/library/security_warnings.html)

## 스케줄 연결과 자동 갱신

원본은 항상 GUI 메모리의 현재 스케줄입니다. 기존 공유용 수집 함수를 Tk 스레드에서
읽기만 하며 웹 요청 때문에 화면 갱신·저장·OCR·GitHub 업로드를 호출하지 않습니다.
어제 0시부터 다음 표시 제한(정기점검/삭제 기준)까지, 최대 앞으로 14일을 수집합니다.
휴식시간은 프로그램의 `휴식시간 추가` 설정을 따릅니다. 출현 중/시간 미확정 항목은
예약 보스로 계산하지 않고 별도 목록으로 표시합니다. 임시 초 보정 미리보기는 공개하지 않습니다.

웹 사용 중에만 3초마다 새 조회용 사본을 전달합니다. 별도 DB를 만들지 않습니다.
코디네이터 스레드가 JSON 변환·원자적 파일 교체를 수행하고, 워커가 1초 간격으로
세션별 파일을 읽어 검증한 뒤 메모리에 보관합니다. HTTP 요청은 이 메모리만 읽습니다.
브라우저는 겹치지 않는 15초 상태 polling을 사용하며 변경 시에만 전체 자료를 받습니다. 숨겨진 탭에서는 요청을 멈춥니다.
각 단계의 확인 주기가 더해져 실제 변경 표시까지 약 10초가 걸릴 수 있습니다. 네트워크 지연은 별도입니다.

자료 내용이 바뀔 때만 revision/updated_at을 바꾸며 수집 시각은 계속 갱신합니다.
15초 동안 자료 갱신이 없거나 자료 읽기가 실패하면 마지막 자료임을 표시합니다.
브라우저 연결 실패 때도 마지막 표를 보존하고 카운트다운은 계속 계산하며, 연결 상태에 `갱신 대기`를 표시합니다.
시간은 관리자 PC의 시간/오프셋을 기준으로 계산하며 마이크로초를 JSON에서 보존합니다.
브라우저 남은 시간은 네트워크 지연 때문에 측정용 초읽기와 미세한 차이가 날 수 있습니다.

공개 필드는 보스명·종류·일정·휴식 종료·중요 표시·서버/시즌·자료 상태로 제한합니다.
원본 저장 문서·설정·Discord 토큰·로컬 경로·내부 세션 ID는 반환하지 않습니다.

## 수명과 진단

워커는 GUI 부모 프로세스를 감시합니다. Windows에서는 프로세스 핸들을 유지해
부모 PID가 재사용돼도 이전 워커가 계속 동작하지 않도록 합니다.
GUI는 실행 세션·PID·프로토콜·포트가 일치하는 응답만 사용합니다.
빠른 ON/OFF나 재시도에서 이전 실행의 응답은 새 상태에 적용하지 않습니다.
시작 제한 시간은 20초, 정상 실행 중 상태 갱신 제한 시간은 10초입니다.
웹 오류 후 자동으로 반복 시작하지 않고 재시도를 제공합니다.

설정·상태·로그는 `%APPDATA%\BossTimer\web_service`에 둡니다.

- `settings.json`: 웹 사용 여부, 선택한 포트.
- `access_settings.json`: 솔트·PBKDF2 검증값·쿠키 서명 키·로그인 세대·차단 목록.
  현재 비밀번호 표시용 값은 Windows 사용자 DPAPI로 암호화하여 함께 저장합니다.
  비밀번호 평문을 보관하지 않으며 HTTP에서는 이 파일의 필드를 노출하지 않습니다.
- `visitors.json`: 최대 1,000개 브라우저의 최근 접속과 최대 200개 로그인 실패 기록.
  마지막 접속/실패 시각을 기준으로 30일 보관하고 웹 기동·실행 중 만료 기록을 정리합니다.
  접속 관리 화면에는 최근 7일만 표시하며 로그인 실패 요약은 이 기간의 최근 30건입니다.
  웹서비스를 꺼도 화면의 캐시된 목록은 최근 7일 기준으로 필터합니다. 차단 목록과 로그인 설정은 만료 정리 대상이 아닙니다.
  워커만 쓰고, 프로그램은 세션별로 정리된 접속 상태만 읽습니다.
- `manager.log`, `worker.log`: 각 최대 256 KiB, 이전 로그 2개씩 보관.
- `network.log`: 진단 시작·항목별 결과·실패 종류·완료·종료 요청. 같은 회전 제한 적용.
- `network_diagnostics.json`: 마지막 진단 결과만 보존. IP 등 네트워크 정보는 로컬 관리창에서만 표시.
- `ddns_settings.json`: 자동 갱신 여부·주소 이름·DPAPI 암호문. 평문 Token을 보관하지 않습니다.
- `ddns.log`: 설정 저장·갱신 결과·DNS 확인·실패 종류. 같은 회전 제한 적용.
- 실행 세션별 상태·종료·조회 사본 파일: 종료 확인 후 해당 세션의 파일만 정리.
  조회 사본은 GUI/봇의 설정이나 실제 스케줄 저장 파일과 분리합니다.

HTTP 질의 문자열·쿠키·헤더와 향후 인증 토큰은 로그에 기록하지 않습니다.
웹 요청 수는 사람 수가 아니며 같은 사람이 페이지를 열고 새로고침하면 증가합니다.
브라우저 이름·IP 등도 실제 사람의 이름을 자동으로 알려주는 정보가 아닙니다.

## 비밀번호와 접속 관리

입장하지 않은 요청에는 스케줄을 반환하지 않습니다. 비밀번호 설정 파일을 읽을 수
없는 경우에도 인증을 해제하지 않고 조회를 중단합니다. 비밀번호 저장·검증에는
PBKDF2-HMAC-SHA256(600,000회)과 무작위 솔트를 사용합니다.
[Python PBKDF2 문서](https://docs.python.org/3/library/hashlib.html#hashlib.pbkdf2_hmac)

로그인은 서명된 HttpOnly·SameSite=Strict 쿠키로 기억합니다. 프로그램/워커 재시작 후에도
서명 키와 로그인 세대를 보존하며, 비밀번호 변경 또는 '모든 브라우저 로그인 해제'는 세대를
바꿔 기존 쿠키를 무효화합니다. 정책 반영은 약 1초, 열린 페이지의 재입장 처리는 다음
15초 상태 polling 때 수행됩니다. 브라우저 쿠키 삭제·시크릿 창에서는 다시 입장해야 합니다.
쿠키 유효기간은 365일이고 사용 중에는 하루 단위로 갱신합니다.
비밀번호나 인증 토큰을 JavaScript 저장소·URL에 넣지 않습니다.
[쿠키 속성과 유효기간](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)

로그인 검증은 최대 두 건을 동시에 수행하며 같은 IP에서 5분 내 5회 실패,
전체 5분 내 30회 실패, 전체 분당 30회 시도 시 일시 제한합니다.
로그인 실패·성공·제한·정책 변경·접속 기록 오류를 웹 전용 로그에 기록합니다.
해시 계산과 저장은 GUI 이벤트 흐름에서 수행하지 않습니다.

접속 목록은 약 5초마다 갱신합니다. 최근 60초 이내 인증 요청이 있으면 '조회 중'입니다.
브라우저 탭을 숨기면 스케줄 polling이 멈추므로 실제 창이 열려 있어도 '최근 접속'으로
바뀔 수 있습니다. 요청 수·브라우저 수는 실제 사람 수가 아닙니다.
HTTPS 시작·승계·재시도에서 사용하는 쿠키 없는 localhost `/api/session` 자체 점검은
방문 ID·쿠키·접속 기록을 만들지 않습니다. 정적 파일과 존재하지 않는 경로도 접속 목록에서 제외합니다.
외부 API 요청과 로그인 실패는 계속 기록하며, 로그인 이력이 없는 방문은 `미인증 방문`으로 표시합니다.
기존 기록은 보존합니다. 새 방문 진단에는 접속 IP·브라우저 구분·인증 여부를 기록하므로 자체 점검과
실제 입장을 구분할 수 있습니다. 공개 규칙 정리 실패 진단에는 방화벽·공유기의 오류 코드도 남깁니다.
IP는 실제 연결 소켓에서 읽으며 X-Forwarded-For 같은 헤더를 신뢰하지 않습니다.
이 단계는 localhost이므로 여러 브라우저가 같은 127.0.0.1로 표시될 수 있습니다.

브라우저 차단은 쿠키 삭제로 우회할 수 있습니다. IP 차단은 같은 IP의 다른 사람까지
포함하므로 프로그램의 중앙 확인 팝업에서 설명하고 적용합니다. 차단 해제는 웹서비스가
꺼져 있어도 가능합니다. 비밀번호 변경·차단 설정은 웹에서 호출할 수 없습니다.

## 다음 단계와 추가 관리 요구사항

1. 로컬 서버: 사용자 연결 확인 완료.
2. 로컬 스케줄 조회·최소 표·자동 갱신: 사용자 조회 확인 완료.
3. 네 자리 비밀번호·로그인 유지·접속 관리: 사용자 비밀번호 입장 확인 완료.
4. 네트워크 진단: 사용자 확인 완료. IPv4 공인 IP/공유기 WAN 일치, ipTIME IGD 발견.
5. 무료 DDNS와 주소 유지: 현재 단계, 사용자 실행 확인 대상.
6. HTTPS와 운영용 웹 통신.
7. 방화벽·자동 포트 개방·외부 바인딩.
8. 실제 외부 접속 확인.
9. 공개 시작·종료·주소 변경의 통합.

모바일 디자인·복사·TXT는 외부 접속 확인 후 추가했습니다. 타임라인은 별도 후속 범위입니다.

각 단계 완료 후 변경 범위를 보고하고 멈춥니다. 전체 프로젝트 회귀 테스트를 반복하지
않으며 문법·import·명백한 실행 오류만 확인합니다. 실제 기능 테스트와 빌드는 사용자 담당입니다.

## 사용자가 확인할 3단계 항목

1. 프로그램 → 스케줄 상단 `웹` → `웹서비스 사용` 체크.
2. `비밀번호` 탭에서 네 자리 저장 후 `브라우저에서 열기` → 비밀번호 입력 → 스케줄 확인.
3. 같은 브라우저를 닫았다가 다시 열고, 프로그램을 재시작해도 입장이 유지되는지 확인.
4. 시크릿 창에서는 비밀번호 입력이 필요한지, `/api/schedule` 직접 접속도 미입장 시 막히는지 확인.
5. 비밀번호 변경 또는 모든 브라우저 로그인 해제로 열린 페이지가 다시 입장을 요구하는지 확인.
6. `접속 관리`에서 선택 브라우저 차단·해제, IP 차단·해제를 확인.
   로컬 IP 차단은 이 PC의 다른 브라우저도 차단합니다. 프로그램에서 해제하면 다시 접속할 수 있습니다.
7. 잘못된 비밀번호 5회 입력 후 일시 제한, 접속 관리의 실패 횟수·최근 시각 확인.
8. 스케줄 자동 갱신·웹 사용 OFF·GUI 종료·웹 재시작이 유지되는지 확인.
9. 실패하면 설정창의 `진단 로그 복사` 내용을 전달.

## 4단계 네트워크 진단 범위

이 단계는 공유기에 포트 생성·삭제 요청을 보내지 않으며, Windows 방화벽·네트워크
어댑터·DDNS·공유기 설정을 변경하지 않습니다. 관리자 권한을 요청하지 않습니다.
진단은 `네트워크` 탭을 처음 열 때와 `다시 진단`을 누를 때만 수행합니다.
프로그램 시작·일상적인 스케줄 갱신·매초 UI 갱신 때문에 인터넷 조회를 반복하지 않습니다.

1. Windows 기본 경로와 인터페이스 우선순위를 읽어 PC 주소·게이트웨이를 선택합니다.
   PowerShell은 고정된 읽기 전용 명령을 숨겨서 실행하며 제한 시간은 12초입니다.
   [Microsoft Get-NetRoute 문서](https://learn.microsoft.com/en-us/powershell/module/nettcpip/get-netroute)
2. Windows 방화벽 프로필 사용 여부를 읽습니다. 이 정보만으로 공개용 허용 규칙이
   준비됐다고 표시하지 않습니다. 개별 규칙은 HTTPS/포트 선택 후 공개 단계에서 관리합니다.
3. 웹서비스가 실행 중이면 localhost 포트의 TCP 응답을 확인합니다.
4. ipify HTTPS API로 공인 IPv4를 확인합니다. 공인 IPv6 기본 경로가 있으면 IPv6 전용
   API도 조회합니다. 프록시는 이 요청에서만 우회해 프록시 IP를 공유기 IP로 오인하지
   않도록 하며, 기존 Windows 인증서 검증 함수를 사용합니다.
   [ipify IPv4·IPv6 API](https://www.ipify.org/)
5. 선택한 기본 공유기에 SSDP 검색을 보내 UPnP IGD 서비스를 찾고
   `GetExternalIPAddress`로 공유기 외부 IP를 읽습니다. SSDP 응답·설명 XML·제어 URL은
   선택한 게이트웨이 IP만 허용하며 리디렉션·DTD·외부 엔터티를 거부합니다.
   [UPnP WANIPConnection 표준](https://upnp.org/specs/gw/UPnP-gw-WANIPConnection-v2-Service.pdf)
6. NAT-PMP에서는 외부 IP 조회(opcode 0)만 사용합니다. 포트 매핑 opcode는 보내지 않습니다.
   [RFC 6886 외부 IP 조회](https://datatracker.ietf.org/doc/html/rfc6886#section-3.2)
7. 공유기 외부 IP가 사설 주소/통신사 공유 주소이거나 조회한 공인 IP와 다르면
   상위 NAT·VPN·여러 회선 가능성을 표시합니다. 응답 없음은 '미지원'으로 단정하지 않습니다.

IPv6 통신 성공은 외부에서 들어오는 연결 성공을 의미하지 않습니다. UPnP 발견도
실제 포트 생성 권한/성공을 보장하지 않습니다. 현재 서버는 계속 127.0.0.1에만
바인딩하며 실제 외부 URL은 표시하지 않습니다. IPv6 사용자의 지원 여부·방화벽·상위
NAT와 외부 접속 검증은 이후 단계에서 확인합니다.

각 HTTP 요청은 3초, SSDP 수신은 2초, NAT-PMP는 총 약 1.75초 제한입니다.
시스템 DNS 조회 등이 길어져도 전용 스레드이므로 GUI/웹서버 상태 감시를 막지 않습니다.
중복 진단 작업은 만들지 않으며 프로그램 종료 시 취소 표시를 전달해 다음 단계 진행과
결과 반영을 중단합니다. 진행 중 네트워크 호출은 제한 시간까지 기다릴 수 있습니다.

### 사용자가 확인할 4단계 항목

1. 프로그램 다시 실행 → `웹 → 네트워크`: 추가 입력 없이 진단이 시작되는지 확인.
2. 진행 중 기존 스케줄 화면·Discord 송출·비밀번호 입장이 계속 동작하는지 확인.
3. PC 주소·기본 공유기·공인 IP·UPnP·상위 NAT 결과를 확인.
4. `진단 결과 복사` 내용 전달. 확인 못한 항목은 `진단 로그 복사`도 함께 전달.
5. 탭 전환·웹 창 재열기로 진단이 반복되지 않는지, `다시 진단`으로 새 결과가 나오는지 확인.

## 5단계 무료 주소

무료 공개 갱신 API와 이후 HTTPS의 DNS 인증 연결을 고려해 DuckDNS를 사용합니다.
ipTIME 공유기 설정 화면을 자동 로그인하거나 비공개 DDNS 등록 API를 호출하지 않습니다.
관리자의 최초 DuckDNS 로그인·주소 등록은 홈페이지에서 한 번 진행해야 합니다.
외부 계정 인증을 프로그램이 대신하거나 Token을 코드에 내장하지 않습니다.
[DuckDNS 공식 API](https://www.duckdns.org/spec.jsp)

`무료 주소` 탭에서 짧은 주소 이름 또는 전체 `이름.duckdns.org`와 홈페이지의 Token을
입력합니다. Discord Bot Token과 다른 값입니다. 저장 성공 후 입력칸의 Token은 지우며
이후 비워두면 기존 Token을 유지합니다. Token 변경 시에만 다시 입력하세요.
Windows DPAPI는 현재 사용자 계정 범위로 사용하며 다른 계정에서도 풀리는 머신 범위
옵션을 사용하지 않습니다. 다른 PC/Windows 계정으로 옮기면 Token을 다시 입력해야 할 수 있습니다.
[Microsoft DPAPI 설명](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata)

웹서버가 실제 실행 중이고 `무료 주소 자동 갱신`을 저장한 경우에만 자동 갱신합니다.
최초 실행은 바로 확인하고 이후 공인 IPv4를 5분마다 확인합니다. IP 변경 시 갱신하고
변경이 없어도 6시간 간격으로 유지 갱신합니다. UI의 `지금 갱신·확인`은 최소 30초 간격입니다.
화면 갱신·스케줄 변경·탭 전환 때문에 갱신 API를 반복 호출하지 않습니다.
웹서버 종료·오류 상태에서는 대기하고 프로그램 종료 시 작업을 중단합니다.
진행 중인 HTTPS 요청은 이미 전송되었으면 완료될 수 있지만 이후 단계와 늦은 결과 반영은
중단합니다. 새 실행/설정 세대가 이전 작업의 결과를 사용하지 않습니다.

공인 IPv4는 ipify HTTPS로 읽고 DuckDNS의 선택한 한 도메인 A 레코드를 갱신합니다.
Token을 포함한 HTTP 질의·URL·응답 본문·예외 전문은 로그나 웹 API에 내보내지 않습니다.
Windows 인증서를 검증하고 리디렉션은 허용하지 않습니다. 이 요청에서만 프록시를 우회합니다.
설정 저장·복호화·HTTPS·DNS 조회는 기존 서버 코디네이터와 분리된 스레드에서 수행합니다.
각 HTTPS 호출 제한 시간은 5초이며 시스템 DNS 지연은 GUI/Discord 흐름을 막지 않습니다.

DuckDNS `OK` 응답과 응답 IP·갱신 종류를 검증한 후 시스템 DNS로 주소를 조회합니다.
DNS 캐시/전파 때문에 다르면 `DNS 반영 대기`로 표시하며 다음 확인 때 재조회합니다.
주소와 IP가 일치해도 포트·HTTPS·방화벽·실제 외부 접속이 완료된 것으로 표시하지 않습니다.
기존 AAAA/TXT 레코드는 지우지 않습니다. 기존 주소에 IPv6 레코드가 있으면 표시하며
현재 IPv4 공개 방향과 맞는지 이후 공개 단계에서 확인합니다.
여러 PC에서 같은 도메인을 갱신하면 서로 다른 IP로 덮어쓸 수 있으므로 PC별로 주소를
나누거나 실제 공개하는 PC에서만 자동 갱신을 켜세요.

### 사용자가 확인할 5단계 항목

1. 프로그램 재실행 → `웹 → 무료 주소 → DuckDNS 홈페이지 열기`.
2. 홈페이지 로그인 → 원하는 주소 이름 등록 → 홈페이지 Token 복사.
3. 프로그램에 주소 이름/Token 입력 → 자동 갱신 체크 → 설정 저장.
4. 웹서비스가 실행 중이면 공인 IPv4와 `IPv4 DNS 일치` 표시를 확인.
   `DNS 반영 대기`면 잠시 뒤 `지금 갱신·확인` 또는 자동 확인을 기다립니다.
5. 프로그램 재시작 후 Token 재입력 없이 자동 확인되는지 확인.
6. 자동 갱신 OFF 저장, 웹서비스 OFF로 갱신이 대기하는지 확인.
7. Token은 대화나 로그에 붙여 넣지 말고, 실패 시 화면 상태 또는 `진단 로그 복사`를 전달.

현재 복사하는 것은 도메인 이름이며 외부 접속 가능한 웹 URL은 다음 단계에서 완성합니다.

## 6단계 HTTPS

`HTTPS` 탭에서 저장된 DuckDNS 주소/Token을 재사용합니다. 별도 웹서버 설치,
인증서 프로그램 설치, 이메일 입력, 웹 인증용 포트 개방은 필요하지 않습니다.
최초 이용약관 동의와 발급 버튼은 사용자가 직접 누릅니다. 인증기관은 Let’s Encrypt
운영 서버이고 등록한 도메인은 공개 인증서 투명성 기록에 남습니다.
[Let’s Encrypt DNS-01](https://letsencrypt.org/docs/challenge-types/)

소스 실행용 Python에는 `requirements-gui.txt` 의존성이 필요합니다.
EXE에서는 ACME·암호화·DNS·Cheroot 모듈을 포함하도록 기존 GUI spec과
DNS 동적 레코드/라이브러리 메타데이터 hook을 연결했습니다. 빌드 전 의존성이
없으면 산출물을 만들기 전에 안내합니다. 별도 웹 EXE는 만들지 않습니다.
이번 소스 작업에서는 의존성 설치 및 import만 확인하며 EXE 빌드는 하지 않았습니다.

발급 작업은 Tk·웹 코디네이터와 분리된 데몬 스레드에서 실행합니다. DNS 인증은
DuckDNS의 TXT 전용 API만 사용하고 A/AAAA는 변경하지 않습니다. 공개 DNS로 NS를
찾고 권한 DNS에 직접 TXT를 확인합니다. 네트워크 요청은 각각 제한 시간을 둡니다.
DNS 반영은 최대 약 3분, ACME 인증/최종 발급은 약 2분을 기다립니다.
정상 반영이면 훨씬 빨리 끝납니다. 수동 재발급 시도 간격은 10분이며 유효하고
갱신 시기가 아닌 인증서는 재발급 대신 재사용합니다.

인증용 TXT 값은 소유권 표시와 함께 유지합니다. 이전에 이 프로그램이 쓴 값만
다음 발급 때 교체하며 다른 서비스가 쓴 TXT는 덮어쓰지 않습니다. 종료/시간 초과 시
다른 PC의 인증 기록을 지우는 문제를 피하기 위해 자동 clear 요청을 하지 않습니다.
DuckDNS는 한 도메인의 하위 이름들이 같은 TXT를 공유하므로 공개 PC마다 다른
도메인을 사용하는 것이 좋습니다. Token·TXT 값·HTTP 요청/응답 전문은 로그에 쓰지 않습니다.
DuckDNS가 반환하는 내용이 빈 TXT 기록은 미설정으로 취급합니다. 실제 내용이 있는
외부 기록만 소유권 확인 대상으로 남기며, 미확인 기록이 곧 다른 서비스의 현재 사용을
뜻하는 것은 아니므로 오류 안내에서도 현재 사용 중이라고 단정하지 않습니다.
[DuckDNS TXT API](https://www.duckdns.org/spec.jsp)

ACME 계정 키는 DPAPI로 암호화합니다. 웹 인증서 개인 키는 암호화된 PKCS8으로 저장하고
해제 암호를 DPAPI로 저장합니다. 평문 개인 키 임시 파일을 만들지 않습니다.
SAN의 주소·키 일치·인증서 유효 기간을 확인한 뒤 세대별 파일을 만들고 current 포인터를
마지막에 교체합니다. 갱신 실패로 기존 인증서/스케줄을 덮어쓰지 않습니다.
무료 주소 설정 변경이나 웹 OFF/다시 ON으로 세대가 바뀌면 늦은 발급 결과는 적용하지 않습니다.

웹서비스가 켜진 동안 시작 시와 12시간마다 갱신 필요 여부를 확인합니다.
실제 인증서 유효 기간의 마지막 1/3 또는 만료 30일 전 중 짧은 기간부터 갱신합니다.
자동 실패 후에는 다음 확인 때 재시도하며 기존 유효 인증서로 계속 서비스합니다.
PC/Windows 계정을 바꾸면 DPAPI 비밀을 읽지 못할 수 있으므로 Token을 다시 입력하고
해당 PC용 인증서를 새로 준비해야 합니다. 인증서/키 디렉터리를 웹에서 제공하지 않습니다.

기존 `127.0.0.1:8765` HTTP는 그대로 유지합니다. HTTPS는 별도의 Cheroot WSGI
리스너로 `127.0.0.1:8766`에만 바인딩합니다. HTTPS 포트를 바꾸려면 발급·확인 버튼으로
저장하며 HTTP 포트와 같으면 거절합니다. 헤더 8KB, POST 본문 128B, 처리 스레드 8개,
대기 요청 32개, 연결 제한 시간 5초를 두고 Windows에서는 포트를 독점합니다.
TLS 1.2 이상·도메인 SNI·Host·Origin 검사와 Secure/HttpOnly/SameSite 쿠키를 사용합니다.
외부 프록시 주소 헤더를 신뢰하지 않고 실제 소켓 IP로 접속을 관리합니다.
리스너 오류는 HTTPS 상태와 웹 전용 로그에만 반영하며 로컬 HTTP와 Discord는 유지합니다.

`로컬 HTTPS 확인`은 DNS나 공유기 경유 없이 127.0.0.1에 연결하면서 실제 DuckDNS
도메인을 SNI/Host로 보내 인증서 체인·주소·TLS와 API 응답을 검증합니다.
`https://127.0.0.1:8766`을 브라우저에서 직접 열면 인증서 이름이 맞지 않으므로
이 단계에서는 전용 확인 버튼을 사용하세요. 브라우저의 기존 로컬 조회는 계속 HTTP로 합니다.
확인 성공도 외부 접속 성공을 뜻하지 않습니다. 방화벽/UPnP와 외부 HTTPS 주소는 다음 단계입니다.

### 사용자가 확인할 6단계 항목

1. 프로그램 재실행 → 웹서비스 ON → `웹 → HTTPS`.
2. 약관 확인·동의 체크 → `무료 인증서 발급·확인` (포트 8766 유지).
3. 발급 진행/만료일과 `로컬 HTTPS 실행 중`을 확인.
4. `로컬 HTTPS 확인` → `로컬 TLS·주소·인증서 검증 성공` 확인.
5. 프로그램 재실행 후 유효 인증서를 재사용하고 HTTPS가 시작되는지 확인.
6. 실패 시 Token 대신 HTTPS 화면 상태와 `진단 로그 복사` 내용 전달.

필요한 로그는 기존 manager/worker 로그와 새 https.log에 단계·오류 종류만 기록합니다.
웹 전용 JSON 읽기·교체는 파일별 Windows 명명 뮤텍스로 GUI/워커 사이에서 보호합니다.
읽기를 마친 뒤 교체하며 파일 교체를 기다리는 시간은 최대 1초로 제한합니다. 외부 프로그램의
일시적인 교체 거부는 최대 약 0.2초 재시도합니다. 상태 보고 파일 저장 실패만으로 HTTP/HTTPS를
즉시 종료하지 않고 재시도하며, 실패/회복을 로그에 기록합니다. 실패가 계속돼 10초간
상태 보고가 없으면 기존 관리자 감시에서 웹 워커를 오류로 처리합니다.
이번 단계에서는 실제 인증서 발급/서버 실행/접속 테스트를 대신 수행하지 않았습니다.

## 7단계 IPv4 직접 공개

`외부 공개` 탭에서 `웹서비스 외부 공개`를 켭니다. 추가 주소·포트·비밀번호 입력은
필요하지 않습니다. 기존 무료 주소 자동 갱신과 HTTPS 인증서·네 자리 입장 설정을 사용합니다.
이 단계는 확인된 IPv4/UPnP 경로를 연결하며, IPv6 및 NAT-PMP 개방은 구현하지 않았습니다.
관련 읽기 전용 진단은 계속 제공하며, UPnP 응답이 없으면 기존 웹서버를 유지하고 안내합니다.

공개 준비 스레드는 웹 코디네이터·Tk·Discord에서 분리됩니다. 시작 시 인증서와 실제
로컬 HTTPS 응답/비밀번호 설정, 기본 경로와 UPnP IGD, 공유기 WAN IPv4와 ipify 공인 IP
일치를 확인합니다. 다중 NAT/CGNAT/VPN 등으로 일치하지 않으면 포트를 열지 않습니다.
Windows 방화벽 설정에는 관리자 권한이 필요합니다. 기존 GUI EXE의 관리자 실행 설정을
유지하며 소스 디버깅이 일반 권한이면 권한 필요 안내를 표시합니다.

방화벽은 프로그램 경로·현재 LAN IPv4·HTTPS 내부 포트의 TCP 인바운드 규칙만 생성합니다.
프로필은 Any이지만 전체 방화벽을 끄거나 일반 Python/다른 포트를 일괄 허용하지 않습니다.
규칙 이름과 그룹·설명에 저장된 전용 소유자 ID를 사용하고 ActiveStore를 읽어 등록을 확인합니다.
별도 차단 규칙·회사 정책 등의 효과까지 허용 성공으로 단정하지 않으며 실제 접속은 다음 단계입니다.
PowerShell은 고정 스크립트와 환경 변수 JSON을 사용하고 사용자 값을 명령어로 조합하지 않습니다.
[Microsoft New-NetFirewallRule](https://learn.microsoft.com/en-us/powershell/module/netsecurity/new-netfirewallrule)

UPnP는 진단에서 발견한 기본 공유기의 제어 주소만 사용합니다. TCP 외부 포트 443을 먼저
확인하고 사용 중이면 8443, HTTPS 내부 포트 순으로 시도합니다. 기존 매핑이 있고 BossTimer의
설명 ID·내부 IP·내부 포트가 모두 일치하지 않으면 건드리지 않습니다. 포트 값 일치가 필요한
공유기의 오류 724에는 내부 포트와 같은 후보로 계속 시도합니다.
기본 임대는 1시간이며 20분마다 조회·갱신합니다. 영구 임대만 지원하는 오류 725에는
임대 0으로 요청하고 표시합니다. 설정/네트워크 변경 감지 시 공개를 중단하고 재시도를 안내합니다.
수신 SOAP XML은 크기 제한·DTD 금지·서비스/응답 검사 후 사용합니다.
[UPnP WANIPConnection 규격](https://upnp.org/specs/gw/UPnP-gw-WANIPConnection-v1-Service.pdf)

규칙을 변경하기 전에 `public_resources.json`에 소유권과 회수 정보를 저장합니다.
실패·OFF·웹서버 오류·정상 종료에는 공개 요청을 먼저 해제하고 매핑을 다시 조회한 뒤
현재도 본인 소유인 매핑만 삭제합니다. Windows 규칙도 이름/그룹/설명이 일치할 때만 삭제합니다.
삭제 실패는 로그와 자원 기록에 남겨 다음 시작·재시도에서 정리합니다. 강제 종료/공유기 장애로
즉시 정리를 보장할 수 없는 경우에도 리스너는 워커 종료와 함께 닫히며 유한 임대는 만료합니다.
영구 임대나 남은 방화벽 규칙은 다음 실행에서 소유권 확인 후 회수합니다.

공개 제어는 10초마다 45초 유효 기간의 `public_listener.json` 요청을 갱신합니다.
현재 워커의 실행 ID, 인증서 도메인/포트와 일치할 때만 HTTPS를 IPv4 `0.0.0.0`에 바인딩하고
외부 포트의 Host/Origin도 허용합니다. IPv6 및 기본 HTTP는 외부에 열지 않습니다.
요청이 만료되거나 OFF/설정 오류이면 HTTPS를 127.0.0.1로 되돌립니다. 예약 갱신을 제외하면
일상 유지 중 방화벽 명령·UPnP API를 계속 호출하지 않으며 공개 요청 갱신은 로컬 파일 작업입니다.
공개/로컬 전환 시 HTTPS가 짧게 다시 바인딩될 수 있지만 기본 HTTP/GUI/Discord는 유지합니다.
한 PC의 공개 과정 실패가 OCR/스케줄/음성/Discord 프로세스를 종료하지 않습니다.

공개 준비 후 URL을 표시합니다. 외부 포트 443이면 `https://이름.duckdns.org`, 다른 후보면
`https://이름.duckdns.org:포트`입니다. 자동 설정 성공과 로컬 TLS 응답만으로 인터넷 접속
성공을 표시하지 않습니다. 화면에는 `공개 준비 완료 · 외부 접속 미검증`을 구분해 표시합니다.
같은 공유기의 공개 주소 접속은 NAT loopback 지원에 영향을 받으므로 실제 확인은
휴대폰 Wi-Fi를 끄고 모바일 데이터에서 비밀번호 입장/스케줄 조회로 진행합니다.
기존 AAAA 레코드가 있으면 브라우저가 다른 IPv6 주소를 시도할 수 있습니다. 이 단계에서는
AAAA를 임의로 지우지 않으며 IPv4 포트 준비만 표시합니다.

### 사용자가 확인할 7단계 항목

1. 프로그램 재실행 → 웹서비스 ON → `웹 → 외부 공개`.
2. `웹서비스 외부 공개` 체크 → 방화벽·공유기·HTTPS 준비 상태 확인.
3. 공개 주소 복사 → 휴대폰 Wi-Fi OFF → 모바일 데이터로 주소 접속.
4. 기존 웹 비밀번호 입력 → 스케줄 조회. 실패 시 상태와 진단 로그 전달.
5. 외부 공개 OFF 후 공개 연결이 닫히고 같은 PC의 기본 HTTP는 유지되는지 확인.
6. 재실행 시 저장된 공개 설정을 재사용하고 자체 규칙을 다시 준비하는지 확인.

이번 소스 수정에서는 구문/import와 정적 PowerShell 구문만 확인합니다.
실제 방화벽 변경·UPnP 변경·웹서버 실행·외부 접속·EXE 빌드는 실행하지 않았습니다.
외부 접속 결과를 확인한 뒤 다음 단계의 접속 진단 표시를 보완합니다.

## 외부 접속 확인 후: 모바일 스케줄 화면

- 모바일 한 열 레이아웃. 지난 보스는 상단 두 줄과 전체 목록의 최근 두 항목만 취소선으로 표시합니다.
- `다음 보스`/`다가오는 보스` 제목을 생략하고 다음 보스 시간·이름·큰 카운트다운과 그다음 보스 한 항목을 표시합니다.
- 전체 목록은 날짜별로 구분하고 시간·보스·종류·남은 시간을 표시합니다. 휴식시간은 진행 중 상태와 종료 시간을 계산합니다.
- 전체 탭 본문은 선택한 날짜 한 날을 표시합니다. 시간 오른쪽 `오늘 / 다음날`로 이동합니다.
  복사 기간은 기본/24시간/48시간/전체이며 기본 기간은 다음 날 08시까지, 17시 이후에는 다다음 날 08시까지입니다.
  실제 관리자 프로그램에서 제공한 범위를 넘겨 일정을 생성하지 않습니다.
- 고정보스/휴식시간 표시, 보스색/고정보스색을 선택할 수 있습니다. 웹 전용 보스 색상 규칙을 사용하고, 설정 참조 항목은 저장된 글자색·배경색을 보정 없이 적용합니다.
- 텍스트 복사와 읽기용 TXT 저장은 날짜 제목과 `시간 보스명`을 출력합니다. 서버 자료를 수정하지 않습니다.
- 이미지 복사/PNG 저장/지원되는 모바일 파일 공유. 현재 조회 기간과 표시 옵션을 따르고 지난 두 항목은 이미지에서도 취소선을 표시합니다.
  긴 스케줄은 이미지당 최대 60개 항목으로 나눠 각 페이지를 복사·저장합니다. 미리보기는 열었을 당시의 일정입니다.
- 전체 알람은 모든 날짜에 적용됩니다. 보스별 선택은 이름+종류를 기준으로 유지하되, 주요 탭에서 일괄 변경한 날짜에는 해당 날짜의 선택을 우선합니다.
- 오늘/내일/모레 주요 탭의 `주요 알람`은 선택한 날짜의 주요 보스만 ON/OFF합니다. 다른 날짜의 같은 보스와 일반 보스의 선택은 유지합니다. 주요 보스가 없으면 버튼을 비활성화합니다.
  서버·시즌별로 브라우저 localStorage에 선택만 저장합니다. PC/Discord 설정 변경, 음성 재생, 알림 권한 요청은 하지 않습니다.
  전체 선택은 모든 개별 선택을 ON/OFF로 맞추며 새로운 보스도 마지막 전체 선택을 따릅니다. 기본 OFF입니다.

### 데이터와 갱신 구조

관리자 프로그램이 원본입니다. GUI의 기존 캡처/스냅샷 생존 확인 주기는 유지하고,
웹은 받은 일정으로 카운트다운·다음 보스·지난 항목을 직접 계산하며 매초 서버에 요청하지 않습니다.
다음·다다음 보스와 1시간 이내 일정만 초까지 표시하고, 그 이후 일정은 `시:분`으로 표시합니다. 분 단위 표시는 올림하여 남은 시간을 줄여 보이지 않게 하며, 1시간 경계에 도달하면 자동으로 초 표시로 전환합니다.
최초 접속에는 `/api/schedule`을 받고, 이후 15초마다 작은 `/api/status`로 갱신 여부와 서버 시각을 확인합니다.
`schedule_version`이 바뀐 경우에만 전체 일정을 다시 받습니다. 실행 세션이 달라져도 버전이 달라집니다.
연속 실패 시 재시도 간격은 15→30→60→120초로 늘리고, 성공하면 15초로 돌아옵니다.
여러 브라우저의 조회가 몰리지 않게 최대 1초의 분산 시간을 더하며 서버의 `Retry-After`도 따릅니다.
정상 상태에서 관리자 수정 반영은 확인 간격만큼 지연될 수 있습니다.
화면이 숨겨지면 폴링과 화면 갱신을 멈추고, 다시 보이면 시각/버전을 확인합니다.
연결이 끊겨도 열린 페이지의 마지막 일정으로 시간 계산은 계속하며 갱신 대기 상태를 표시합니다.
조회 실패를 최신 일정으로 표시하거나 브라우저에 스케줄/비밀번호를 영구 저장하지 않습니다.
프로그램 종료 후 새 페이지 접속은 불가능합니다. 별도의 상시 서버나 오프라인 설치형 서비스가 아닙니다.

페이지 스타일과 브라우저 코드만 `web_service_page.py`/`web_schedule_frontend.py`에 격리합니다.
API 인증/차단과 기존 HTTPS 공개 절차는 유지합니다. 이미지 미리보기용 CSP `img-src 'self' blob:`만 추가합니다.
외부 CSS/폰트/JS/CDN을 사용하지 않고 PNG/TXT도 브라우저 안에서 생성합니다.

디자인 참고: [Linear interface refresh](https://linear.app/now/behind-the-latest-design-refresh),
[Material 3 typography](https://m3.material.io/styles/typography/applying-type).
클립보드 호환성 참고: [MDN Clipboard.write](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard/write),
[WebKit Async Clipboard](https://webkit.org/blog/10855/async-clipboard-api/).

확인할 항목: 320~430px 휴대폰 화면, 자정/17시 경계, 지난 항목 최대 두 개, 시간 경과 후 다음 보스 전환,
PC 일정 수정 후 자동 갱신, 알람 선택 재접속 유지, 전체/개별 선택, 이미지 페이지 이동 및 PNG/TXT 공유.
실제 휴대폰 테스트와 빌드는 사용자가 진행합니다.

### 스케줄 중심의 간결한 배치

상단 브랜드 대신 `서버 길드 이름 n차`와 `복사`, `로그아웃`을 한 줄로 표시합니다.
상단 제목 글자 크기는 기존보다 4px 줄이고, 폭이 부족하면 제목의 차수를 생략합니다. 매우 긴 이름은 말줄임하며 전체 제목은 유지합니다.
시간/연결 상태는 좌/우로 표시하고 실제 시각 숫자만 진한 녹색으로 강조합니다.
프레임 제목은 현재 날짜 `mm월 dd일 요일`이며, 오른쪽 끝에 `전체 알람`을 둡니다.
사용자 탭에서 선택 목록이 있으면 설정 버튼은 날짜·시각 묶음과 별도 형제 요소
`#custom-clock-actions`에 놓입니다. 버튼은 최소 80×40px이며, 헤더의 flex 줄바꿈으로
폭이 부족하면 사용자 알림부터 아래로 옮기고 더 좁아지면 설정도 같은 줄로 내립니다.
시계의 고정 8ch 슬롯은 유지하고 내일·모레 표시는 시계와 한 묶음으로 둡니다.
리사이즈 감시나 초 단위 DOM 재배치 없이 CSS로 처리합니다. (페이지 개정 152)
그 아래 하나의 프레임에 지난 두 보스, 다음/다다음 보스, 나머지 일정을 이어 붙입니다. 다음 보스 하단의 날짜·종류는 생략합니다.
페이지 개정 156부터 지난 보스는 일반 테마 최대 2개, 아이언맨 최대 1개입니다. `recentBosses`가 실제 항목 수를
제한하며 같은 시각의 동시 젠도 예외로 늘리지 않습니다. 요약과 본문이 같은 선택 함수를 사용합니다.
다음 보스 영역에만 텍스트 선택·이미지 드래그를 막아, 마우스로 끌어도 글자 선택 블록이 생기지 않습니다.
요약에 표시한 보스는 아래 목록에 중복 표시하지 않습니다. 여백과 카운트다운 크기를 줄여 첫 화면의 일정 표시를 늘립니다.
배경/프레임의 두 톤을 사용하며 침공 행·요약에는 별도 세 번째 배경색을 적용합니다.

기간·보스색·고정보스색·고정보스·휴식시간과 공유 버튼은 `스케줄 복사` 팝업으로 옮겼습니다.
팝업은 선택 결과를 미리 보여주고 텍스트/이미지/TXT에 같은 옵션을 적용합니다.
복사 옵션은 본문을 필터링하지 않습니다. 본문은 기존 기본 조회 기간을 유지하며 행을 `시간 보스명 (남은 시간)`으로 표시합니다.
본문에서는 휴식 행을 숨기고, 현재 진행 중인 휴식만 남은 기간을 `휴식 중 <1시간 28분>` 형태로 표시합니다.
휴식이 자정을 넘어도 시작 날짜로 지난 날짜 제목을 만들지 않습니다. 종료 시각에 도달하면 상태 표시를 숨깁니다.
이미지/텍스트 공유와 복사 미리보기에서는 기존 휴식 체크 옵션을 유지합니다. 내부 행 배경을 조금 밝게 조정합니다.
이미지와 텍스트의 제목도 서버/길드/시즌 정보로 바꿉니다. 브라우저 알람 선택과 조회 API는 유지합니다.

일반 일정과 다다음 보스는 같은 `[시간] 보스명 (남은 시간)` 배치를 사용합니다.
남은 시간 글자 크기는 보스명과 같으며, 예정 시각까지 1시간 이내이면 빨간색으로 표시합니다.
다음 보스의 큰 카운트다운은 4px 줄이고, 다다음 보스와 이후 행의 여백·알람 버튼 높이를 줄였습니다.
전체 알람 ON 배경은 녹색, OFF는 빨간색입니다. 개별 알람은 배경색 없이 OFF 점은 배경에 가까운 회청색, ON 점은 녹색 빛으로 표시합니다.
복사는 하늘색, 로그아웃은 빨간색입니다. 젠 시각은 굵은 흰색, 남은 시간은 기본 흰색/1시간 이내 빨간색이며 지난 보스의 회색은 유지합니다.
설정 참조 항목의 고정보스 글자색·배경색은 PC의 색상 표시 체크를 변경하지 않고 저장된 설정에서 읽습니다.

### 웹 전용 보스 색상과 숨김

색상 규칙은 읽기 전용 스냅샷에만 적용하며 PC 설정·원본 스케줄·Discord 표시는 바꾸지 않습니다.
일반 보스 2·3·4챕은 흰색, 5챕은 연한 나무색, 6챕은 연남색, 던전은 아이보리 글자입니다.
7·8챕과 절대자는 보스 설정의 글자색·배경색을 사용합니다. 최하층강글·최하층스네르·최하층굴베는 아이보리 글자/황토색 배경입니다.
침공 보스는 보스 설정의 `침공 글자색`과 `침공 배경색`을 직접 읽어 적용합니다.
고정보스 기본 글자는 하늘색, 핏빛고블린·황금고블린은 노란색, 지옥성채 정예는 보라색입니다.
월드보스·닻·공성전·쟁탈전·방어전·점령전은 고정보스 설정의 글자색·배경색을 사용합니다.
신청/마감(방어전 신청, 점령전 신청, 방어전 신청마감, 점령전 신청마감), 공성전 공격대상 선택, 공성전 입찰시작은 웹 데이터에서 제외합니다.
요약·조회 목록·웹 복사 미리보기·이미지·TXT에도 같은 숨김이 적용됩니다. PC의 해당 일정은 보존합니다.
웹 복사 옵션의 색상 체크를 끄면 지정 배경색도 끄고 기본 테마로 내보냅니다. 지난 보스의 회색 취소선은 유지합니다.

### 배포 포함 방식

스케줄 HTML/CSS는 `web_service_page.py`, JavaScript는 `web_schedule_frontend.py`,
입장 페이지는 `web_service_login.py`에 내장되어 있습니다. `boss_timer_gui.spec`의
hiddenimports에 웹 worker와 세 페이지 모듈을 명시하여 GUI EXE 안에 포함합니다.
별도 HTML/CSS/JS 파일을 배포 폴더에 복사할 필요는 없습니다. 사용자 수동 빌드 시 현재 소스가 반영됩니다.
DuckDNS Token, 웹 인증 설정, 인증서 개인키와 사용자 일정은 공용 배포 ZIP에 넣지 않습니다.

### 공동 관리 고정 주소: 구현 완료, 실제 두 PC 검증 필요

같은 길드의 주소 하나와 DuckDNS 계정/Token 하나를 신뢰하는 공동 관리자들이 사용하면
주소를 유지하면서 대상 공인 IP를 바꿀 수 있습니다. 현재는 `web_independent_controller.py`가 웹을 독립적으로 실행합니다.
권한이 없는 PC는 로컬 웹서버만 유지하고 외부 접속·DNS 갱신·인증서 갱신을 중지합니다.

처음 연결과 승계 모두 받는 PC의 현재 로컬 스케줄을 웹에 표시합니다.
웹 승계는 스케줄 업로드 결과·자료 버전·수동 동기화 여부와 무관하게 진행합니다.
스케줄을 자동 다운로드하거나 관리자 프로그램에 적용하지 않습니다. 필요하면 사용자가 수동 동기화합니다.
Discord 권한 확보 직후 음성 입장과 웹 설정·인증서·로컬 HTTPS 준비를 병행합니다.
기존 웹 담당자가 없는 첫 연결은 권한 확보 직후 음성 입장과 외부 공개를 병행합니다.
다른 PC의 웹을 인계할 때는 음성 입장 성공 후 기존 웹의 종료를 확인하고 공개를 전환합니다.
음성 입장 실패 시 기존 공개를 유지하며, 새 웹의 공개 실패 시 기존 웹 담당을 복구하는 절차를 유지합니다.

`web_shared_state.py`가 인증서/개인키, 로그인 서명 키·비밀번호 검증 정보, 차단 목록, DNS 인증 TXT 소유 정보를
DuckDNS Token을 키로 AES-GCM 암호화하여 승계 저장소로 전달합니다. Token 자체는 저장소에 올리지 않습니다.
연결 준비 후 암호화된 공동 상태를 내용 변경 시에만 업로드하며, 인계 시점에도 요청 ID별 암호화 상태를 전달합니다.
각 PC에는 동일한 길드 주소와 Token을 직접 입력합니다. 다른 PC의 Windows 보호 파일을 복사하지 않습니다.
외부 포트는 처음 성공한 포트를 고정해 전달합니다. 해당 포트를 확보할 수 없으면 주소를 다른 포트로 바꾸지 않고 웹 오류로 처리합니다.
같은 공유기에 이전 담당자의 포트 규칙이 남으면 암호화된 인계 정보와 소유 표시가 일치하는 BossTimer 규칙만 회수합니다.
만료된 인계 인증서는 공개에 사용하지 않고 DNS 인증 소유 정보와 접속 설정만 이어받아 갱신을 준비합니다.
목록/페이지 파일은 GUI EXE에 내장되며 새 웹 브리지·권한 게이트·공동 상태 모듈도 빌드 목록에 포함합니다.
DNS 캐시로 인해 주소 교체 직후 일부 사용자는 이전 PC로 접속할 수 있어 무중단 전환을 보장할 수 없습니다.
외부 공개는 원격 권한 기록을 5초마다 확인하며 10초 유효 기간으로 제한합니다.
`web_authority_gate.py`의 실행 ID/만료 확인을 HTTPS 바인딩과 모든 외부 HTTP 요청에서 각각 검사합니다.
권한 반납 시 바로 임대를 차단하고 공개 포트/방화벽 규칙을 정리합니다. 임대 갱신이 멈추면 기존 리스너도 스스로 차단합니다.
DNS 주소는 반납 때 삭제하지 않습니다. 새 담당자의 스케줄·HTTPS·공개 포트 준비 후에만 그 PC의 IP로 갱신합니다.

외부 공개 탭의 `웹 강제 승계/재시도`는 현재 Discord 권한을 재검증하고 웹 프로세스/공개 준비만 다시 시작합니다.
권한이 없으면 거부하고, 진행 중이던 오래된 웹 작업은 재시도 세대로 취소합니다. Discord 연결·송출권한은 건드리지 않습니다.
`웹 긴급 중지`는 요청을 즉시 차단하고 웹서비스를 OFF로 저장한 뒤 소유한 웹 자식 프로세스를 종료합니다.
정상 종료 2초 → terminate 1초 → kill 1초의 기존 종료 경로를 사용합니다. 웹 재시도로 다시 켤 수 있습니다.
기존 배포본의 GUI에는 이 차단 기능이 없으므로 공동 관리 PC들의 GUI는 모두 이번 소스로 교체해야 합니다.

오늘 확인할 순서:
1. 두 PC의 시즌/게임 서버, DuckDNS 주소/Token을 맞추고 웹서비스를 켭니다.
2. 첫 PC가 Discord 권한을 얻으면 공개 주소가 생성되는지 확인합니다.
3. 둘째 PC는 봇만 연결한 상태에서 스탠바이이며 DNS를 갱신하지 않는지 확인합니다.
4. 둘째 PC가 Discord 권한을 승계하면 수동 동기화 없이 그 PC의 현재 스케줄로 같은 웹 주소에 연결되는지 모바일 데이터로 확인합니다.
5. 로그인 유지, 개별 알람 선택 유지, 이전 PC의 외부 접속 차단을 확인합니다.
6. 웹 실패 상태에서 `웹 강제 승계/재시도`, 정상 운영 중 `웹 긴급 중지`와 재시도를 확인합니다. Discord는 계속 송출해야 합니다.
7. 로그의 `web_authority_changed`, `web_handover_local_schedule_prepared`, `web_shared_state_imported/published`,
   `web_handover_prepare_failed`, `web_public_retry_requested`, `web_emergency_stop_requested`를 확인합니다.

DuckDNS 공식 API: https://www.duckdns.org/spec.jsp

## 웹 화면 수동/자동 업데이트

`웹 → 서비스 → 웹 화면 업데이트`에서 `수동 웹 업데이트`를 누릅니다.
기본 자동 업데이트는 체크 ON, 매일 한국시간 03:00입니다. 시간을 입력하고 `설정 저장`으로 바꿀 수 있습니다.
03:00을 지나 처음 켜는 경우 웹서비스가 켜져 있으면 그날 한 번 확인합니다.
웹서비스 OFF에서는 자동 확인하지 않으며 수동으로 파일만 받아두면 다음 ON 때 적용됩니다.
스탠바이 관리자도 자기 PC의 파일을 업데이트할 수 있습니다. 송출권한/DuckDNS Token은 업데이트 조건이 아닙니다.
확인 실패도 그날 한 번으로 기록하므로 반복 요청하지 않습니다. 실패 후에는 수동 버튼으로 재시도합니다.

업데이트 원본은 기존 공개 저장소 `pulpul7/pulpul7-boss_timer_app`의 **main 브랜치 `web_assets/`**입니다.
이 폴더를 처음 GitHub에 올려야 다른 PC에서 받을 수 있습니다. 이 작업에서 GitHub 업로드는 수행하지 않습니다.
외부에서 이 파일을 수정·커밋하면 각 관리자는 수동 업데이트 또는 예약 시각에 새 파일을 받습니다.
릴리스 ZIP 생성, 해시 수동 입력, 관리자별 별도 주소 설정은 필요하지 않습니다.

복사 후 다시 검증하며 완료 전에는 실행 중 파일을 덮어쓰지 않습니다.

## 전체 / 오늘 주요 / 내일 주요 / 모레 주요

보스 스케줄 창의 `웹` 버튼은 이 PC의 공개 준비가 완료되고 웹 공개 권한·스케줄 반영이 유효하면 녹색으로 바뀝니다.
Discord 송출 상태 오른쪽에 `웹 공개 중 / 웹 준비 중 / 웹 대기 / 웹 오류 / 웹 OFF`를 표시합니다.
다른 PC가 웹을 유지하는 분리 운영은 `웹 별도 PC`로 구분합니다.
기존 스케줄 게시 주기(약 3초)에서 로컬 상태만 읽어 갱신하며 외부 접속 확인 요청은 추가하지 않습니다.

웹의 복사 창에서 **텍스트 복사**와 **TXT 저장**은 날짜별 제목 아래 `HH:MM 보스명`으로 출력합니다.
날짜 제목은 `10월 12일 월요일` 형태이며 날짜 사이에는 빈 줄을 하나 넣습니다.
서버·길드 제목, 조회 기간, 별표, 종류, 경과 문구는 텍스트에 덧붙이지 않습니다.
텍스트·TXT는 기간·고정보스 선택을 따르되 휴식은 항상 제외합니다. 이미지·미리보기는 기존 `휴식시간` 선택을 따릅니다. **초단위 표시 (텍스트·TXT)**는 기본 해제입니다.
체크하면 시간만 `HH:MM:SS`로 바뀝니다. 이미지의 시간과 보스명은 모두 22px로 표시하며 겹치지 않게 간격을 계산합니다.

웹 상단 서버·길드·차수 글자는 기존보다 4px 키웠습니다. 현재시간 레이블은 제거하고
날짜 오른쪽에 `HH:MM:SS`를 표시합니다. 시간도 기존보다 4px 키우고 기본 박스 배경을 조금 어둡게 했습니다.
기존 시간 위치에는 `전체`, `오늘 주요`, `내일 주요`, `모레 주요` 탭을 배치했습니다.
선택한 탭은 진한 배경·파란 테두리로 구분하며 마우스/터치와 방향키·Home/End를 지원합니다.

주요 기준은 현재 보스 설정의 별표와 고정보스의 공성전, 쟁탈전, 길던/길드던전,
지옥 성채, 트리니티 리그, 점령전, 방어전입니다. 지옥성채 정예는 별표가 있어도 주요 탭에서 제외합니다.
침공 보스도 본서버 보스의 별표를 따릅니다. `침공 미미르`는 미미르의 별표가 켜져 있으면 주요 보스로 분류하며, 설정한 별명으로 표시되는 경우도 기존 이름 해석을 사용합니다.
고정보스는 표시 별명보다 설정의 원래 이름을 우선해 분류합니다. 기존 숨김 신청/입찰 항목은 계속 제외합니다.
오늘/내일/모레는 관리자 PC의 날짜를 기준으로 하고, 주요 탭에서는 해당 날짜 전체를 사용합니다.
다음/다다음 보스도 선택한 탭 안에서 계산하며 지난 보스는 최대 두 개로 유지합니다.
이미지/텍스트 복사의 기간은 기존 설정을 따릅니다. 전체 탭은 `전체 알람`, 주요 탭은 선택한 날짜에만 적용되는 `주요 알람`을 표시합니다. 이 선택은 브라우저에 저장하며 별도 API 요청을 보내지 않습니다.

관리자 스냅샷의 별표/주요 여부 변경을 별도 `major_version`으로 확인합니다.
기존 15초 상태 조회에 브라우저의 주요 버전을 같이 보내고, 바뀌었을 때만 표시 메타데이터를 응답합니다.
별표만 바뀌면 전체 스케줄을 재다운로드하지 않습니다. 일정/이름/색/서버 등의 변경은 기존 전체 데이터 갱신을 사용합니다.
탭 전환과 초 단위 시간 표시는 브라우저 안에서 처리하므로 별도 API 요청이 발생하지 않습니다.
이 부분 갱신을 위해 GUI의 스냅샷/웹 API도 수정했으므로 이번 버전은 GUI 교체 또는 소스 재실행이 필요합니다.

### 날짜 이동·휴식 순서와 반복 요청 보호

전체 탭의 기본 날짜는 오늘입니다. `다음날`은 표시 중인 날짜에서 하루씩 이동합니다.
이미 오늘인데 `오늘`을 누르거나 다음날에 표시할 일정이 없으면 동작하지 않습니다.
주요 탭에서는 날짜 이동 버튼을 숨깁니다. 날짜·탭 전환은 받은 자료만 사용하며 서버 조회를 하지 않습니다.
선택한 날짜의 일정 목록은 캐시해 매초 전체 자료 필터를 반복하지 않습니다.

다음·다다음 보스를 목록 밖으로 끌어올리지 않고 휴식·이벤트 사이의 실제 시간 위치에 강조 표시합니다.
다음 보스보다 앞선 휴식은 본문에서 숨깁니다. 다음 보스의 남은 시간으로 기다리는 시간을 확인할 수 있습니다.
예를 들어 04:23 휴식 → 06:03 최하층강글 → 06:17 탕그 → 06:17 휴식이면, 본문은 최하층강글부터 표시하고 이후 휴식은 유지합니다.
복사·이미지 출력에는 선택한 `휴식시간` 옵션에 따라 앞선 휴식도 포함됩니다.
두 휴식을 사이의 보스를 무시하고 합치지 않으며 관리자 프로그램의 원본 일정은 변경하지 않습니다.

화면 복귀·온라인 복구 이벤트가 반복돼도 다음 조회 시각 이전에는 API를 다시 호출하지 않습니다.
입장 화면의 실패 조회도 15→30→60→120초로 늘리고, 숨겨진 동안에는 중지합니다.
429 제한 응답은 로그인 해제나 페이지 재로딩으로 처리하지 않고 마지막 일정과 로그인 쿠키를 유지합니다.

HTTP·HTTPS가 동일한 워커의 `web_request_limits.py` 제한을 공유합니다.
대상은 첫 페이지와 `/api/session`, `/api/status`, `/api/schedule`입니다.
브라우저별 순간 8회/초당 0.5회 회복, IP별 순간 120회/초당 10회 회복,
워커 전체 순간 240회/초당 40회 회복으로 정상 polling 여유를 둡니다.
초과하면 429와 대기 초를 반환합니다. 브라우저 식별값을 바꿔도 IP·전체 제한은 적용됩니다.
버킷은 최대 4,096개이며 미사용 기록을 정리합니다. 제한 진단 로그는 최대 30초에 한 번 남깁니다.

JavaScript·CSS는 `private, no-cache`와 ETag로 매번 최신 버전을 확인하면서 변경 없으면 304로 본문 전송을 생략합니다.
입장·차단·웹 권한 검사는 캐시보다 먼저 수행하고 HTML·일정 API는 계속 `no-store`입니다.
이번 서버 요청 보호는 Python 수정도 포함하므로 웹 파일과 관리자 프로그램을 함께 반영해야 합니다.

## 닉네임 / 일반·게스트 비밀번호

입장 화면에는 기본값 `guest`인 닉네임 입력란이 있습니다. 길드원은 자신의 닉네임으로 바꿔 입력하고,
손님은 그대로 쓰거나 원하는 닉네임을 입력합니다. 닉네임은 최대 40자이며 접속 관리의 접속 ID 앞에 표시됩니다.
닉네임은 식별용 표시이며 계정 인증이 아닙니다. 일반·게스트 구분은 실제 입력한 비밀번호로 결정합니다.
브라우저에는 마지막 닉네임만 저장하며 비밀번호는 저장하지 않습니다.

`웹 → 비밀번호`에서 일반 비밀번호와 게스트 비밀번호를 별도로 설정합니다. 서로 다른 네 자리 숫자를 사용합니다.
게스트 비밀번호를 변경하면 기존 게스트 로그인만 만료되고 일반 로그인은 유지됩니다.
반대로 일반 비밀번호 변경은 일반 로그인만 만료됩니다. 기존에 입장한 웹페이지도 다음 정상 상태 조회 시
비밀번호 입력 화면으로 돌아가며, 만료된 로그인 쿠키는 삭제합니다. 화면 복귀 시에도 인증을 다시 확인합니다.
`게스트 입장 중지`는 게스트 비밀번호를 비활성화하고 기존 게스트 로그인을 해제합니다.
새 게스트 비밀번호를 저장하면 다시 입장을 허용합니다. `모든 브라우저 로그인 해제`는 두 종류 모두 해제합니다.
게스트도 스케줄 조회·복사를 사용할 수 있으며 수정 권한은 없습니다. 차단 목록은 그대로 유지됩니다.

기존 일반 비밀번호·로그인·접속 기록을 보존합니다. 기존 기록에 닉네임이 없으면 `guest`로 표시합니다.
공동 관리용 암호화 웹 설정에도 두 비밀번호의 검증값과 로그인 만료 정보를 함께 전달합니다.

### 현재 비밀번호 표시와 승계 시 로그인 유지

`웹 → 비밀번호`에서 일반·게스트의 현재 네 자리 번호를 각각 확인할 수 있습니다.
입력란은 새 번호를 저장할 때 사용합니다. 현재 번호는 프로그램 재시작 후에도 표시됩니다.
표시용 암호화 값은 GUI 전용이며 웹 상태 API·접속 목록·진단 로그에는 포함하지 않습니다.
복호화와 검증은 별도 웹 관리 스레드에서 값이 바뀔 때만 수행합니다.

이전 버전은 검증값만 저장하여 현재 번호를 표시할 수 없습니다.
이 경우 **기존과 같은 번호를 한 번 저장**하면 기존 로그인은 그대로 유지하며 표시 기능을 활성화합니다.
같은 번호를 다시 저장할 때는 로그인 서명 키·검증값·로그인 세대를 바꾸지 않습니다.
다른 번호로 변경하거나 게스트 입장을 중지하거나 로그인 해제를 누른 경우에만 해당 로그인을 만료합니다.

일반 웹 승계와 분리 운영에서 웹을 다시 가져오는 과정 모두 기존 암호화 설정 전달 경로를 사용합니다.
두 비밀번호, 로그인 서명 키, 일반·게스트 로그인 세대, 차단 정책을 함께 가져옵니다.
표시용 번호는 기존 PC에서 읽고 AES 암호화 전달 자료에 넣어 받은 PC의 Windows 계정으로 다시 암호화합니다.
다른 PC의 DPAPI 암호문을 그대로 저장하지 않습니다. 구버전 검증값만 받아도 기존 로그인은 유지합니다.
표시용 값을 읽지 못하거나 다시 암호화하지 못해도 로그인 키·비밀번호를 새로 만들지 않습니다.
이 경우 현재 번호 표시만 제한하며 `access_pin_display_unavailable` 로그에는 역할만 기록합니다.

길드원이 동일한 공개 주소로 접속하면 PC가 바뀌어도 기존 로그인 쿠키로 입장합니다.
기존에 만료·삭제된 쿠키나 다른 주소에서 받은 쿠키는 승계로 복구하지 않습니다.
이번 변경은 웹 API·관리 UI도 포함하므로 관리자 PC들의 GUI를 함께 교체해야 합니다.
수동 웹 업데이트 원본에는 `web_assets/` 전체와 `metadata.json`의 `login_api: 2`를 함께 올려주세요.
이전 입장 화면이 저장되어 있으면 새 프로그램은 해당 파일을 보존하고 내장 최신 화면을 사용합니다.

## 웹 휴식 일정 표시

전체 스케줄에 진행 중·예정된 휴식 일정을 표시합니다. 이미 끝난 휴식은 표시하지 않습니다.
상단 `복사` 왼쪽의 `휴식 ON/OFF`로 표시를 전환하며, 기본값은 ON입니다. 선택은 브라우저에 저장됩니다.
휴식은 `[시작 시간] 휴식 (1시간 28분)`처럼 시작부터 끝까지의 전체 길이를 표시합니다.
시간이 지나도 괄호의 길이는 줄어들지 않습니다. 진행 중인 휴식은 테두리로 구분하고 취소선을 긋지 않습니다.
이전 날짜에 시작한 진행 중 휴식 때문에 본문에 지난 날짜 제목이 끼어들지 않도록 처리합니다.
다음·다다음 보스는 계속 보스만을 기준으로 계산합니다. 주요 탭의 주요 보스 필터도 유지합니다.
본문의 휴식 표시 선택과 복사 창의 `휴식시간` 체크는 독립적입니다.
텍스트·TXT·이미지 복사에도 휴식의 전체 길이를 표시합니다. 웹 요청을 추가하지 않고 브라우저에서 처리합니다.

휴식 표시와 웹 알람 선택은 처음 방문할 때 ON입니다. 이후에는 각 브라우저에 저장된 마지막 선택을 복원합니다.
이미 OFF로 저장한 선택도 유지하며, 전체 알람과 보스별 선택을 각각 기억합니다.
같은 브라우저의 다른 탭에도 선택 변경을 반영합니다. 웹 알람은 선택만 저장하는 기존 동작을 유지합니다.
휴식 일정은 하늘색 배경과 읽기 쉬운 진한 글자로 표시합니다. 복사 색상을 사용하면 이미지에도 반영됩니다.

`휴식시간 설정`의 시간 구간별 `행수`를 웹 본문과 복사 미리보기의 휴식 칸 높이에도 반영합니다.
예를 들어 행수 1/1.5/2/3은 기본 높이의 1/1.5/2/3배입니다. 내용은 세로 중앙에 표시합니다.
행수를 바꾸면 기존 스케줄 갱신 경로로 전달합니다. 남은 시간이 줄어도 칸 높이는 바뀌지 않습니다.
이 변경에는 관리자 스냅샷도 포함되므로 GUI와 웹 파일을 함께 적용해야 합니다.
# 예외 운영: Discord 담당과 웹 담당 분리

Discord의 `/웹서버 관리자이름`으로 현재 송출 담당자 또는 지정된 웹 담당 PC에서 웹 공개를 한 번 시도할 수 있습니다.
예: `/웹서버 나츠` (관리자이름 입력란). 목록의 관리자 ID도 허용하며 동명이인은 ID로 구분합니다.
Discord 관리자/서버 관리 권한이 필요합니다. 기존 Discord 응답 선점과 로컬 요청 경로를 사용합니다.
대상 PC가 응답하기 전에는 웹·음성 권한을 변경하지 않습니다. 웹 설정이 없으면 DuckDNS 설정을 안내합니다.
성공·실패 결과를 요청자에게만 표시하며, 실패 후 추가 자동 공개 재시도는 하지 않습니다.
이미 정상 공개 중이면 현재 주소를 알려줍니다. 음성 권한은 승계하지 않으며 일반 대기 PC의 웹을 임의로 공개하지 않습니다.
응답은 기존 내부 연결 이벤트로 전달합니다. 이벤트 누락 시 기한 끝에서만 기록을 한 번 확인하며 GitHub 주기 조회는 추가하지 않습니다.

웹을 공개할 수 없는 PC가 Discord 송출을 맡아야 할 때 사용하는 기능입니다.
새 담당자의 웹이 OFF이거나 무료 주소·외부 공개 설정 전이면 같은 시즌·게임 서버의 기존 웹 담당자를 자동으로 유지합니다.
연결 준비 중이거나 일시 오류·재시도 중이라는 이유로 자동 선택하지 않습니다. 웹 설정이 완료된 PC의 일반 승계는 기존 동작을 유지합니다.
기존 담당자도 웹이 OFF라고 알려온 경우에는 분리 운영과 스케줄 전달을 새로 만들지 않습니다.
분리 운영을 지원하는 이전 GUI가 웹 사용 상태를 알려오지 않는 경우에는 기존 웹이 켜져 있을 가능성을 보존합니다.
웹 설정 사용 여부는 바뀔 때만 기존 담당자 등록 경로로 공유하며, 별도의 GitHub 주기 조회는 추가하지 않습니다.

1. 관리자 1은 기존 웹을 공개하고, 프로그램과 봇을 계속 켜 둡니다. 사람이 자리에 있을 필요는 없습니다.
2. 관리자 2가 웹 OFF/설정 전이면 자동으로 분리합니다. 설정이 완료돼 있어도 기존 웹을 유지하려면 **웹 → 공동 운영 → 다음 승계는 Discord만 · 기존 관리자 PC의 웹 유지**를 체크합니다.
3. 관리자 2에서 디코 실행으로 승계합니다. 해당 선택은 성공적으로 요청이 저장되면 해제됩니다.
4. 관리자 1은 음성 송출을 중단하고 기존 승계 스케줄 업로드를 진행하며, 웹·무료 주소 갱신은 유지합니다.
5. 관리자 2의 현재 로컬 스케줄을 조회용 웹 자료로 전달합니다. 관리자 프로그램의 스케줄 동기화는 수동입니다.
   기존 승계 스케줄 업로드가 실패·대기 중이어도 웹 자료 전달은 막지 않습니다.
6. 최초 자료와 이후 마지막 변경 후 90초(1분 30초) 동안 추가 변경이 없으면 조회용 스케줄을 업로드합니다.
   Discord 내부 연결 스레드로 전달 요청을 보내고, 관리자 1이 요청받은 파일만 다운로드하여 웹에 반영합니다.
   관리자 1의 로컬 스케줄·설정은 덮어쓰지 않습니다. 동일 자료는 반복 업로드하지 않습니다.

관리자 1에는 확인·재시도 메시지박스를 띄우지 않습니다. 초기 연결 변경 확인 실패도 자동 재시도합니다.
음성 종료 확인, 승계 업로드, 웹 다운로드·반영 응답, 웹서버·외부 공개의 일시 오류는 제한된 자동 재시도로 처리합니다.
웹 전달은 최대 3회 시도하고 응답 대기·실패 상태를 공동 운영 화면과 진단 로그에 표시합니다.
문제가 해결된 뒤 관리자 2의 **지금 웹 갱신**으로 재시도할 수 있습니다.
웹 준비 응답이 늦거나 실패해도 웹 담당자를 자동 변경하지 않습니다.

**웹도 이 PC로 승계**는 관리자 2에서 요청합니다. 관리자 1이 외부 접근을 차단하고 진행 중인
무료 주소 갱신을 마친 뒤 중단 확인을 자동 전송합니다. 확인 전에는 관리자 2의 외부 공개를 허용하지 않습니다.
기존 PC의 최신 비밀번호·인증서·공개 포트 설정도 암호화해서 자동 전달합니다.
기존 웹 PC가 응답하지 않으면 기존 분리 운영을 유지하며, 확인 없이 강제로 주소를 빼앗지 않습니다.

제약: 같은 Discord 서버·게임 서버·시즌에서 사용하며, 두 PC 모두 GUI와 봇을 새 버전으로 교체해야 합니다.
GitHub 저장소와 안내채팅 채널을 함께 사용합니다. 웹 담당자의 PC·프로그램·봇이 실행 중이어야 합니다.
실행 세션과 승계 요청에 묶인 역할이므로 프로그램을 재시작한 뒤에는 담당 상태를 확인하고 승계를 다시 설정합니다.
이후 다른 PC로 Discord를 승계해도 기존 분리 운영은 유지되며, 기존 웹 PC가 Discord를 다시 맡으면 일반 운영으로 합쳐집니다.

진단 이벤트: `web_delegation_role_changed`, `web_delegated_schedule_uploaded`,
`web_delegated_schedule_applied`, `web_delegated_operation_failed`, `web_handover_local_schedule_prepared`,
`web_delegated_worker_retry`, `web_delegated_public_retry`, `web_delegated_host_stopped`,
`web_delegated_return_completed`, `web_host_voice_stop_retry`, `handover_upload_retry_result`.
GitHub 스케줄 반복 조회를 추가하지 않으며, 웹 담당자의 공개 권한 유지도 로컬 GUI·봇 상태만 확인합니다.

## 수동 웹 종료 / 단독 강제 실행

웹 → 공동 운영의 **이 PC 웹 종료**는 외부 접근, 주소 갱신, 웹 프로세스를 종료합니다.
봇 연결과 디코 송출권한은 유지합니다. **웹 단독 강제 실행**은 현재 PC의 스케줄을 그대로
공개하며, 인계 업로드·스케줄 다운로드를 기다리지 않습니다. 봇 연결과 DuckDNS 설정은 필요합니다.
다른 PC가 웹 담당이면 동일한 원격 웹 종료 경로로 종료를 요청하고, 공개 차단·프로세스 종료·
진행 중인 주소 갱신 종료를 확인한 뒤 이 PC의 웹만 시작합니다. 종료 확인이 없으면 새 공개를 시작하지 않습니다.
단독 실행 중에는 디코 송출권한과 별도로 웹을 운영합니다. 웹 설정을 켠 PC에서 새 디코
접속·승계를 요청하면 일반 웹 자동 승계로 돌아갑니다. 이때 기존 단독 웹도 새 PC의 준비·
공개 중지 확인 전까지 유지합니다. 내부 음성 재접속은 단독 모드를 변경하지 않습니다.
새 승계에서 '기존 웹 유지'를 다시 선택하거나, 받는 PC의 웹이 꺼져 있으면 기존 웹을 유지합니다.
웹서비스 사용 또는 외부 공개를 다시 켜면 이전 긴급 중지 상태도 해제됩니다.
웹을 다른 PC에 인계할 때는 기존 PC의 웹서비스·외부 공개 체크를 보존하고 대기합니다.
외부 접근 차단, 진행 중인 주소 갱신 종료, 기존 공유기 규칙 정리가 확인된 뒤 새 PC가 공개합니다.
직접 누르는 '이 PC 웹 종료'와 `/웹서버 로그아웃 이름`은 기존처럼 웹 사용 설정을 끕니다.
강제 실행 내부에서 보내는 인계용 종료 요청은 실행 세션과 진행 중인 웹 작업을 검증한 뒤
설정을 보존합니다. 이미 준비된 로컬 웹 프로세스도 재사용하며, 불필요한 재시작을 줄입니다.
프로그램 재시작 후 남은 단독 웹 기록은 해당 세션의 종료 기록 또는 인증된 기존 접속 확인에서
새 실행 세션으로 교체되었음이 확인될 때만 정리합니다. 응답이 없는 것만으로 운영 중인 웹을 끊지 않습니다.
자동 웹 승계는 웹 작업 스레드에서도 시작하므로 스케줄 화면 갱신에 의존하지 않습니다.
`web_auto_return_check` 로그는 대기 조건이 달라질 때만 기록하고, `web_auto_return_queued`는
실제 승계 요청이 등록되었음을 표시합니다. 별도 GitHub 반복 조회는 추가하지 않습니다.
새 PC의 준비 실패 사유는 공동 운영 화면에 표시하고 기존 내부 Discord 이벤트로 이전 PC에
한 번 전달합니다. 이전 PC의 `web_peer_preflight_failed` 로그에서도 실패 단계와 사유를 확인할 수 있습니다.
인계 스케줄 업로드의 상세 결과는 `web_handover_upload_result`와 현재 요청의 `web_transfer`에 기록합니다.
이 업로드 결과는 웹 승계를 제한하지 않습니다. 요청별 암호화된 웹 설정이 뒤늦게 도착하면
`web_handover_settings_available` 이벤트로 설정 준비를 한 번 다시 수행하며, 스케줄 성공 이벤트로 재시도하지 않습니다.
더 최신인 서버 스케줄을 구버전 PC의 다른 내용으로 덮어쓰지는 않습니다. 디코 기록에서 이 PC의 웹 담당 유지가 먼저 확인되면,
기존 송출권한의 웹 작업만 종료하고 공개 권한은 유지합니다.

스케줄 창을 닫아 숨긴 뒤 도착한 확인창은 숨은 창을 부모로 사용하지 않고 현재 보이는
메인 창에 표시합니다. 웹 설정 가져오기는 UI와 같은 잠금 순서(웹 역할 → 승계 → 웹 매니저)를
사용합니다. UI 응답이 15초 이상 멈추면 AppData/BossTimer/ui_responsiveness.log에 작업 위치를
한 번 기록하며, 복구 후 새 정지가 있을 때 다시 기록합니다. 지역 변수나 인증정보는 저장하지 않습니다.
승계 확인창은 진행창 위에 표시하고 중앙 위치는 원래 부모 창을 기준으로 유지합니다.
받는 PC의 웹서비스 또는 외부 공개를 껐을 때는 이전 시도의 실패 표시 대신 '웹 별도 PC'로 표시합니다.
웹 인계 완료 또는 재시도가 이전 준비 작업을 취소한 경우에는 내부 취소로만 처리합니다.
취소된 작업은 새 작업의 공개 권한을 끄거나 기존 웹 복구 절차를 실행하지 않습니다.
`web_handover_obsolete_operation_cancelled` 로그에 이전·현재 웹 작업 번호를 기록합니다.
현재 작업의 실제 설정·공개 오류에는 기존 차단·복구 절차를 유지합니다.
자동 웹 승계가 요청되기 전에는 '웹 승계 대기', 인계 후 새 PC의 공개 확인 중에는 '웹 준비 중'으로 표시합니다.
'웹 별도 PC'는 기존 웹 유지를 선택했거나 새 PC의 웹 공개 설정이 꺼진 경우에 표시합니다.

재연결은 이 PC의 `web_service/public_connection_cache.json`에 저장한 성공한 공유기 연결 정보를 먼저 사용합니다.
현재 로컬 경로의 IP와 공유기의 외부 IP가 그대로인지 확인하며, 다른 PC의 캐시는 사용하지 않습니다.
캐시 연결에서는 랜카드 전체 조회·UPnP 재탐색·공인 IP 서비스 조회를 반복하지 않습니다.
실패하거나 네트워크 정보가 바뀌면 실패한 공개 규칙을 정리한 뒤 전체 진단으로 한 번 전환합니다.
공개 권한, 인증서, 포트 소유 확인과 방화벽 설정은 생략하지 않습니다. 방화벽 권한 오류나 작업 취소는 재탐색하지 않습니다.
HTTPS를 준비하는 동안은 로컬 상태만 0.5초 간격으로 확인하며, 네트워크 진단은 반복하지 않습니다.
진단 로그의 `public_fast_connect_begin`, `public_fast_connect_failed`, `public_connection_cache_invalid`로 경로를 확인할 수 있습니다.
`web_first_publication_parallel`은 음성 입장 완료 전에 첫 외부 공개를 시작한 기록입니다.
암호화된 공동 인증서·비밀번호는 재사용하고, 이후 설정 변경도 공동 저장소에 반영합니다.

Discord 관리자/서버 관리 권한이 있는 사용자는 `/웹서버`의 관리자이름 입력칸에
`로그아웃 나츠`를 입력해 나츠 PC의 웹을 종료하거나, `단독 나츠`로 단독 실행을 요청할 수 있습니다.
기존처럼 `나츠`만 입력하면 일반 웹 공개 재시도입니다. 종료 명령도 중복 응답 방지를 적용합니다.
모든 관리자 PC의 GUI와 봇을 새 버전으로 교체해야 합니다. 이전 GUI에는 종료 명령을 보내지 않습니다.

진단 이벤트: `web_standalone_stage`, `web_standalone_start_failed`, `web_standalone_lease_failed`,
`discord_web_stop_verified`, `discord_web_standalone_requested`, `web_standalone_shared_state_published`.

웹 페이지 개정 번호는 `web_assets/metadata.json`의 `page_revision`입니다. 재빌드한 내장 페이지보다
개정 번호가 낮은 AppData 저장본은 그대로 보관하고 새 내장 페이지를 사용합니다. 수동·자동 웹 업데이트도
더 낮은 개정 번호를 적용하지 않습니다. 이번 화면의 개정 번호는 103이며, 이후 호환되는 외부 웹 수정은
같은 번호 이상을 사용합니다. 새 EXE에서 이전 웹 화면을 대체해야 할 때는 이 번호를 올립니다.
`web_pages_bundled_preferred`, `web_page_update_older_revision_ignored` 로그에서 선택 이유를 확인합니다.

서비스 → 웹 화면 업데이트의 **로컬 웹 적용**은 수정한 `web_assets`의 여섯 파일을 검증·복사하고
기존 업데이트 경로로 웹 프로세스만 다시 시작합니다. Discord와 관리자 프로그램은 계속 실행됩니다.
소스 실행에서는 프로젝트의 `web_assets`, EXE 실행에서는 기억한 폴더 또는 EXE 옆 `web_assets`를
찾습니다. 없으면 한 번 폴더를 선택합니다. HTML·CSS·JS 수정은 컴파일이 필요 없으며 적용 후
브라우저를 새로고침합니다. Python 서버·관리자 UI 변경은 새 GUI EXE 빌드와 프로그램 재시작이 필요합니다.
기존 수동 웹 업데이트는 계속 공식 저장소를 사용합니다. 로컬 적용은 저장소에 파일을 올리지 않습니다.
진단 이벤트는 `web_page_local_update_begin`, `web_page_local_update_applied`입니다.

사용자 탭의 **설정 ⚙**은 같은 탭 안에서 전체 보스 설정·고정보스 카탈로그를 보여줍니다.
약칭 변경과 일정 갱신에도 원래 보스명을 기반으로 한 ID로 선택을 유지합니다. 선택은 브라우저의
`BossTimer.webCustom.v1:<서버>:<길드>`에 저장하며 데스크톱 스케줄을 수정하지 않습니다.
설정 화면에는 검색창 없이 전체 보스 목록을 표시하며 보스 선택 변경은 저장 버튼을 눌렀을 때만 저장합니다.
원래 선택으로 되돌리면 저장이 비활성화됩니다. 대기·탭 전환·백그라운드·페이지 이탈·접속 서버 변경은
임시 선택을 자동 저장하지 않습니다. 저장 전 직접 새로고침하거나 다른 서버로 이동하면 저장하지 않은 선택은 유지되지 않습니다.
삭제된 보스의 기존 저장 선택은 보관하여 같은 보스가 다시 등록되면 적용합니다.
보스 목록은 기존 15초 상태 조회에서 개정이 바뀐 경우에만 전달하므로 새 조회 주기를 추가하지 않습니다.

전체·주요 보스·사용자 탭은 마우스 또는 터치로 끌어 순서를 바꿀 수 있습니다.
왼쪽 탭을 오른쪽으로 옮기면 두 탭을 교환하고, 오른쪽 탭을 왼쪽으로 옮기면 해당 위치에
끼워 넣고 나머지를 한 칸씩 밉니다. 드래그 중에는 목적지를 테두리로 표시하며 손을 뗄 때 적용합니다.
선택된 탭과 표시 중인 내용은 유지합니다. Alt+좌우 방향키로도 같은 규칙을 사용할 수 있습니다.
순서는 각 브라우저의 `BossTimer.webTabs.order.v1`에 저장하며 서버 요청을 추가하지 않습니다.
폰에서는 처음 누른 탭이 터치 입력을 끝까지 유지하며 탭 영역의 스크롤·길게 누르기 메뉴를 막습니다.
손가락이 위아래로 약간 흔들려도 드래그를 유지하며 본문 스크롤은 기존처럼 사용할 수 있습니다.

웹 알림은 보스별 **알림 ON/OFF**로 통합합니다. 별도의 알림 켜기/끄기 버튼은 숨기며,
전체 알림 OFF는 모든 보스의 실제 안내를 중지합니다. 주요·사용자 탭의 일괄 버튼은 해당

개정 88: 안쪽 경계의 꽃 장식은 4개 중 1개만 남기고, 외곽 경계 장식 수는 유지합니다. 머무는 꽃잎도 직전 개수의 25%로 줄입니다(진입 8개 중 1개만 머묾).
외곽 사진 장식의 꽃 중심·줄기를 고정하고 밝은 꽃잎 픽셀의 끝부분만 휘게 하는 작은 변형 프레임을 최초 한 번 캐시합니다.
캔버스 꽃은 연속적인 저주파 불규칙 바람에 반응하고, 버튼·탭 꽃도 같은 꽃잎 변형을 서로 다른 속도·시차로 재생합니다. 꽃 전체가 걷거나 회전하던 효과는 제거합니다.
보스별 알람 ON 앞 꽃은 14×15px에서 16.8×18px로 20% 확대합니다. OFF는 기존 크기를 유지합니다.
꽃잎 항상 ON, 휴식 장식 제외, 테마/화면 숨김 시 정지는 유지하며 추가 네트워크 요청은 없습니다.
개정 89: 스크롤 중 안쪽 고정 꽃 장식을 숨기고 마지막 스크롤 후 180ms가 지나면 복원합니다. 외곽 꽃과 날리거나 잠시 머무는 꽃잎은 유지합니다. 기존 프레임 루프를 사용하며 별도 타이머·네트워크 요청은 추가하지 않습니다. 알림음 선택의 소리 ON/OFF 체크박스는 현재 테마의 강조색을 사용합니다.

개정 96: 벚꽃의 카드 안쪽·옆쪽 고정 꽃은 화면 캔버스에서 카드 내부의 절대 위치 요소로 옮겼습니다.

낙하는 경계로 끌어당기는 경로 대신 바람·회전·얇은 면의 뒤집힘을 반영하며 실제 통과한 경계에서만 8개 중 1개가 잠시 걸립니다.

휴식 박스 주변에는 꽃무늬 날개를 가진 나비 한 마리만 표시합니다. 기존 휴식 꽃 띠는 복원하지 않습니다.

터치·클릭·키보드 동작 시 SVG 이미지 말풍선 !!를 띄워 550ms에 화면 밖으로 도망가며 약 10초 후 돌아옵니다.

나비 컨트롤러 web_assets/limited_sakura/butterfly.js는 기존 1MiB 웹 파일 한도를 유지하기 위해 별도 소형 자산으로 분리했습니다.
기존 꽃 애니메이션 프레임 루프를 공유하며 추가 폴링·타이머·스크롤 재생성은 없습니다.

개정 101: 터치 후 나비가 도망가는 시간을 550ms에서 2,750ms로 늘려 같은 거리의 속도를 1/5로 낮췄습니다.

느린 접근이 마감 시간을 넘기면 도착 시간을 남은 구간에 맞춥니다. 스크롤·테마 전환 시

### 프로그램 종료와 웹 종료 분리 (개정 103)

GUI의 창 닫기와 atexit은 웹 연결만 분리합니다. 별도 웹 프로세스가 HTTP/HTTPS, 접속 세션,
푸시 발송, 공유기 포트 유지와 DuckDNS 자동 갱신을 계속 맡습니다. PC 종료·절전·인터넷 단절은
서비스를 중단할 수 있으며 PC 부팅 시 자동 실행을 등록하지는 않습니다. 명시적인 웹 종료,
웹서비스 사용 해제, 검증된 웹 승계는 기존 종료 절차로 웹 프로세스와 공개 규칙을 정리합니다.

재실행하면 AppData의 비공개 실행 기록과 최근 heartbeat를 확인하고 새 controller nonce 응답을
검증하여 같은 PID·run_id·포트에 다시 연결합니다. 호환되는 웹 런타임은 프로그램/웹 코드 버전이
달라도 중단하지 않고 ‘웹 코드 업데이트 대기’로 표시합니다. 명시적인 웹 업데이트나 재시작 때
새 코드를 적용합니다. 미확인 PID를 강제 종료하거나 프로세스 이름으로 일괄 종료하지 않습니다.
동일 사용자 설정 경로에는 Windows mutex로 한 웹 프로세스만 실행합니다. PyInstaller 자식은
자체 압축 해제 환경을 사용하여 GUI의 임시 파일 삭제에 영향을 받지 않게 합니다.

GUI가 없을 때는 마지막 검증된 스케줄을 사용하며 captured_at/updated_at을 꾸며 갱신하지 않습니다.
스케줄 제공 기간이 끝나거나 자료 검증이 실패하면 푸시를 중단합니다. 새 일정 입력·수정은 GUI를
연결한 뒤 반영됩니다. 웹 상태에는 ‘백그라운드 운영 · 저장된 일정으로 안내 중’을 표시합니다.

공동 웹 소유권은 암호화된 사용자 범위 DPAPI 자격으로 별도 확인합니다. GUI가 없는 동안
5초 간격으로 소유권/종료 요청을 확인하고 30초마다 90초 유효한 백그라운드 표시를 갱신합니다.
확인 실패는 최대 30초 간격으로 늦추고, 15초 동안 소유권을 확인하지 못하면 공개/푸시를 차단합니다.
봇의 접속 종료만으로 웹 종료를 단정하지 않으며, 승계 시 백그라운드 웹에 종료 요청을 남기고
포트 규칙·주소 갱신의 정리 응답을 확인합니다. GitHub Token 원문은 상태 파일/진단에 기록하지 않습니다.
최초 적용은 GUI 전체 재빌드가 필요하며 Discord 봇 단독 변경은 없습니다.


VS Code 디버그 실행에서는 웹 프로세스 생성 구간에만 pydevd의 스레드별
`skip_subprocess_arg_patch()`를 적용합니다. Windows에서는 디버거가 허용한
`CREATE_BREAKAWAY_FROM_JOB`으로 launcher의 kill-on-close Job Object에서 분리합니다.
`CREATE_NEW_PROCESS_GROUP`만 지정하면 디버그 종료 때 웹도 지연 종료될 수 있습니다.
GUI·Discord 봇의 디버그 설정은 변경하지 않으며 일반 실행에 디버거를 새로 import하지 않습니다.
`worker_spawned.debugger_detached`에 적용 여부를 기록합니다. 적용 전 실행한 웹에는 소급 적용되지
않으므로 GUI를 새로 실행하여 새 웹 프로세스를 시작해야 합니다. 별도 테스트 빌드는 생성하지 않습니다.

재연결 시 공개 유지 의도와 워커의 순간적인 표시 상태를 구분합니다. 이전 공개가 준비된 상태이거나
일치하는 비공개 실행 기록의 `keep_background`·`public_enabled`가 유지된 경우, 기존 PID에 제어만
다시 연결합니다. 일시적인 `off` 표시를 공개 중지 명령으로 되돌려 보내지 않습니다. 공개 여부는
실제 워커 상태를 표시하며 새 공개 작업이나 Discord 승계를 시작하지 않습니다. 명시적인 웹 종료와
외부 공개 해제는 우선합니다. 이전 코드가 일시적인 OFF를 명령에 반영했더라도 남아 있는 유지 의도와
워커의 소유권 검증으로 복구할 수 있습니다. 소유권 미확인·소유자 변경 시에는 계속 공개를 차단합니다.

백그라운드 소유권 조회가 성공하면 15초 증명을 갱신하고, 후속 표시 기록 저장 충돌은 별도로 재시도합니다.
표시 저장 실패만으로 조회 결과를 버리지 않으며 실제 소유권 조회 실패는 기존 만료 정책을 유지합니다.
인증서·DDNS 설정 변경은 파일 내용으로 비교하므로 동일 내용의 재저장이 유지 작업을 반복 시작하지 않습니다.
재연결 수정은 새 GUI에 적용되고, 워커 내부 보강은 명시적인 웹 재시작 이후 새 워커에서 적용됩니다.

### 재접속 시 로그인 유지 (개정 104)

외부 주소의 쿠키 없는 첫 `/` 요청은 방문자 쿠키를 새로 발급하지 않습니다. `SameSite=Strict` 때문에
외부 링크 진입에서 잠시 전달되지 않은 기존 쿠키를 덮어쓸 수 있기 때문입니다. 로그인 화면의 같은
사이트 `/api/session` 요청에서 기존 쿠키를 먼저 확인하고, 새 브라우저라면 이때 방문자를 등록합니다.
로컬 HTTPS 검사 요청은 계속 방문자를 만들지 않으며 localhost 브라우저의 입장은 유지합니다.
익명 첫 화면에도 기존 새로고침 제한을 적용합니다. 쿠키의 HttpOnly·Secure·SameSite와 비밀번호
변경에 따른 만료 규칙은 유지하며 비밀번호를 브라우저에 저장하지 않습니다.

스케줄 조회의 401·403만으로 로그인 화면으로 전환하지 않습니다. 같은 5초 요청 제한 안에서
세션 확인을 추가하고, 실제 로그인 만료 또는 관리자 차단이 확인된 경우에만 전환합니다. 공유기나
중간 장치의 오류 응답·정상 세션·일시적인 설정 읽기 실패·503·연결 장애는 마지막 스케줄과 로그인을
유지하고 기존 대기 간격으로 재시도합니다. 정상 조회에는 세션 확인 요청을 추가하지 않습니다.
실행 중인 워커에는 자동 반영하지 않으며 명시적인 웹 재시작으로 서버 변경을 적용합니다.

Discord 동시 실행 요청에서 같은 PC의 웹이 이미 공개 중이면 공유 소유자만 확인하고 종료합니다.
이 확인 중 `busy` 플래그만으로 '웹 승계 중'으로 바꾸지 않으며 실제 공개 상태와 권한 준비가 유지되면
'웹 공개 중'을 유지합니다. 실제 준비·승계·종료 단계는 해당 진행 문구를 계속 표시합니다.
재사용 완료는 `web_existing_public_reused`로 기록하고 기존 PID·run_id·공개 규칙을 변경하지 않습니다.

### 나비 화면 경계와 비행 (개정 105)

나비와 느낌표는 화면 크기의 고정 전용 레이어 안에 둡니다. 레이어의 overflow와 paint containment로
화면 밖 이동이 문서의 가로 폭·스크롤 범위에 포함되지 않게 하고, 경계 밖 그림은 잘라냅니다.
내부 좌표는 기존 문서 좌표를 유지하며 렌더링할 때 스크롤 좌표를 빼므로 같은 나비·진행 중인 비행을
스크롤 때문에 다시 만들지 않습니다. 다른 꽃 장식과 스케줄 레이아웃의 overflow는 변경하지 않습니다.

큰 원과 뒤로 도는 경로는 작은 불규칙 상승·하강 지점의 부드러운 곡선으로 대체합니다. 지점과 가벼운
상하 움직임은 비행 시작 때 한 번 정하여 프레임마다 떨리지 않고 매번 다른 리듬으로 이동합니다.
가까운 목적지에서는 움직임 폭을 줄이고 좌우 기울기도 제한합니다. 퇴장은 가까운 측면 경계를 향하며
화면 너비에 맞춰 사라집니다. 기존 비행 시간·15초 전 접근·5초 전 출발·터치·테마 전환 조건은 유지합니다.
나비 파일 검증 해시와 CSS·내장 대체 파일을 함께 갱신합니다.

### 사용자 설정·벚꽃 수량·푸시 중복 등록 (개정 106)

사용자 설정의 일괄 선택 버튼은 '주요보스체크', 해제 버튼은 '전체 해제'로 표시합니다.
벚꽃 이미지 종류와 아틀라스는 유지하고 동시에 떠다니는 꽃잎은 폰 최대 5개·PC 최대 9개로 줄입니다.
생성 간격도 1.9~3.2초로 늘립니다. 박스 내부의 고정 꽃은 제거하며 왼쪽 경계 꽃만 기존 크기의 두 배로
표시합니다. 오른쪽 경계·탭·ON 아이콘·떨어졌다 걸리는 꽃잎과 나비 동작은 유지합니다.

푸시 등록에는 브라우저별 임의 식별자를 localStorage에 보관해 전달합니다. 닉네임이나 IP로 기기를
합치지 않습니다. 동일 브라우저 식별자 또는 동일 푸시 주소로 재등록하면 이전 접속 ID의 등록을 대체해,
과거 ON 설정이 새 OFF 설정과 함께 남지 않게 합니다. 다른 브라우저·기기의 설정은 독립적으로 유지합니다.
단순히 접속 ID가 바뀌었다는 이유로 정상 푸시 구독을 강제 재발급하지 않습니다. 이전 ID로 이미 대기 중인
푸시도 발송 직전에 새 등록을 확인하여 취소됩니다. 기기 식별자가 없는 과거 등록은 푸시 주소도 다르면
같은 기기라고 추측해 일괄 삭제하지 않습니다.

### 꽃 밀도·시간 대비·스펙트럼 위치 (개정 107)

다음 보스에는 왼쪽 경계·세로 64% 위치에 기존 큰 크기의 꽃 한 개를 유지합니다. 다른 고정 경계 꽃은
같은 보스 식별자에서 항상 같은 표본을 선택하여 왼쪽 약 30%·오른쪽 약 20%만 남깁니다. 양쪽 크기는
직전 왼쪽 크기의 70%(폰 약 32.2px·PC 약 40.6px)로 맞춥니다. 스크롤 때문에 표본이나 위치를 바꾸지
않으며, 전체 탭 장식은 80% 크기로 줄여 왼쪽으로 이동합니다. 꽃 이미지 종류와 떨어지는 꽃잎 수는 유지합니다.

다크 테마의 젠 시간·남은 시간은 실제 보스 배경의 명도에 따라 검정 또는 흰색을 선택합니다. 밝은 7챕
배경에서도 시간을 읽을 수 있으며 보스 이름 색과 밝은 테마의 기존 스펙트럼 규칙은 유지합니다.

스펙트럼 선택기와 팔레트는 고정 저장창에서 보스 목록 위의 별도 영역으로 이동합니다. 팔레트를 펼치면
문서 흐름에서 목록을 아래로 밀며 보스 버튼 위를 덮지 않습니다. 보스의 색상 번호 배지는 왼쪽 위로 옮겨
이름·오른쪽 별표와 분리합니다. 하단 고정 저장창에는 되돌리기 왼쪽에 주요보스선택·전체해제 버튼을 두며
상단 버튼과 같은 선택·실제 변경 감지·저장 버튼 확정 동작을 사용합니다. 일반 사용자는 개발자 색상 도구를 볼 수 없습니다.

### 사용자 탭 연속 휴식 표시 (개정 108)

개정 168에서는 사용자·주요 보스 탭의 현재 표시 날짜 안에 앞으로 안내할 보스가 없으면 휴식도 표시하지 않습니다.
전날과 다음날에만 선택 보스가 있어 오늘에는 휴식만 걸치는 경우, 오늘 마지막 보스가 끝난 뒤 다음날 보스까지의 휴식이 남는 경우를 포함합니다.
젠 후 3초 유지 중인 보스는 여전히 표시 대상으로 보고, 유지 시간이 끝나면 별도 갱신 없이 휴식도 숨깁니다.
정상 구간의 재계산 휴식과 지난 보스 기록은 유지합니다. 다른 날짜로 이동해 실제 다음 보스가 표시되면 원래 휴식 구간을 사용할 수 있습니다.
`visibleRows`에서 표시 범위의 남은 보스 유무를 확인하며 원본 일정과 휴식 데이터, 전체 탭과 복사 옵션은 변경하지 않습니다.
검증은 `test_web_schedule_views.js`와 `check_web_avengers_browser.ps1 -EmptyCustomRest`를 사용합니다.

사용자 탭에서 선택하지 않은 보스가 숨겨진 뒤 연달아 남는 휴식 박스를 하나로 표시합니다.
시간은 원본 휴식 구간의 합계이며 겹친 시간은 한 번만 계산합니다. 숨겨진 보스의 진행 시간은
더하지 않습니다. 각 원본 구간은 툴팁으로 확인하며, 실제 휴식 구간 안에서만 휴식 중 상태로 표시합니다.
선택한 보스가 사이에 있으면 박스를 분리합니다. 원본 스케줄과 전체·주요보스 탭, 복사 데이터는 보존합니다.

### 선택 탭 꽃·다음 보스 가지꽃·날짜 경계 (개정 109)

벚꽃 테마의 선택 탭 장식은 전체·주요보스·사용자 모두 같은 34.4px 크기와 왼쪽 위치를 사용합니다.
다음 보스의 왼쪽 꽃을 유지하고 오른쪽 아래에 다른 종류의 가지꽃을 추가합니다. 두 꽃 모두
스크롤 시 기존 DOM과 위치를 유지합니다. 일반 박스의 왼쪽 꽃 표시 비율은 30%에서 50%로
변경하며 축소된 크기는 유지합니다. 오른쪽 일반 꽃의 20% 비율은 유지합니다.
전체 탭에서 정오 이후 다음 날 08시까지 표시하는 날짜 경계는 보스 이름과 같은 18px 기준 크기,
굵은 글씨, 대비 외곽선, 테마 색 테두리와 배경을 적용하여 꽃 장식보다 위에 표시합니다.

### 컬러 테마 박스 경계·날짜 이중 구분선 (개정 110)

스펙트럼 배경이 지정된 보스 박스도 각 컬러 테마의 테두리·그림자를 사용합니다. 기존 핑크 공통
스타일의 다음 보스 테두리와 안쪽 핑크 그림자가 남던 경로를 배경 지정 여부와 분리하여 수정했습니다.
날짜 경계의 바깥 박스·채움·그림자를 없애고, 날짜 아래에 5px 간격의 테마색 평행선 두 줄을 표시합니다.
보스 이름 크기의 굵은 날짜 글씨와 대비 외곽선은 유지합니다.

### 컬러 테마 남은 시간 강조색 (개정 111)

1시간 이내 남은 시간에 공통 핑크 경고색을 덮던 스펙트럼 강조 규칙에서 컬러 테마를 제외합니다.
컬러 테마의 다음·다다음·일반 보스는 스펙트럼 배경의 검정/흰색 대비 글씨를 유지하고,
스펙트럼을 지정하지 않은 박스는 해당 테마 글자색을 유지합니다. 알림 시각과 점멸 조건은 유지합니다.

### 벚꽃 표시 비율·다음 보스 꽃 잘림 (개정 112)

일반 박스 왼쪽 꽃을 40%로 조정합니다. 꽃 크기, 오른쪽 20% 비율, 다음 보스 양쪽 꽃은 유지합니다.
벚꽃 테마의 다음 보스와 초기 개요 영역에 남아 있던 overflow:hidden을 풀어 박스 경계를 넘는 꽃을
표시합니다. 기존 핑크 장식 의사요소는 숨기고, 뷰포트의 가로 overflow만 clip하여 꽃이 페이지 폭을
늘리지 않도록 합니다. 수직 스크롤과 꽃의 DOM·바람 애니메이션은 유지합니다.

### 푸시 ON 저장 응답 누락 뒤 OFF 재전송 (개정 113)

푸시 설정을 POST하기 직전에 마지막 성공 서명을 무효화합니다. 서버가 ON을 저장한 뒤 응답만
끊겨도 이전 OFF 서명과 같다는 이유로 후속 OFF 저장을 생략하지 않습니다. 초기 등록에서도
브라우저 구독 준비 후에는 전송 준비 상태를 유지하여, 등록 중 OFF로 바뀌거나 응답이 누락되면
최신 선택을 다시 보냅니다. 설정 재시도 횟수와 백오프는 유지합니다.
진단 push_subscription_changed에 전체 기본값과 개별 ON/OFF 개수를 추가하여 전송 등록 유지와
보스 알림 선택 상태를 구분합니다. 닉네임·다른 기기의 등록은 임의로 합치지 않습니다.

### 날짜 양옆 이중 구분선 (개정 114)

날짜 경계를 `왼쪽 선 / 날짜 / 오른쪽 선`의 세 열로 표시합니다. 날짜 앞에는 보스의 시간 표기
영역에 대응하는 9ch 공간과 행 안쪽 여백을 두며 그 공간에도 선을 표시합니다. 양옆 모두 위 3px
굵은 선과 아래 1px 선을 사용하고 선 사이 빈 간격은 2px로 줄입니다. 날짜 글씨의 굵기·외곽선은
유지하며 좁은 화면에서는 보스 이름과 같은 17px 기준으로 표시합니다.

### 핑크 장식 규칙과 컬러 테마 분리 (개정 115)

밝은 테마가 공유하는 data-theme-pink 속성은 색상 모드·레이아웃 용도로 유지하되, 기존 핑크
고정색 장식 규칙은 :where(:not([data-theme-solid])) 범위로 제한합니다. :where를 사용하여 기존
사진 테마의 우선순위는 바꾸지 않습니다. 컬러 테마는 독립된 전체 팔레트와 공통 배치를 사용합니다.
상단 이전 보스 별표는 이전 보스 글자와 동일한 테마 보조색으로 표시하며, 경고 문구도 핑크를
상속하지 않습니다. 검증에서는 핑크 고정색을 가진 102개 선택자의 범위와 컬러 10종의 기본 변수
완전성, 기존 테마 복원·스펙트럼·자산 선택·설정 레이아웃을 확인합니다.

### 개나리 연노랑 스펙트럼 (개정 116)

개나리 테마의 30개 번호를 유지하며 크림·개나리·레몬의 좁은 노랑 범위(47/51/55도)로 단순화합니다.
목표 밝기는 0.97에서 0.75까지만 사용하여 짙은 앰버·갈색 구간을 연노랑으로 교체합니다.
표시 이름도 연한 노랑 기준으로 맞춥니다. 기존 보스별 번호와 다른 테마의 팔레트는 유지합니다.

### 다음 보스 상단 테두리의 스펙트럼 연결 (개정 117)

컬러 테마에서 다음 보스의 2px 상단 테두리는 고정된 테마 경계색을 사용하고 있어, 배경 스펙트럼을
바꿔도 이전 색이 남은 것처럼 보였습니다. 스펙트럼이 지정된 다음 보스는 테두리도 현재
--boss-spectrum-bg 색을 사용하고 가장자리 그림자는 제거합니다. 번호를 바꾸면 배경과 테두리가
함께 갱신되며, 스펙트럼을 해제하면 기존 테마 경계색을 사용합니다.

### 날짜 경계 중앙 정렬 (개정 118)

날짜 경계의 양쪽 선 열을 같은 1fr 비율로 맞추고 표시 글자를 중앙에 정렬합니다.
위 3px·아래 1px 선과 2px 간격, 글자 외곽선 및 모바일 글자 크기는 유지합니다.

### 하단 스펙트럼 도구·권한별 숨김 (개정 119)

스펙트럼 선택·배경 저장과 색상 목록을 고정 하단 영역의 주요보스선택 버튼 위로 이동합니다.
하단 영역은 한 열의 독립된 행으로 배치하고 팔레트는 일반 흐름에서 펼쳐 버튼을 덮지 않습니다.
ResizeObserver가 하단 높이를 측정해 보스 목록의 아래 여백을 함께 조정합니다. 작은 화면에서
팔레트 높이를 제한하고 하단 자체 스크롤도 지원합니다. 서버 can_save=false 계정은 버튼을
비활성으로 보이는 대신 도구 영역 전체를 숨깁니다. 기존 개발자·마스터 저장 권한은 유지합니다.

### 스펙트럼 보스 선택 상태의 연두색 채움 (개정 120)

스펙트럼이 지정된 보스 버튼도 선택 중에는 연두색 배경과 진한 녹색 글씨로 표시합니다.
기존에는 스펙트럼 배경의 !important가 선택 배경을 덮어 연두 테두리만 남았습니다. 선택 배경을
우선하고 별표·절대자 문구에도 대비 글씨를 적용합니다. 선택 해제 시 저장된 스펙트럼 배경을
다시 표시하며 실제 색상 번호와 저장·미리보기 데이터, 보스 선택 저장 방식은 변경하지 않습니다.

### 벚꽃 테마 휴대폰 작업량 최적화 (개정 121)

휴대폰 꽃잎 캔버스는 최대 24fps·DPR 1, PC는 최대 30fps로 그립니다. 기존에는 화면 주사율마다
전체 캔버스를 지우고 그렸습니다. 동일한 120Hz·DPR3 모의 환경의 2초 비교에서 그리기 240→48회,
캔버스 가로 픽셀 585→390, 변경 없는 시계 갱신의 추가 위치 읽기 4→0회를 확인했습니다.
실제 온도·배터리 측정 결과가 아니라 실행 경로와 모의 작업량 비교입니다.

박스 배치 키가 바뀌었을 때·스크롤·크기 변경 시 위치를 갱신하며 주기적 보정은 10초 간격입니다.
고정 꽃의 DOM과 스크롤 위치는 유지하고, 화면 밖 꽃·알람 버튼 장식의 움직임만 일시정지합니다.
폰의 꽃 바람 준비는 48px·4x4 격자·17개 변형·42개 스트립 프레임으로 줄여, PC 경로 대비
준비 그리기 호출이 1/5 미만입니다. 화면을 숨기면 미완료 준비를 중단하고 복귀 시 다시 준비합니다.

나비는 비행할 때만 최대 30fps 반복을 사용합니다. 쉬거나 기다릴 때는 시계 갱신·스크롤에만
반응하며 좌표가 같으면 스타일을 다시 쓰지 않습니다. 보스 15초 전 방문·5초 전 출발·터치 도망·
다른 테마로 이어지는 도망은 유지합니다. 화면이 숨겨지면 나비 레이어와 날개도 그리지 않습니다.
열지 않은 사용자 설정의 보스 버튼에는 스펙트럼 스타일을 매초 다시 쓰지 않습니다.

나비 제어 파일과 서버 무결성 해시를 함께 수정했으므로 수정본 적용 후 독립 웹서비스를
명시적으로 종료했다가 다시 실행하여 새 코드로 열어야 합니다. 이 작업에서 빌드·실행 중 서비스
재시작·실제 알림 발송은 수행하지 않았습니다.

### 공통·빗소리·겨울 테마 작업량 최적화 (개정 122)

일정 목록은 변경 키가 달라질 때만 만들고 남은 시간·현재 시각·젠 전후 상태는 계속 갱신합니다.
사용자 설정은 선택·저장·카탈로그·편집 상태가 바뀔 때 갱신하며, 저장 전에는 저장 버튼 안내를 표시합니다.
자동 저장 타이머나 카운트다운은 사용하지 않습니다. 설정창을 보고 있는 동안 숨은 일정 목록을 그리지 않으며 알림 처리와
열린 복사창 갱신은 유지합니다. 닫힌 복사창의 보스 검색도 생략합니다. 휴식의 고정 도움말은
목록 생성 시 한 번 만듭니다. 다크·컬러·배경 테마에 공통 적용됩니다.

겨울 눈은 휴대폰에서 최대 24fps, 그 외에는 최대 30fps이며 캔버스 DPR은 1입니다.
눈 개수와 이동 속도는 유지합니다. 120Hz·DPR3 모의 휴대폰에서 2초간 그리기는 60회에서
48회로, 390×844 화면의 캔버스는 585×1266에서 390×844로 줄어듭니다.
화면을 숨기거나 겨울 테마를 벗어나면 프레임을 취소하며 복귀 시 중복 루프를 만들지 않습니다.

빗소리는 기존 네이티브 오디오 반복을 유지하고 정지·테마 변경 후 0.3초 뒤 오디오 컨텍스트를
일시 중단합니다. 그 사이 재생을 다시 시작하면 이전 정지 작업은 새 재생을 중단하지 않습니다.
재생 중인 소리를 단순히 화면이 숨겨졌다는 이유로 끄지는 않습니다. 물방울은 마지막 입력부터
4초 조건을 유지하면서 연속 스크롤의 대기 타이머를 재사용합니다. PointerEvent를 지원하면
터치 이벤트를 중복 등록하지 않습니다. 사용하지 않는 유리 캔버스 효과는 계속 비활성 상태입니다.

테마 문구 위의 나비는 메뉴가 접혀 있으면 표시하지 않고 접힌 메뉴를 향한 복귀 비행도 취소합니다.
다음 보스 방문은 메뉴와 별개로 동작하지만 대상 박스가 화면 밖이면 비행을 시작하지 않습니다.
15초 전부터 5초 전 사이에 박스를 화면으로 가져오면 방문하며, 진행 중인 비행은 스크롤로 재생성하지
않습니다. 쉬는 나비는 연속 프레임 루프 없이 실제 비행에만 최대 30fps를 사용합니다.

`test_web_theme_performance.js`는 눈 그리기 횟수, 연속 입력 타이머, 정지 후 재생 경합,
닫힌 복사창과 열린 사용자 설정의 작업 경로를 검증합니다. 실제 휴대폰 온도·배터리 측정은 별도입니다.
나비 파일의 무결성 해시도 변경했으므로 적용 시 웹서비스를 종료 후 다시 실행하고 페이지를 새로고침합니다.
실행 파일·배포본은 생성하지 않았습니다.

### 휴대폰 테마·스케줄 갱신 절감 (개정 128)

겨울 눈 개수는 이전 계산값의 70%로 줄입니다. 정수 반올림을 적용하므로 390×844 모의 화면은
45개에서 32개, 기존 최대 100개는 70개입니다. 이동 속도·눈 모양·배경은 유지합니다.
겨울·벚꽃은 프레임 사이에 타이머로 쉬고 필요한 시점에만 requestAnimationFrame을 요청합니다.
기존처럼 60/120Hz 콜백마다 깨어나 그릴 시각인지 확인하지 않습니다. 최대 그리기 빈도는
휴대폰 24fps, 그 외 30fps이며 실제 빈도는 브라우저 스케줄에 따라 이보다 낮을 수 있습니다.
화면 숨김·테마 변경 시 프레임과 대기 타이머를 모두 취소합니다.

다크·컬러·모든 배경 테마에서 일반 스케줄 행의 남은 시간·상태 갱신은 보이는 영역과 위아래
160px 여유 구간으로 제한합니다. IntersectionObserver가 화면 진입을 알려주면 즉시 현재 시각으로
맞추며 매초 getBoundingClientRect를 호출하지 않습니다. 새로 만든 행은 먼저 정상 표시하고,
IntersectionObserver를 지원하지 않는 브라우저는 기존 전체 갱신으로 돌아갑니다. 다음 보스 요약·
시계·동시 젠/점멸 판정·알림과 푸시 조건은 유지합니다. 페이지가 숨겨지거나 떠나면 1초 시계
타이머도 제거하며, 복귀 시 중복 타이머나 밀린 호출을 만들지 않습니다.

빗소리는 기존 네이티브 오디오 반복과 정지 후 컨텍스트 중단을 유지합니다. 비활성 유리 캔버스는
켜지 않으며, 드문 나비 비행의 경로·속도·방문 시각과 꽃 종류·스크롤 중 고정 위치도 유지합니다.
기존 JS 자산의 1MiB 제한을 지키기 위해 일부 내장 모듈은 코드 들여쓰기만 줄였습니다.
문자열 내용·그림 품질·읽기용 원본 모듈은 보존하며 다중행 문자열이 있으면 이 정리를 생략합니다.

비빌드 모의 검사에서 120Hz의 240프레임 구간에 겨울 콜백은 약 41회로 줄었습니다.
1,000개 행 중 10개만 보이는 조건에서는 1분간 행 시간 계산이 60,000회에서 600회로 줄었고,
숨겨진 10분 동안 시계 콜백은 0회였습니다. 이는 휴대폰 온도·배터리 실측 결과가 아닙니다.
관련 검사: `test_web_theme_performance.js`, `test_web_visible_updates.js`,
`test_web_limited_sakura.js`, `test_web_limited_sakura.py` 및 기존 스케줄/알림/자산 검사.

### 설정 메뉴 공개 (개정 123)

설정 메뉴는 닉네임 터치·기존 해제 기록과 관계없이 모든 접속자에게 표시합니다.
접힌 메뉴의 버튼은 `설정 펼치기`이며 기존 접힘 상태 저장과 10분 자동 접기는 유지합니다.
초기 테마 복원 스크립트도 같은 공개 조건을 사용하므로 일반 사용자의 저장된 테마를 첫 화면부터 적용합니다.
닉네임 그림으로 바뀌는 8회 터치와 저장 상태, 벚꽃 테마의 기존 닉네임 제한,

미리보기와 이미지 복사·PNG 저장·공유는 같은 목록을 사용합니다. 텍스트·TXT의 휴식 제외 규칙은 유지합니다.

이미지는 현재 복사 미리보기의 계산된 카드 배경·그라데이션·테두리·이름/시간/상태 글자색을 읽어 그립니다.
현재 테마의 바탕색·제목색·글꼴을 사용하고 벚꽃·겨울·빗소리 사진이 이미 로드되어 있으면 그 사진도 사용합니다.
추가 사진 요청이나 주기적인 캔버스 렌더링은 하지 않습니다. 로드되지 않은 사진은 테마 색 배경으로 대체하며,
PNG 캔버스를 오염시키는 외부 출처 사진은 제외합니다. 페이지별 출력은 이미지를 연 시점의 색상을 유지합니다.
정적 PNG에는 화면의 꽃잎·눈·나비 등 동적인 오버레이를 재현하지 않습니다.

기존 6개 파일·각 1MiB의 웹 패치 계약을 유지합니다. JS에 있던 빗방울 스프라이트의 동일한 Base64 바이트를
`index.html`의 `rain-foreground-photo` 템플릿으로 옮겨 파일당 제한 안에 담았습니다. 이미지 자체는 변경하지 않았습니다.

### 단일 EXE 웹 준비 응답 확인

배포 EXE에서는 실행기와 실제 웹 작업의 PID가 다를 수 있습니다. 본체가 실행기 PID만 인정하면
HTTP·HTTPS 준비 로그가 있어도 20초 뒤 응답 없음으로 처리하고 정상 웹을 종료할 수 있습니다.
`web_worker_identity.py`는 Windows의 직접 자식 관계·동일 실행파일 경로·생성 시각을 확인한 작업의 응답을 인정합니다.
실행 세션·프로토콜·포트 확인과 기존 종료 절차는 유지하며, `worker_status_identity_verified`에 두 PID를 기록합니다.
웹 프로세스 자체의 시작 오류는 HTTPS 실패와 구분해 실제 안내를 표시합니다.

이는 본체 제어 코드 수정이므로 정적 웹 파일 업데이트로는 반영되지 않습니다.
소스 회귀 검사 통과와 실제 EXE 재빌드·최초 실행 확인을 구분해야 합니다.

### 웹 승계 후 이전 PC로 잘못 복구되는 경우

웹 프로세스는 주소 갱신을 완료했지만 본체의 비활성 DDNS 상태를 보고 실패로 판단하면,
시험 공개 기한 120초 후 이전 웹 담당자를 복원할 수 있었습니다.
웹 공개 확정은 `publication_ddns_status()`로 받은 실제 웹 프로세스의 상태와 이번 승계 이후 갱신 응답을 사용합니다.
응답이 없거나 웹의 DDNS가 미설정이면 본체의 과거 성공 기록으로 대신 확인하지 않습니다.
주소 확인 전에는 `웹 주소 확인 중`을 표시합니다.

공개 성공 후 공유 기록에서 백업 담당자가 제거되면 이전 복구는 취소합니다.
복구 직전에도 정상 상태를 재확인하고, 확정/복구 작업을 직렬화해 늦은 작업이 정상 웹을 중단하지 않게 했습니다.
실제 주소·웹 준비 실패에 대한 기존 복구는 유지합니다.
변경은 본체 제어 코드이므로 참여하는 관리자들의 본체에 반영해야 하며 정적 웹 ZIP으로 적용되지 않습니다.

### 3초 주기 웹 수집과 보스전 타이머 표시 지연

웹용 스케줄 생성은 Tk 메인 스레드의 3초 게시 콜백에서 실행됩니다. 생성이 0.3초 걸리면 같은 스레드의
보스전 타이머도 그동안 표시를 갱신하지 못합니다. 경과시간은 `perf_counter`로 계속 측정됩니다.

`web_snapshot_memo.py`는 원본 스케줄·설정의 내용과 날짜/제어 경계로 변경을 판별합니다.
변경이 없으면 이미 만든 보스·고정보스·휴식·목록을 재사용하고 수집 확인 시각만 새 봉투에 갱신합니다.
따라서 반복 생성은 건너뛰고 웹의 15초 신선도 검사와 기존 90초 위임 전송 계약은 유지합니다.
원본 내부의 시간 수정·삭제·별표·막타·약칭·색상·휴식/통계 설정과 서버·시즌 변경을 검사하며,
자정·점검·서버 오픈 경계는 편집 없이도 재수집합니다. 변경 후 생성 실패는 다음 주기에 재시도합니다.

Tk 변수를 작업 스레드에서 읽거나 이전에 제공한 봉투를 수정하지 않습니다.
최초 생성과 실제 변경 시 생성 비용은 남습니다. `schedule_snapshot_collection_slow`는
`reused`를 함께 기록해 재사용 검사 비용과 실제 재수집 지연을 구분합니다.
이 변경은 본체 코드이며 새 실행부터 반영됩니다. 소스 검사와 실제 타이머의 표시 개선 실측은 구분합니다.

### 벚꽃 나비의 현재 방문 시각

나비는 다음 보스 젠 15초 전에 접근을 시작하며 젠 시각에도 머물고, 1초 후에 화면 밖으로 떠납니다.
과거 개정의 '5초 전 출발' 조건은 이 규칙으로 대체합니다. 같은 시각의 보스는 한 번만 방문합니다.
터치 도망과 비행 속도, 보스 박스의 젠 후 3초 이동 조건은 유지합니다. 화면 복귀 시 이미 출발 시각이
지났으면 지난 착지를 다시 재생하지 않습니다. 별도 `butterfly.js`와 서버의 검증 해시를 함께 반영해야 하며,
기존 여섯 파일의 웹 업데이트만으로는 이 별도 스크립트가 교체되지 않습니다. 적용 후 페이지를 새로고침합니다.
# 아이언맨 HUD 테마 (소스, 미배포)

테마 탭의 리미티드 스페셜 에디션에서 `아이언맨`을 선택합니다. 게스트를 포함해 선택할 수 있으며 기존 사용자별 테마 저장을 사용합니다. 내부 키 `avengers`는 유지하므로 기존 선택이 이어집니다. 다른 컬러 테마의 핑크 플래그와 분리했고, 선택 시 눈·빗방울·벚꽃 효과를 중지합니다. 다음 보스의 시간과 이름이 한 줄에 안 들어가면 이름 전체를 시간 아래에 표시합니다.

엔드게임 포탈과 아이언맨 아머 사진을 로컬 파일로 보관하고 기존 스타일시트에 포함합니다. 전체 화면을 빨간 아머 케이스로 감싸고, 보스·휴식 패널은 두꺼운 금색 절삭 모서리와 금속 그라데이션을 사용합니다. 보스 이름은 밝은 연노랑이며 선택·클릭 색상은 빨강입니다. 상단과 다음 보스 오른쪽에는 원형 아크 리액터, 다음 보스 왼쪽에는 금색 헬멧을 표시합니다. 열 개의 blob 이미지 주소를 재사용합니다. 리액터 두 개의 내부 빛만 CSS 회전·투명도로 움직이며, 화면 밖·백그라운드에서는 멈춥니다. 동작 줄이기에서는 링만 천천히 회전합니다. 다음 보스 장식은 시네마틱 공간을 위해 약 15% 줄였습니다.

수정 위치·이미지 출처·소스 동기화 순서는 `web_assets/avengers/README.md`를 참고합니다. 색상 스펙트럼 편집 대신 이 테마 전용 HUD 배경을 사용합니다. 복사 PNG에는 색상과 배경사진을 반영하며 CSS 장식까지 화면 캡처처럼 복제하지는 않습니다.

## 시네마틱 (런타임 소스·브라우저 검증)

`web_cinematic.py`가 프로젝트/내장 `시네마틱/*.mp4`의 비디오 트랙 길이·프레임률을 읽습니다.
배포 EXE 옆에 `시네마틱` 폴더가 있으면 그 폴더를 우선합니다. 원본은 변환·덮어쓰기하지 않습니다.
동영상은 인증된 동일 출처 `/cinematic/` 경로로 제공하며 HTTP·HTTPS 모두 byte Range/ETag를 지원합니다.
영상별 길이·프레임률·해상도를 현재 파일에서 읽습니다. 경로 이탈·링크·잘못된 메타데이터는 제공하지 않습니다.

- 자동 시작: `보스 시각 - 5초 - 해당 MP4의 비디오 트랙 길이`.
  자동 영상은 페이지 세션의 첫 시작 위치만 무작위로 정하고, 이후 목록 순서대로 재생하며 끝에서는 처음으로 이어집니다.
  실제 자동 재생의 `play` 이벤트에서만 순서를 넘깁니다. 시간 계산·사전 준비·생략된 연속 보스는 순서를 소비하지 않습니다.
  같은 보스의 일시정지·이어 재생은 선택을 유지하며, 확인용 패널 이전·다음은 자동 순서를 바꾸지 않습니다.
  테마 재선택은 순서를 유지하고 페이지를 새로 열면 첫 위치를 다시 선택합니다. 목록 변경 시 다음 파일이 남아 있으면 그 위치를 이어갑니다.
- 전체 스케줄의 보스를 시각순으로 묶습니다. 앞 보스와의 간격이 150초 이하로 이어지면 같은 묶음이며 첫 보스만 재생합니다.
  필터를 바꿔도 전체 스케줄 기준 묶음은 유지합니다. 재생 중 다른 영상의 시작 구간이 겹치면 폐기하며 큐·나중 재생은 없습니다.
- 마지막 프레임의 중앙 시각으로 이동해 캔버스 한 장으로 보존하고 비디오의 src를 제거해 디코더를 해제합니다.
  개정 175부터 정지 화면은 영상 종료 5초 후 작은 화면으로 줄고, 추가 5초 후 지워져 헬멧·아크가 있는 기본 화면으로 돌아갑니다.
  단독 보스 또는 연속 묶음의 다음 보스 전환으로 기존 해제 조건을 먼저 만족하면 기다리지 않고 지웁니다.
- 재생 중 `.ironman-cinematic-stage`는 기존 다음 보스 박스 전체를 채우는 절대 배치 배경입니다.
  영상 비율이나 16:9로 박스를 조정하지 않습니다. `object-fit:cover; object-position:center`로 가운데를 보여주고 양옆 넘침을 자릅니다.
  최초 표시도 영상 종료 후와 같은 작은 제목·남은 시간 높이입니다. 초기 화면부터 CSS로 적용하여 큰 박스가 먼저 보이지 않습니다.
  영상 재생 때만 기존 재생 높이로 펼치며 영상 비율로 높이를 계산하지 않습니다.
  일시정지는 작은 제목·남은 시간 높이로 줄이고 이어 재생하면 기존 박스 높이로 복원합니다.
  영상 종료 후의 마지막 프레임은 기존 재생 영역과 창 높이를 유지하며 남은 시간을 영상 위에 표시합니다.
  영상 종료 후 5초가 지나면 작은 창으로 줄이고, 그 뒤 5초가 지나면 초기 그림을 복원합니다. 타이머 한 개를 두 단계에서 재사용합니다.
  새 영상·조기 보스 전환·테마 이탈·페이지 이탈은 이전 예약을 취소합니다. 백그라운드 지연 복귀 때는 실제 경과한 단계를 정리합니다.
  연속 보스 묶음에도 이 시간 제한을 적용하며, 묶음의 나머지 영상 생략 규칙은 유지합니다.
  재생 중에는 남은 시간을 숨기고 젠 시각·보스 이름만 표시합니다(작은 등장 예고 문구는 유지).
  일시정지·마지막 프레임 상태에서는 남은 시간을 왼쪽 `1ch` 들여쓰기로 표시합니다.
  헬멧·아크·알람 버튼은 계속 숨깁니다. 정지 화면 해제 시 원래 표시가 돌아옵니다.
  일반 다음 보스의 헬멧은 직전 크기의 1.3배(최대 54.6×65px), 아크·발광 영역은 최대 54×54px이며 좁은 화면에서는 더 줄입니다.
  헬멧은 절대 배치를 유지하고 아래 위치·시간 왼쪽 여백을 맞춰 창의 높이를 늘리지 않습니다.
  아크의 회전 빛은 바깥 링의 비대칭 흰색·청록색 호와 밝은 점으로 표시하며 4.5초 회전과 4.8초 발광을 사용합니다.
  두 CSS 레이어만 사용하며 화면 밖·백그라운드에서는 멈춥니다.
  시스템 동작 줄이기 모드에서는 아이언맨 아크 링만 12초 주기로 천천히 회전하고 발광 점멸은 끕니다.
  검증은 발광을 고정한 두 시점의 회전 변환과 실제 화면 픽셀을 비교합니다. CSS 실행 상태만으로 회전 성공을 판단하지 않습니다.
  영상·일시정지·마지막 프레임 위의 이름·남은 시간에는 별도 그라데이션 배경을 깔지 않습니다. 일반 화면의 이름 배경은 유지합니다.
- 영상 재생 중 왼쪽 아래에 작은 `곧 보스가 출연 합니다.` 문구가 점멸합니다.
  기존 `spawnBlink`의 T-5초~젠 후 3초 조건으로 메인 남은 시간과 외곽선도 점멸합니다.
  문구·시간은 CSS opacity, 외곽은 CSS outline/glow로 처리하며 새 JS 주기 타이머는 없습니다.
  등장 안내는 기능적 신호이므로 동작 줄이기 설정에서도 완만한 점멸을 유지합니다(문구 1.6초, 시간·외곽 1.4초 주기).
  장식 아크의 동작 줄이기 규칙은 유지합니다. 안내 문구는 카운트다운보다 위의 레이어에 배치합니다.
- 사용자 탭 옆 상단 `재생` 버튼은 숨깁니다. 다음 보스 아래 조작부의 이전·재생/일시정지·다음으로 수동 확인합니다.
- 다음 보스 프레임 아래에는 금속 프레임에 맞춘 역삼각형 SVG만 표시합니다(접힌 높이 22px).
  조작부 스타일은 플레이어와 같은 런타임의 `/cinematic/player.css`에서 불러옵니다.
  이전 페이지 스냅샷과 섞여도 전용 `#ironman-media-dock` 규칙으로 격리하며 CSS 준비 전에는 조작부를 숨깁니다.

  일시정지를 해제하여 해당 보스 영상을 재생합니다. 이미 자동 재생 구간에 들어갔다면 현재 시각에 맞는 위치부터 재생합니다.

### 전체 테마 상단 메뉴 자동 숨김

개정 174에서는 아래의 작은 날짜·시간 표시를 제거합니다. 개정 173의 상단 간격과 표시 영역 높이(13.75px + 아래 1px)는
빈 정적 여백으로 그대로 유지하며, 날짜·시간 DOM 갱신과 접힘 시 시계 갱신 호출도 제거합니다. 메뉴 복귀 시 기존 상단 시계는 유지합니다.

개정 172에서는 메뉴를 숨긴 동안 다음 보스 위에 현재 날짜·요일·시간을 작은 노란색(11px, `#ffe279`)으로 표시합니다.
개정 173에서는 이 표시를 왼쪽으로 붙이고 접힌 화면의 상단 패딩을 2px, 프레임 상단 패딩을 0으로 줄입니다.
시계와 첫 다음 보스 사이 간격은 1px이며, 메뉴를 복원하면 테마의 기존 상단 간격으로 돌아갑니다.
선택한 스케줄 날짜와 관계없이 실제 현재 시각을 사용하며, 메뉴가 접히는 즉시 그립니다.
기존 로컬 1초 시계를 재사용하고 페이지가 백그라운드이면 기존 시계 중지 규칙을 따릅니다.
메뉴를 복원하면 작은 시계는 숨기고 갱신도 멈추며 기존 상단 시계로 돌아갑니다. 새 요청·타이머는 추가하지 않습니다.

다크를 포함한 모든 테마에서 사용자 입력이 3초간 없거나 아래로 스크롤하면 제목·탭·날짜와 시계·오늘/다음날·휴식/고정·전체 알림 영역을 접습니다.
`recent`의 지난 보스도 메뉴와 함께 숨기고, 다음 보스부터 아래쪽 스케줄을 계속 표시하여 세로 공간을 확보합니다.
메뉴가 보일 때의 첫 아래쪽 휠/세로 스와이프는 실제 목록 이동에 앞서 메뉴를 접고 다음 보스 위치에서 멈춥니다.
같은 제스처의 연속 입력은 소비하고, 새 아래쪽 제스처부터 목록을 정상 스크롤합니다. PC는 300ms 넘는 휠 입력 간격, 모바일은 새 터치 시작으로 제스처를 구분합니다.
첫 접힘 중 이미 반영된 스크롤도 다음 보스 위치로 보정합니다. 설정·입력란·팝업 조작과 주로 가로 방향인 터치는 이 하강 정지에서 제외합니다.
아래에서 올라오는 첫 스크롤은 메뉴가 숨겨진 다음 보스 위치에서 멈춥니다. 최상단 도착 자체로 메뉴를 열지 않습니다.
PC에서는 휠/트랙패드 연속 입력이 300ms 넘게 멈춘 뒤, 최상단에서 새로 위쪽 방향으로 스크롤하면 메뉴를 표시합니다.
같은 스크롤의 연속 입력과 관성은 다음 보스에서 멈춘 상태를 유지합니다. 이미 최상단에서 유휴 상태로 숨겨졌다면 새 위쪽 휠 입력으로 바로 표시합니다.
휴대폰·태블릿에서는 끌어서 올라오는 동작 역시 다음 보스에서 멈춥니다. 새로 최상단에서 위로 스크롤하는 제스처나 가벼운 탭으로 메뉴를 표시합니다.
탭은 450ms 이내·이동 10px 이내로 구분하고, 탭이 끝나면 즉시 메뉴와 지난 보스를 표시하여 최상단으로 이동합니다.
단순 touchstart는 드래그와 구분할 수 없어 표시 조건으로 쓰지 않습니다. 핀치·취소·길게 누르기도 탭으로 취급하지 않습니다.
표시용 탭은 보스 알림 클릭으로 이어지지 않게 하고, 최상단의 표시용 위쪽 스크롤은 당겨서 새로고침으로 이어지지 않게 합니다.
마우스 이동·클릭·화면 진입·일반 키보드 입력과 Ctrl+휠 확대는 숨겨진 메뉴를 복원하지 않습니다.
메뉴가 보이는 동안의 입력은 3초 유휴 시각을 갱신합니다.
단, 마우스가 다음 보스 박스의 아래쪽 경계를 벗어나면 그 시점부터 3초를 셉니다.
아래쪽 영역 안에서 계속 마우스를 움직여도 시간을 연장하지 않으며, 박스 위쪽으로 돌아오면 일반 입력 기준으로 돌아갑니다.
터치 이동에는 이 마우스 위치 조건을 적용하지 않습니다. 클릭·키보드 등 실제 조작과 기존 편집 예외는 유지합니다.
설정 페이지·사용자 보스 편집·열린 팝업·입력란 편집·누르고 있는 터치가 있으면 메뉴를 유지합니다.
기존 설정창의 1분 자동 닫기와는 별도로 동작합니다.

`web_menu_idle.js`의 `WebMenuIdle`은 단일 타이머와 마지막 입력 시각으로 판단합니다.
`sync_web_sakura.py`가 기존 정적 파일 크기 제한 안에서 이 모듈을 압축해 `schedule.js`에 포함하며, 별도 요청이나 서버 경로를 추가하지 않습니다.
휠 리스너는 첫 하강 입력을 취소할 수 있도록 등록하고, 첫 제스처를 붙잡는 동안만 기본 스크롤을 막습니다. 접힌 뒤 새 하강 입력과 일반 목록 탐색은 정상 처리합니다.
마우스 이동마다 타이머를 새로 만들지 않으며 백그라운드/페이지 이탈 중에는 타이머를 중단합니다.
