# 공지 / AI 모듈 업데이트

## 이번 구현 범위

- 스케줄 창 상단 `업데이트 확인`: 배포 날짜(한국시간), 버전, 설치 상태, 제목, 릴리스 설명/패치 내역, 설치/실패 이력.
- 기존 저장소 `pulpul7/pulpul7-boss_timer_app`의 공개 GitHub Releases만 조회한다. 본체 배포 ZIP, 초안, 시험판(prerelease)은 대상이 아니다.
- 기본 자동 확인: 활성화, 한국시간 06:00 이후 하루 첫 확인. 오후에 처음 켜도 확인한다. 계속 실행 중이면 날짜 변경 후 기준 시각에 확인한다. 창에서 활성화/시각을 저장할 수 있다.
- 자동 확인에 실패해도 당일 무한 재시도하지 않는다. 오류는 이력에 남기며 `지금 확인`으로 재시도한다.
- 새 버전 발견 시 부모 중앙의 자체 Tk 안내창에서 5초 후 다운로드/설치한다. 취소·Esc·Enter·창 닫기는 모두 취소다. 취소한 버전은 수동 설치 가능하다.
- 수동 확인은 자동 설치 카운트다운을 시작하지 않는다. 원하는 버전을 선택하고 설치 확인을 눌러야 한다.
- 설치 파일은 다음 프로그램 실행 때 검증하고, 모듈을 실제 로드하여 시작 검사를 통과하면 적용된다. 본체/디코봇을 강제 종료하거나 재시작하지 않는다.

**독립 모듈 실행/시작 검사/복구와 실제 공지 수집을 연결했다. 시간 분석·TTS·질문 버튼은 다음 단계다.**
관리 화면/기록/기간 제어는 `notice_module/payload/`로 옮겼다. 본체는 `notice_runtime.py`의 최소 host API로 연결한다.
다운로드된 공식 모듈을 고유 Python namespace로 로드한다. `sys.path`를 변경하지 않으며, 검증 폴더에 `.pyc`를 생성하지 않는다.
새 모듈 시작 실패 시 이전 정상 버전, 그것도 불가하면 EXE에 포함된 내장 모듈로 복구한다.
시작 확인 전 프로세스가 종료되면 기록된 trial을 다음 실행에서 감지하여 같은 실패 버전의 반복 실행을 막는다.
실패 버전은 자동 설치 대상에서 제외하고 업데이트 창에서 사용자가 직접 재시도할 수 있다.
이 구조는 독립 **배포/업데이트** 구조이며 보안 샌드박스나 별도 프로세스 격리가 아니다.
악의적 코드·무한 대기·네이티브 충돌을 본체와 완전히 격리하는 기능은 제공하지 않는다.

## 배포자가 게시할 형식

GitHub 저장소에 ZIP을 소스로 커밋하지 않고, **Release 첨부 파일**로 올린다.

- 태그 권장: `ai-v1.0.0` (본체 태그와 분리)
- 첨부 파일명: `Update_AI_v1.0.0.zip` — 공백 없음, 대소문자 구분
- 릴리스 제목: 버전별 업데이트 제목
- 릴리스 본문: 기능 추가, 수정 사항, 설명, 알려진 문제
- 같은 AI 버전을 여러 릴리스에 중복 게시하지 않는다.
- 모든 버전은 이전 버전이 없어도 설치 가능한 **완전한 모듈 패키지**로 올린다. 순차 적용이 필요한 차등 패치는 지원하지 않는다.
- 다른 버전을 제거하지 않으면 창에서 과거 릴리스 설명도 볼 수 있다. 로컬 설치 이력은 릴리스가 삭제되어도 보존된다.
- GitHub API의 asset `digest`가 `sha256:...`인 파일만 설치 가능하다. 없으면 추측하거나 검증을 생략하지 않고 설치 불가로 표시한다.

ZIP 최상단:

```text
module.json
payload/
  __init__.py
  main.py
  ... 필요한 모듈 파일만 ...
```

`module.json` 형식 예시(배포 시 실제 값으로 작성):

```json
{
  "module_id": "boss_timer_notice_ai",
  "api_version": 1,
  "version": "1.0.0",
  "min_app_version": "5.0.0",
  "python_version": "3.13",
  "entrypoint": "payload/main.py",
  "files": {
    "payload/__init__.py": "해당 파일의 실제 SHA-256 소문자 64자리",
    "payload/main.py": "해당 파일의 실제 SHA-256 소문자 64자리"
  }
}
```

- 위 Python 버전/본체 최소 버전은 예시이며, **실제 배포 EXE의 Python major.minor와 실제 본체 메타데이터 버전**에 맞춰야 한다.
- `max_app_version`을 선택적으로 지정할 수 있다.
- `files`는 `module.json`을 제외한 ZIP 안의 모든 파일 경로와 해시를 포함해야 한다.
- 본체에 없는 Python 라이브러리를 자동으로 pip 설치하지 않는다. 의존성을 포함하거나 본체 지원 범위에 맞춰야 한다.
- 허용 확장자: `.py`, `.json`, `.txt`, `.md`, `.png`, `.jpg`, `.ico`, `.wav`, `.mp3`.
- 최대 ZIP 32 MiB, 압축 해제 96 MiB, 항목 2,000개. 실행 파일/DLL, 링크, 암호 ZIP, 경로 탈출, Windows 특수 경로, 대소문자 중복 파일은 거부한다.

## 검증과 파일 보존

1. 설치 직전 공식 배포 목록을 다시 가져오고 현재/설치 대기 버전보다 높은지 숫자로 비교한다 (`1.10.0 > 1.9.0`).
2. 다운로드 크기·GitHub SHA-256을 검사한다.
3. 내부 모듈 ID, API, 버전, 본체/Python 호환성, 전체 파일 해시, Python 문법을 검사한다.
4. 프로세스 간 잠금 안에서 버전을 다시 비교한다. 다운로드 중 다른 창/프로세스가 상위 버전을 설치해도 구버전을 덮어쓸 수 없다.
5. 전용 임시 폴더를 검증한 뒤 별도 버전 폴더로 이동하고, 상태 JSON을 원자적으로 교체한다.
6. 다음 실행에서 파일 검사 → 모듈 로드 → `start()` → `health_check()`를 수행한다. 성공 후에만 시작 확인을 확정한다. 실패하면 이전/내장 모듈로 복구하고 실패 기록을 남긴다.

설치 위치는 EXE/소스 옆 `update_ai/`이며, 폴더 쓰기 권한이 필요하다.

- `state.json`: 자동 확인 설정, 마지막 확인일, 적용/대기/이전 버전, 배포 목록 캐시, 작업 이력
- `versions/<버전>-<해시>/`: 각 버전 파일 (기존 버전 보존)
- `updater.lock`: 여러 프로세스의 동시 상태 변경 방지 (프로세스 종료 시 잠금 해제)

내장 모듈 버전도 현재 버전 비교에 포함한다. 예를 들어 내장 1.0.0이 있으면 같은 1.0.0 ZIP은 설치하지 않는다.
내장 모듈이 더 최신인 본체로 업데이트한 경우 더 오래된 외부 모듈을 우선 로드하지 않는다.

## 모듈 API v1

- 진입 파일: `MODULE_API = 1`, `create_plugin(host)`.
- 반환 객체: `start()`, `health_check()`, `open_management()`, `stop()`.
- `health_check()` 결과: `{"ok": true, "api_version": 1, "features": [...]}`.
- host 제공: Tk root, 별도 data_root, get_server/get_parent, 자체 중앙 message_box, log, call_later/cancel_later.
- 본체 객체 전체나 본체의 내부 공지 구현을 import하지 않는다. 모듈 내부 import는 상대 import를 쓴다.
- 시작/상태 검사는 GUI 스레드에서 실행되므로 짧게 끝나야 한다. 네트워크, 대기, 무거운 분석, 데이터 스키마 변경을 수행하지 않는다.
- 수집은 독립 worker에서 실행하고, 이후 분석도 UI를 막지 않도록 연결한다. 실패한 시작의 예약/자원은 `stop()`에서 정리해야 한다.
- 이 단계는 GUI host만 연결했다. 디코 명령 등록·음성 큐 연결은 후속 단계에서 최소 인터페이스를 확장한다.
- 데이터 스키마 마이그레이션은 현재 없다. 추후 추가 시 복구 호환성과 별도 백업 전략부터 구현한다.

## 수동 패키징 (아직 실행하지 않음)

1. `notice_module/payload/` 안에서 모듈 수정.
2. `notice_module/metadata.json`의 모듈 버전 올리기. 본체 버전과 별개다.
3. 본체 EXE와 같은 Python major.minor에서 `python build_ai_update.py`를 직접 실행.
4. `dist_AI/Update_AI_v<버전>.zip`과 표시된 SHA-256 확인. 같은 이름 파일이 있으면 덮어쓰지 않고 거부한다.
5. 기존 GitHub 저장소에 Release 첨부 파일로 업로드하고 제목/패치 설명 작성.

스크립트는 패키지 `module.json`과 파일별 해시를 생성하고 기존 설치 검증기로 확인한다.
GUI/자동업데이터/본체 빌드는 이 스크립트를 자동 실행하지 않는다.
최초 본체 수동 빌드에서는 `boss_timer_gui.spec`가 `notice_module/`을 신뢰할 내장 기본 소스로 포함한다.

이 폴더는 Git에서 제외했고 초기 배포에 포함하지 않는다. 설정·서버 스케줄·토큰·음성에는 접근하지 않는다.
이력은 삭제하지 않으며 향후 정리 기능은 별도 동의를 받아 추가한다.

SHA-256은 파일 손상/잘못된 파일 검출용이다. 배포 신뢰는 고정 GitHub 저장소와 HTTPS에 기반하며,
게시자 전자서명을 별도로 검증하는 구조는 아니다. 저장소 배포 권한은 엄격히 관리해야 한다.

## 확인 방법

```text
python -B -m unittest test_notice_collection test_notice_runtime test_notice_management test_ai_module_updater -v
```

네트워크는 가짜 응답으로 대체하며, OS 임시 폴더에 만든 테스트 데이터는 테스트 후 정리한다.
실제 게임, 사용자 설정, 실제 설치 폴더, GitHub 배포를 변경하지 않는다. 빌드는 실행하지 않는다.
최초 실제 Release 업로드 후 다운로드·5초 안내·재시작 적용은 사용자 환경에서 별도 확인해야 한다.

GitHub 배포 파일 API 참고: https://docs.github.com/en/rest/releases/assets
