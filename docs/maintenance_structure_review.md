# 점검·서버오픈 구조 검토

확인일: 2026-10-30. 현재 소스의 실행 경로를 검토하고 격리된 객체로 재현했다.
아래 검토·재현 항목은 수정 전 소스의 문제를 기록한다. 이어진 개선 요청으로 소스를 수정했으며 현재 구현 범위는 바로 아래에 구분한다.
관리자 EXE의 전체 상태 파일을 확보한 것은 아니므로, 원격 운영 상태 전체와 소스 재현 결과를 구분한다.

## 개선 구현 · 2026-10-30

- `schedule_maintenance.py`가 날짜별 점검과 주간 반복 경계를 계산한다. 정기점검 공지의 예외 시각은 그 주에만 적용하며 반복 설정을 바꾸지 않는다.
- 기존 `schedule_control_events`에 선택적 `planned_end_at`, `reopened_at`, `cancelled_at`, `maintenance_id`를 저장한다. 종료 예정은 실제 종료와 다르며 시계만으로 종료시키지 않는다.
- 새 알리미 호스트 콜백은 시작·연장·완료·취소를 같은 종류·시작 시각의 회차에 연결한다. 서버·시즌, 입력/인계/전체 업데이트 충돌과 저장 실패를 검사한다. 실패한 저장은 메모리 변경도 복원한다.
- 공지 수집이 꺼져 있거나 점검 분류가 꺼져 있으면 자동 적용하지 않는다. 충돌·읽기 실패·불명확한 기간은 보류한다. 알 수 없는 과거 임시점검을 오래된 공지로 새로 만들지 않는다. 종료 공지가 늦게 수집된 정기점검은 정확한 날짜의 회차를 만든 다음 종료시킬 수 있다.
- 재수집 기록은 서버·시즌·행동·시각별로 중복 적용을 막는다. 인계 등 `deferred`만 자동 재시도하며 중단된 `pending`이나 실패를 성공으로 추정하지 않는다.
- 일반 보스는 점검 후 입력된 자료인지 검사한다. 고정보스는 생성 시각이나 일반 보스 존재 여부에 의존하지 않는다. 확인된 오픈 이후 고정보스는 다시 허용하고, 지난 정기점검 이전의 오래된 제어는 현재 고정보스를 계속 막지 않는다. 기록은 보존한다.
- GUI/웹 공유의 세 고정보스 생성 경로와 Discord 조회·일반/고정 알림 작업이 공통 가시성 정책을 사용한다. 각 기능의 조회 기간·사용 설정·침공 조건은 유지한다.
- `HHMM 서버오픈 컷`과 점검 예약어를 일반 보스 컷보다 먼저 분류한다. 일반 보스 컷은 그대로다. `0일`은 오늘이며, `1일 HHMM ... 컷`은 하루 전 날짜를 뜻한다. 지난 임시점검 수동 입력의 기존 `historical_only` 규칙은 유지한다.
- 새 보스 입력 때 다른 보스의 점검 전 미래 기록을 자동 삭제하던 경로를 제거했다. 같은 보스 덮어쓰기와 명시적 삭제·백업·복구는 유지한다. 지난 자료는 표시 조건으로 숨기며 오픈했다고 재활성화하지 않는다.
- 취소된 회차는 점검 알람·현재 제어·화면 행에서 제외한다. 정기점검 제어와 계산된 정기점검 행은 화면에서 중복 표시하지 않는다.

검증: `test_maintenance_lifecycle.py`는 시작→연장→완료→저장/복원→웹 스냅샷·Discord 조회/고정 알림, 취소·충돌·저장 롤백·기존 문법을 연결해서 검사한다. 기존 공지·입력·웹 관련 검사 결과는 `DEBUG_NOTES.json`과 `BUILD_HANDOFF.md`에 기록한다.

한계: 알리미 1.0.2와 새 본체·봇 소스가 필요하다. 선택적 API가 없는 구형 호스트/모듈은 기존 가져오기 경로를 사용한다. 기존 독립 웹 프로세스와 업데이트 전 EXE를 자동 교체하지 않는다. 관리자의 실제 자료와 EXE 실행 결과는 확인하지 않았고, 저장 자료를 일괄 이행·삭제하지 않았다. 공지 읽기 기반의 기존 정기 서버오픈 알람/입력 기준 어댑터는 별도로 유지한다.

## 수정 전 검토 기록

## 결론

정기점검과 임시점검은 저장 형식부터 완전히 같은 기능은 아니다. 그러나 입력 분류, 점검 상태의 종료,
일정 신선도, 화면 표시와 자료 정리가 서로 다른 기준으로 연결되어 있어 문제가 반복될 구조가 있다.
고정보스 누락은 브라우저 캐시 초기화나 웹 재시작으로 해결할 유형이 아니다.

## 확인한 문제

1. **표시 이름과 내부 종류가 다르다.**
   `_normalize_schedule_control_name`은 텍스트 `정기점검`도 `temporary_maintenance`로 분류한다.
   반면 정기점검 버튼과 공식 정기점검 공지 반영은 별도의 반복 설정을 바꾼다.
   따라서 같은 이름을 봐도 어느 입력 경로를 거쳤는지에 따라 동작이 다르다.

2. **임시점검 시작과 종료가 한 흐름이 아니다.**
   공지 가져오기는 임시점검 시작을 저장하지만 요청에 종료 시각을 넘기지 않는다.
   완료·연장·취소 제목은 이 시작 가져오기 후보에서 제외된다.
   `NoticeHost`에는 시작·정기 설정 반영 콜백은 있지만 임시점검 종료 반영 콜백은 없다.
   `server_open_override`는 정기점검 기사만 처리하는 읽기 전용 경로다.
   `_get_schedule_active_control_event`는 지난 제어 중 가장 최근 항목을 계속 선택한다.
   실제 종료가 스케줄에 기록되지 않으면 예전 임시점검이 다음 주에도 기준으로 남을 수 있다.

3. **일반 보스의 신선도 검사가 고정보스에 맞지 않는다.**
   `_is_schedule_event_visible`는 점검 뒤 만들어진 `created_at`을 요구한다.
   `_is_fixed_boss_schedule_row_visible`는 그 자리에 `None`을 전달한다.
   그래서 새로 입력한 일반 보스는 보이고, 요일·시각으로 계산하는 고정보스는 숨겨진다.
   별도로 고정보스 생성 자체도 `_has_schedule_data_for_fixed_boss_rows`에 의존한다.

4. **제어 문법보다 일반 보스 컷 문법이 먼저 해석된다.**
   `1031 서버오픈 컷`은 `server_open` 제어가 아닌 일반 보스 컷으로 파싱된다.
   `컷` 없는 지난 시각은 기본적으로 다음 날로 이동하고, `0일`은 입력 당일을 뜻한다.
   사용자가 예상하는 오픈 처리와 실제 저장 상태가 달라질 수 있다.

5. **표시 제한과 저장 자료 정리가 결합되어 있다.**
   새 보스 자료를 입력하면 `_delete_schedule_hidden_after_temporary_maintenance_if_needed`가
   점검 전 생성된 미래 행을 백업한 뒤 실제 목록에서 제거한다.
   백업·복구 경로는 있지만, 점검 표시 기준이 단순히 화면만 숨기는 것은 아니다.
   따라서 재입력·삭제·동기화를 임의로 반복하는 것은 원인 확인을 더 어렵게 할 수 있다.

6. **디코와 웹이 고정보스에 다른 유효성 판단을 한다.**
   디코 `ScheduleReader.upcoming_rows`는 고정보스 파일의 사용·요일·격주 조건을 읽는다.
   웹은 GUI 공유 자료를 받아 점검·삭제·일반 일정 존재 조건까지 적용한다.
   이 차이 때문에 디코에 고정보스가 나와도 웹 자료 생성이 정상이라는 증거는 되지 않는다.
   의도된 조회 기간 차이는 유지하되, 공통 고정보스 유효성 기준을 명시할 필요가 있다.

정기점검 공지의 실제 날짜를 반복 요일·시각 설정에 반영하는 어댑터도 있다.
특정 주의 예외 일정과 매주 반복 템플릿을 같은 값으로 다루는 점은 추가 설계 위험이다.
이번 관리자 고정보스 누락의 실제 원인으로 확인된 항목과는 구분한다.

## 재현·검증

- 실제 파서에서 `정기점검`·`임시점검` 텍스트가 모두 `temporary_maintenance`가 됨을 확인했다.
- `1031 서버오픈 컷`이 일반 `scheduled` 항목이 됨을 확인했다.
- 10월 29일 임시점검을 유지한 채 10월 30일 및 11월 5일에 새 일반 입력이 있는 상태를 만들었다.
  두 시점 모두 일반 일정은 표시되고 고정보스는 숨겨졌다. 11월 5일 사례는 새 정기점검을 지난 뒤에도 같았다.
- 같은 분석 가능한 완료 공지에서 정기점검 오픈 정보는 반환되고 임시점검 오픈 정보는 반환되지 않았다.
- 기존 비빌드 검사 68개가 통과했다: `test_notice_regular_maintenance`, `test_notice_server_open`,
  `test_schedule_input_day_default`, `test_schedule_active_import`, `test_notice_maintenance_extensions`,
  `test_notice_maintenance_formats`. 개별 구성요소 검증 통과와 위 연결 문제는 동시에 성립한다.
- 실제 사용자 설정·스케줄·음성·실행 중인 프로세스는 변경하지 않았다. 빌드·배포·Git 게시도 하지 않았다.

## 개선 방향과 순서

1. 반복 정기점검 템플릿과 실제 한 번의 점검 회차를 구분한다.
   회차에는 종류, 시작, 종료 예정, 확인된 실제 오픈, 취소·완료 상태와 출처 식별자를 둔다.
   종료 예정 시각이 지났다는 이유만으로 완료를 추정하지 않는다.
2. 공지의 임시점검 시작·연장·완료·취소와 수동 입력이 같은 회차를 변경하도록 연결한다.
   같은 회차의 재수집은 중복 처리하지 않고, 다른 회차의 오픈으로 종료시키지 않는다.
3. 일반 보스 무효화와 반복 고정보스 표시 기준을 분리한다.
   고정보스에 가짜 생성 시각을 넣는 단기 패치보다, 점검 상태에 맞는 명시적 유효성 판단을 사용한다.
4. 예약어인 점검·서버오픈을 일반 보스보다 먼저 해석한다.
   지원하지 않는 `컷` 조합은 명확히 거절하거나 명시적으로 제어 입력으로 처리한다.
   지난 날짜는 날짜가 보이는 입력·미리보기로 확인한다.
5. 표시 판정은 데이터를 지우지 않게 하고, 자료 정리는 명시적인 재생성·초기화 작업의 범위와 백업으로 관리한다.
   기존 백업과 사용자가 의도한 점검 후 정리 정책을 보존하는 이행 방안이 필요하다.
6. 공통 판단 결과를 GUI·웹·디코·알람에서 재사용하고, 출력 기간과 UI 필터만 각 기능에서 적용한다.
   입력→점검→재오픈→고정보스 표시→재시작→다음 정기점검의 통합 회귀 검사를 먼저 만든다.

실행 파일과 공지 모듈의 호환성, 저장된 제어 기록의 이행, 웹 전송 캐시 무효화는 실제 수정 때 함께 다뤄야 한다.
현재 자료를 일괄 삭제하거나 과거 점검을 모두 자동 종료 처리하는 방식은 이행안으로 사용하지 않는다.
