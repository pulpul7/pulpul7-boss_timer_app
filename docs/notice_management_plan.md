# 공지 / 알림 관리: 확정 사항과 구현 상태

## 배포할 때 전달할 문구

> 같은 게임 서버에서는 한 클라이언트만 `이 클라이언트에서 자동 안내 송출`을 켜 주세요.
> 다른 PC는 오프라인 사용 또는 자동 안내 송출을 끈 상태로 사용해 주세요.
> 공지 수집은 각 클라이언트가 독립적으로 합니다. 다른 PC와 설정이나 읽은 기록을 동기화하지 않습니다.
> 현재 별도의 중복 접속·중복 송출 차단 기능은 없습니다.

현재 서버당 사용자 한 명을 전제로 한다. 중앙 송출 담당 선출, 접속 잠금, 클라이언트 간 통신은 이번 범위에 넣지 않는다.
위 안내는 알림 관리 창의 설정 탭에도 표시한다.

## 이번에 구현한 것

- `소요시간/점수` 왼쪽 `알림 관리` 버튼.
- 현재 서버별 수집 활성화, 수집 종류, 조회 시간표, 이 클라이언트 자동 안내 송출 설정 저장.
- 등록된 알림의 사용 체크, 제목, 유효 시작/종료(KST), 상태, 원문/참고 내용, 안내 문장, 출처, 행사 자체 기간 표시.
- 수동 알림 등록, 유효기간 수정, 개별 사용 해제, 알림 폐기.
- 기간 미확정 또는 시각 없이 날짜만 있는 데이터는 임의의 시각을 추정하여 송출하지 않는다.
- 종료·폐기 이력은 종료·폐기 시점부터 30일 보존. 개별/전체 이력 수동 삭제. 실행 중인 알림은 이력 삭제에 포함하지 않는다.
- 시작 시 및 실행 중 매시간 모든 로컬 서버 기록을 정리한다. 목록 조회/저장 시에도 만료와 이력 보관 기간을 검사한다.
- 전용 저장소 `notice_data/<서버ID SHA-256>.json`. 시즌별 스케줄 저장과 분리하여 같은 서버의 설정이 다음 시즌에도 유지된다.
- 서버가 전환되면 이전 서버 창에서 저장하지 못하게 한다. 알림 관리 버튼을 다시 누르면 현재 서버 창을 연다.
- 손상된 JSON은 초기화하거나 덮어쓰지 않고 오류로 표시한다. 프로세스 간 파일 잠금과 원자적 저장으로 로컬 기록을 보호한다.

**독립 모듈 실행 연결 완료:** 관리 화면과 기록 로직은 `notice_module/payload/`에 있다. 본체의 `notice_runtime.py`가 내장 또는 설치된 모듈을 로드하고 시작 실패 시 복구한다.

**수집 연결 완료:** 현재 선택 서버의 설정으로 공개 카페 상단 공지를 독립 워커에서 조회한다. `수집한 공지 / 원문` 탭에서 제목/작성일/본문/출처/수정 감지/실패를 확인한다.
`지금 공지 수집`은 시간표를 건너뛰는 일회 조회이며, 수집 꺼짐 설정을 무시하지 않는다.

**아직 연결하지 않은 것:** 본문 시간 추출, 반복/마감 알림 생성, Discord 명령/질문 버튼, TTS 큐·중지·재개.
수집 원문과 실행할 알림은 별도다. 수집이나 수동 등록만으로 음성을 송출하지 않는다.

기본값은 `수집 켜짐 / 이 클라이언트 송출 꺼짐`이다. 임의의 최초 송출을 방지하며, 사용자가 창에서 바꿀 수 있다.
`notice_data/`는 Git에서 제외하고 기존 배포 스크립트의 데이터 수집 대상에도 넣지 않았다.
수동 배포 때 이 폴더를 통째로 복사하면 해당 PC의 서버 설정까지 복사되므로 기본 배포에 포함하지 않는다.

## 수집 / 안내 분리

- 수집은 클라이언트별 독립 실행. 중앙 수집 서버나 다른 사용자의 로그인에 의존하지 않는다.
- 수집 중단은 신규 수집을 막는 설정이다. 이미 등록된 유효한 알림의 송출 중단과는 별개다.
- 전체 자동 안내 중단은 `이 클라이언트에서 자동 안내 송출` 체크 해제로 제어한다.
- 조회 시간표에 없는 시간은 조회하지 않는다. **조회 시간표가 음성 안내 시간을 제한하지 않는다.**
- 조회 규칙은 위에서부터 처음 일치하는 규칙을 사용한다. 기본값:
  - 매일 06:50~09:30: 15분
  - 수요일 09:30~11:00: 3분
  - 매일 09:30~24:00: 10분
- 점검 연장에 따른 동적 조회 모드는 3단계 본문 시간 추출과 함께 구현한다. 현재 기본/수정된 시간표에 따른 조회가 동작한다.
- 사용자 권한을 별도로 나누지 않는다. 사용자는 알림을 제어하고 알고리즘/기능 배포는 제작자가 관리한다.

## 모든 알림의 유효기간

- `valid_from <= 현재 시각 < valid_until`만 송출 가능하다. 시작과 종료 모두 확정돼야 한다.
- 원문 행사 기간(`event_from`, `event_until`)과 안내의 유효기간은 별도 저장한다.
- 예: 판매 전날 안내는 판매 시작 전까지, 구매 안내는 판매 종료 전까지.
- 시각이 불분명하면 내용은 보여주되 `기간 미확정 · 실행 보류`로 표시한다.
- 기한 경과 시 알림은 즉시 논리적으로 무효다. 파일 정리 시각과 무관하게 재생/재개 전에 다시 검사해야 한다.
- 만료된 이벤트는 이력으로 이동한다. 프로그램이 꺼져 있으면 다음 실행 때 정리하며, 오래전에 끝난 알림을 다시 재생하지 않는다.
- 폐기한 글의 상세 이력을 지워도 동일 공지가 재등록되지 않도록 최소한의 source 식별자만 공지 해제까지 별도로 보관한다. 상세 이력/본문은 30일 이후 삭제한다.
- 사용자가 직접 바꾼 기간과 꺼둔 체크는 재수집 때 덮어쓰지 않는다.

## 수집 모듈 / 음성 큐가 지켜야 할 계약

`notice_management.NoticeStore`를 서버 ID별로 생성한다. 콜백을 실행할 때 현재 UI 서버를 다시 참조하여 다른 서버 저장소로 바꾸지 않는다.

- `register(event, collected=True)`: 수집 결과 등록. `id`와 `source_key`는 공지 게시판/글 ID뿐 아니라 안내 종류·회차/판매 구간을 식별해야 한다.
  - 같은 글의 전날 예고/시작 안내/종료 1시간 전 안내는 서로 다른 유효기간을 가진 알림 인스턴스다.
  - 수집기가 정제한 제목/본문/시각/안내 문장을 저장한다. 댓글·조회수 등은 입력하지 않는다.
  - 아직 중요한 수정과 단순 수정의 분류/재안내 정책은 수집 모듈에 구현하지 않았다. 모든 원시 페이지 변경을 새 안내로 등록하면 안 된다.
- `delivery_token(id)`: 현재 송출 가능하면 `(server_id, id, revision, generation)` 반환, 아니면 `None`.
- 큐 등록뿐 아니라 **재생 직전과 일시정지 후 재개 직전에도 token이 여전히 같은지 검사**한다. 다르면 기존 대기/일시정지 음성을 폐기한다.
- 체크 해제·전체 설정 변경·기간 변경·본문 변경·만료·공지 해제는 이전 큐 항목이 그대로 재개되지 않도록 한다. 실제 큐 취소는 향후 음성 host에서 이 계약에 연결해야 한다.
- `complete_delivery(token)`: 실제 재생 성공 후에만 호출. 발견·다운로드·큐 삽입만으로 안내 완료 처리하지 않는다.
- `reconcile_sources(keys, successful=True)`: **전체 상단 공지 목록을 성공적으로 확인했을 때만** 호출. `keys`에는 최근 새 글뿐 아니라 현재 공지에 남아 있는 기존 알림 종류도 포함해야 한다.
  - 실패/부분 조회는 공지 해제로 간주하지 않는다.
  - 사용자 폐기 식별자는 공지에서 내려간 것이 확인된 뒤 해제한다.

파일 잠금은 같은 PC의 JSON 손상 방지용이며, Discord 접속이나 여러 PC의 송출을 조정하는 기능이 아니다.

## 앞으로 이어 붙일 안내 정책

- 알림은 보탐을 보조한다. 일괄 음성 시간 제한은 없애고 알림별 적절한 기회·유효기간을 둔다.
- 참여 독려는 여러 대상 전체 합계 두 번. 다가올 대상까지 30분 이하라면 독려하지 않는다.
- 이전권은 특별 안내로 참여 독려 횟수와 분리한다. 공식 본문의 판매 구간별로 시작·종료 1시간 전·10분 전을 등록한다.
- 마지막 판매일을 특히 챙긴다. 전날 주요 시간이나 7·8챕/절대자처럼 사람이 모이는 보스 안내 후 다음날 판매 시작 시각을 예고한다.
- 판매 당일 주요 보스 안내 뒤 구매 알림은 두 번을 넘을 수 있다. 고정 13시/고정 주 2회라고 가정하지 않고 매 공지의 실제 날짜·시간을 읽는다.
- 일반 공지/업데이트/점검 발견 안내는 반복 방송하지 않는다. 중요한 시간 변경은 별도 수정 안내로 처리한다.
- 클래스 변경권은 구매/획득과 사용기한을 구분한다. 이벤트 아이템도 드롭/교환/사용/삭제 기한을 구분한다.
- 큐는 기존 보스 차임벨·초읽기와의 우선순위, 일시정지·재개를 연결해야 한다. 이전권은 다른 일반 안내보다 먼저 처리하는 방향이며 실제 보스 초읽기를 끊는 동작은 넣지 않는다.
- `/공지`, 전문 읽기, 내용이 있는 질문만 버튼 표시, `/중지` 및 실패 시 음성 연결/볼륨 대응은 이후 음성/Discord 단계다.

## 비빌드 검증

`python -B -m unittest test_notice_management -v`

임시 폴더의 가짜 서버/이벤트로만 검사한다. 실제 스케줄·설정·음성·카페·디코에는 접근하지 않는다.
실제 알림 관리 창 모양과 클릭 동작은 사용자 환경에서 확인한다. EXE/ZIP 또는 테스트 배포 폴더는 생성하지 않는다.

## 실제 수집 구현 메모 (2단계)

- 조회 주소: https://m.cafe.daum.net/odin/CT9G (공식 카페의 공개 모바일 페이지).
- 실제 확인한 `noticeContainer` 내 `li.notice`만 읽는다. 일반 게시글 목록/하단 JavaScript의 중복 글은 읽거나 실행하지 않는다.
- 게시판 ID + 글 ID로 식별하므로 상단에 연결된 업데이트 게시판 `DEH7/275`도 별개 원문으로 정상 수집한다.
- 제목으로 계정보호, PC 런처 오류 도움말, 운영정책/약관 등을 제외한다.
- 목록용 원문은 오래된 작성일이어도 현재 공지에 있으면 유지한다. 최근 3일 전까지의 신규 안내 후보 여부(`recent`)는 별도 표시용 데이터로 보존한다. 아직 신규 음성 안내는 생성하지 않는다.
- 본문은 `#article.tx-content-container`만 읽는다. 댓글·조회수·스크립트·숨김·취소선 텍스트는 현재 안내용 본문에 포함하지 않는다. 표의 행/열 구분을 유지한다.
- 본문 이미지 주소만 기록하며 이미지 다운로드나 OCR은 하지 않는다. 이미지뿐인 글은 원문 확인 필요로 보류한다.
- 재조회 시 서버가 ETag/Last-Modified를 제공하면 조건부 요청을 사용한다. 본문/제목/이미지 주소 해시가 같으면 판본을 올리지 않는다. 목록 날짜만으로 본문 수정을 알아낼 수는 없어 대상 공지 본문은 조건부 재확인한다.
- 응답 누락, 구조 변경, 인증 페이지, 잘못된 링크, 응답 크기 초과는 실패로 처리한다. 빈 목록을 추측하지 않는다.
- 일부 본문 실패 시 기존 본문을 보존하고 그 주기의 공지 해제 판단을 유보한다. 확인된 빈 공지 목록만 실제 해제로 처리한다.
- 설정/서버 ID를 캡처한 워커가 해당 서버 저장소에만 결과를 쓴다. 늦게 도착한 이전 요청이 새 결과를 덮지 않도록 요청 token을 검사한다. 수집 도중 끄거나 모듈을 중지하면 결과를 적용하지 않는다.
- 프로그램을 껐다 켜도 마지막 조회 시각을 보존하므로 같은 주기 안의 자동 중복 조회를 줄인다. 실패도 같은 주기로 재시도하며 수동 확인은 가능하다.
- 수집 상태와 원문은 기존 서버별 JSON의 추가 키(`collection`, `articles`)에 보존한다. 이전 알림 설정/이벤트 형식은 변경하지 않는다. 이전 모듈은 추가 키를 무시하고 보존할 수 있다.
- 실제 검증: 7개 중 대상 4개, 본문 길이 각각 664/321/6467/6430자. 본문 저장 없이 읽기 전용 검증했다. 실제 날짜/판매 시각 해석과 유효기간 생성은 다음 단계다.

전체 비빌드 검증: `python -B -m unittest test_notice_collection test_notice_runtime test_notice_management test_ai_module_updater`
