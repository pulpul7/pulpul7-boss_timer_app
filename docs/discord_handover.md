# 봇 연결과 관리자 송출 권한

프로그램 시작 시 저장된 Discord 필수 설정이 완성되어 있으면 봇 Gateway만 연결한다.
음성채널 입장과 송출 권한은 프로그램 버튼 또는 관리자 명령으로 별도 요청한다.
설정, 스케줄, 차임벨, 음성 파일을 초기화하지 않는다.
GUI와 봇 모두 이번 소스로 교체해야 하며, 빌드와 실제 검증은 사용자가 진행한다.

관리자 연결·승계에는 안내채팅 채널을 공용으로 사용한다. 별도 승계 제어 ID 입력란은 없다.
모든 관리자 PC의 안내채팅 ID를 같은 채널로 설정하며, 비워두면 각 봇이 같은 서버의 `보탐매니저` 채널을 찾는다.
설정 변경 후 연결을 재사용할 때에도 저장된 안내채팅 ID를 봇에 전달한다. 승계 제어 메시지는 일반 안내 보관 개수·정리에서 제외한다.

## 관리자 접속 안내와 내부 통신 (2026-10-05)

- 예전 `관리자 연결·승계 알림`의 `BossTimer-Control-v3` JSON은 사용자 안내가 아니라 봇 사이의 변경 힌트·목록 조회 요청·응답이었다. `/보탐 관리자`에서 보인 두 박스는 조회 요청과 다른 봇의 응답이다.
- 내부 제어 데이터는 안내채팅 아래 `보탐매니저 내부 연결` 공개 스레드에서만 주고받는다. 안내채팅 ID는 계속 공용으로 사용하며 별도 ID 입력은 없다. 스레드는 기존 것을 재사용하고, 처음에만 자동으로 만든다.
- 봇에는 안내채팅 채널의 공개 스레드 만들기·스레드에서 메시지 보내기·메시지 기록 보기 권한이 필요하다. 내부 데이터는 알림을 억제하고 60초 후 삭제한다. 스레드 오류 때 일반 채팅으로 보내는 대체 경로는 없다. 공개 스레드 안에서는 내부 데이터를 확인할 수 있다.
- 관리자 목록 조회·접속 정보 등록·중간 승계 단계에는 일반 채팅 안내를 보내지 않는다. 구버전이 일반 채팅에 보낸 제어 메시지도 새 봇은 응답하지 않는다.
- 실제 승계 승인을 받고 접속 요청을 기록한 새 담당자만 `관리자 접속 시작`을 요청당 한 번 보낸다. 현재 연결 재확인·승계 거절에는 새 안내가 없다.
- 음성 입장·실행 세션·권한 세대 확인 뒤 같은 담당자가 `관리자 접속 완료`를 한 번 보낸다. 담당자, 관리자 ID, 시즌·서버, 음성채널, 권한과 스케줄 유지 정보를 보여주며 내부 JSON은 표시하지 않는다.
- 시작 안내는 60초 후 삭제한다. 완료 안내는 자동 삭제 시간을 지정하지 않고, 일반 안내 메시지 정리와 음성 패널 채널 정리에서도 제외한다.
- 시작·완료 안내는 기존 변경 알림 요청에 함께 실어 별도 비동기 작업에서 순서대로 보낸다. 안내 전송 실패가 승계 실패로 취급되거나 음성 입장을 기다리게 하지 않는다. 기존 GitHub SHA 충돌 검사·송출 종료 확인·자동 동기화 금지는 유지한다.
- `thread-v1` 통신 호환 정보를 확인해 예전 일반 채팅 방식의 봇을 재사용하지 않는다. 모든 관리자 PC의 GUI와 봇을 함께 교체하고 이전 프로세스는 종료해야 한다. 기록 스키마는 바꾸지 않는다.
- 실제 Discord 접속·승계 테스트와 빌드는 사용자가 수행한다. 수정 과정에서는 소스 구문과 변경 내용만 검증한다.

## 짧은 Gateway 단절과 음성 재입장 (2026-10-05)

02:58:00의 Gateway 단절은 02:58:01에 기존 세션 재개로 복구됐다. 이전 `on_disconnect`는 단절 즉시 `authority_needs_sync=True`, `authority_until=0`을 저장해 기존 음성 연결까지 종료했다. 그 결과 첫 음성 재입장이 15초 시간 초과되고 두 번째 시도에서 02:58:21에 입장했다. `lease_remaining_sec=-397309.453`은 유효기간 0에서 시스템 단조 시계 값을 뺀 결과이며 실제 장애 시간이 아니다. 기존 로그에는 최초 Gateway 단절의 종료 코드나 하트비트 진단이 없어 네트워크·Discord·PC 지연 중 원인은 확정할 수 없다.

- 기존 세션의 짧은 단절에는 마지막 검증된 권한 유효기간을 보존한다. Gateway가 끊겨 있는 동안 송출은 기존 `STATUS.online` 검사로 막고, GUI는 오프라인 상태에서 권한을 갱신하지 않는다.
- 10초 유효기간 초과·명시적인 권한 반납·권한 변경·새 실행 세션의 차단은 유지한다. 기존 세션의 `RESUMED` 이벤트가 만료된 권한을 부활시키지 않는다. 새 로그인 `READY`로 전환된 경우에는 기존처럼 담당자 재검증을 요구한다.
- `RESUMED`에서는 실제 음성 연결 상태를 다시 확인하며 최초 연결 시각은 유지한다. 기존 음성 연결이 살아 있으면 불필요한 퇴장·입장과 재접속 안내를 만들지 않는다. 실제 음성이 끊긴 경우 기존 재접속 감시가 처리한다.
- 단절 로그에 관측된 WebSocket 종료 코드, 하트비트 지연, 실제 음성 연결 상태, 권한 세대와 잔여 유효기간을 남긴다. SDK의 하트비트 응답 없음·이벤트 루프 지연 경고도 별도로 기록한다. SDK 원본 패킷·세션 ID·스택은 복사하지 않는다.
- 소스 구문과 변경 내용만 검증한다. 실제 접속·장시간 단절 테스트와 재빌드는 사용자가 수행한다.

03:39:36 이후 05:14:44까지 로그에는 03:58:05·04:22:52·05:14:44의 Gateway 재개가 3회 있다. 각각 0.468초 안에 복구됐으며 `voice_connected=1`, `generation=133`을 유지했다. 이 구간에는 음성 권한 종료·음성 재입장·프로세스 재시작이 없다. 이전 짧은 단절의 강제 음성 종료 수정은 적용돼 있다.

이때의 `close_code=4000`은 SDK가 재접속 요청·세션 재개 또는 수신 시간 초과를 처리하면서 자체적으로 닫는 기본 코드이기도 하므로 Discord 서버의 실제 오류 코드로 단정하지 않는다. `heartbeat_latency_sec=inf`도 소켓을 정리한 뒤 SDK의 하트비트 측정 객체가 없어져 나온 값일 수 있다. 현 로그만으로 최초 단절 원인을 특정할 수 없다.

후속 진단은 작은 Gateway 제어 패킷만 동기적으로 확인해 Discord 재접속 요청(opcode 7), 세션 무효화(opcode 9), 마지막 하트비트 응답 시각·실제 왕복 지연을 기록한다. 일반 메시지와 인증 패킷 원문은 기록하거나 다른 이벤트로 전달하지 않는다. 큰 패킷은 다시 파싱하지 않으며, 원본 이벤트마다 별도 작업을 만들지 않는다. 재접속 방식·송출 권한·음성 연결 절차는 바꾸지 않는다. 실행 중인 소스 봇에는 다시 실행한 뒤부터 이 추가 진단이 적용된다.

## 보탐로그 팝업의 연결 기록

짧은 Gateway 단절·정상 RESUMED, 관리자 세션·접속 목록·승계 변경 확인, 조회 조정과 일반 관리자 명령은 팝업 로그에 표시하지 않는다. 이 요청을 처리하는 동작과 내부 진단 로그는 유지한다. 팝업은 내부 확인 요청만으로 생성하지 않는다.

연결 관련 팝업 기록에는 실제 음성 자동 재접속, 장애에 따른 봇 재시작·복구, 자동 복구 실패를 남긴다. 연결 결과는 ‘복구 완료/복구 실패’로 표시한다. `connection_log`에는 실제 복구 종류를 구분하며 Gateway 진단 종류는 팝업에서 제외한다. 기존 봇의 종류 없는 `connection_log`는 기존 의미인 실제 음성 복구로 처리한다. 스케줄·초읽기·음성 요청 처리 내역과 Discord 채팅 안내는 변경하지 않는다. 이미 표시된 과거 기록이나 사용자 파일은 삭제하지 않는다.

## 통신 처리와 API 요청 최적화 (2026-10-05)

- Gateway는 discord.py의 세션 재개와 오류별 재시도를 먼저 사용한다. 복구 감시는 최초 Gateway 연결부터 시작하며 90초 동안 READY/RESUMED로 정상 복구되지 않을 때만 런타임을 재시작한다. 짧은 단절에서는 같은 Client와 세션을 재사용하고, 전체 런타임 재시작은 기존 공용 10회 제한을 따른다. 권한 확인의 10초 만료·음성 송출 보호·승계 검증은 늘리지 않는다.
- GUI는 상태 포트가 응답하고 자체 연결 제어가 동작하는 봇의 Gateway/음성 복구를 기다린다. 이때 기존 브리지 실패 누적·대기 하트비트를 초기화하여 GUI가 먼저 봇을 재시작하거나 복구 직후 오래된 실패 기록으로 다시 재시작하지 않게 한다. 상태 포트가 응답하지 않는 실제 프로세스 장애의 복구 감시는 유지한다.
- `Client.is_ready()`는 재개 도중에도 참일 수 있으므로 봇의 실제 online 상태도 함께 확인한다. 정상 확인 이벤트 전에 연결을 정상으로 간주하거나 단절 시각을 지우지 않는다.
- Discord 명령 정의는 한 봇 런타임에서 성공적으로 등록한 뒤 권한 세대가 바뀌었다는 이유만으로 재등록하지 않는다. 처음 등록과 실패 시 재시도는 유지한다.
- 개별 WAV/MP3 준비(파일 열기, 무음 제거, FFmpeg 시작)는 작업 스레드에서 처리한다. 준비 완료 후 권한 세대·취소 여부를 재검증하고, 취소/승계 중 늦게 완성된 소스는 재생하지 않고 정리한다. 초읽기 합성은 기존 작업 스레드 방식을 유지한다.
- 채팅 정리는 최근 100개 조회·회당 최대 20개 삭제·채널별 30초 병합을 사용한다. 기본 보관 수는 12개이며 기존 저장값·사용자 글·고정 글·진행 중인 보스 안내·관리자 접속 완료 기록을 보존한다. 범위 밖의 과거 글을 자동으로 전부 삭제하지 않는다.
- 사운드보드 채널의 정리 요청도 30초 동안 중복을 합친다. 채널 기록 조회는 기존 최근 80개 범위를 유지하고, 삭제 중 권한이 바뀌면 즉시 멈춘다.
- 평상시 1초 상태 확인은 localhost 통신이다. GitHub와 Discord 관리자 probe는 기존 이벤트/명령 경로를 유지하며 주기적인 외부 확인 요청을 추가하지 않는다.
- 현재 송출 담당자/캐시된 우선 담당자의 정상 조회는 기존 직접 응답 경로를 유지한다. 직접 응답 실패 후 여러 PC가 조회 담당자를 고르는 GitHub 대기 루프는 0.5초간 읽기 결과를 공유하여 동일 PC의 0.25초 반복 GET과 겹치는 조회를 줄인다. 3초 담당자 변경 기준은 유지하고, 쓰기는 매번 최신 기록·SHA를 읽으며 PUT 후 읽기 캐시를 비운다.
- SDK가 실제 HTTP 429 제한 경고를 내면 경로별/전체 제한 종류와 재시도 대기시간만 내부 봇 로그에 남긴다. 같은 종류의 반복 경고는 30초에 한 번 기록하고 URL·토큰·메시지 본문은 남기지 않는다. API 재시도는 SDK의 제한 대기 처리를 그대로 사용한다.

검증은 소스 구문과 변경 내용 확인만 수행한다. 실제 연결·승계·음성 타이밍·채팅 보관 확인과 빌드는 사용자가 진행한다.

## 버튼과 표시

- 디코 실행: 연결된 봇을 재사용하고, 연결이 끊겼으면 재연결한다.
- 현재 담당자가 없으면 권한을 얻고 저장된 음성채널로 입장한다.
- 다른 담당자가 있으면 부모 중앙 자체 팝업으로 승계를 묻는다. 아니오는 봇 연결만 유지한다.
- 디코 종료: 현재 담당자의 음성 연결과 권한만 종료한다. Gateway는 유지한다.
- 화면은 봇 연결됨·권한 없음 / 관리자·입장 중 / 관리자·송출 중 / 봇 연결 끊김을 구분한다.

## 연결·승계 진행창

디코 실행 버튼을 누르면 기존 설정·봇 상태 확인 전에 부모 중앙에 진행창을 그린다.
저장된 설정과 봇 확인 이후의 기존 버튼 동작은 동일하며, 새 대기시간을 두지 않는다.
승계받는 PC에는 봇 연결 확인 → 담당자 확인 → 필요한 경우 인계 대기 → 권한 획득 → 음성 입장을 표시한다.
현재 담당자 PC에는 송출 중단 → 스케줄 비교·업로드 성공/생략/실패 → 음성 연결 종료 확인 → 봇 대기를 표시한다.
원격 관리자 호출도 같은 진행창을 사용한다. 기존 확인창과 오류창의 동작은 유지한다.

표시는 기존 GUI 큐에 기다리지 않고 전달하며, 서버 권한 기록에 새 진행 단계를 쓰거나 조회하지 않는다.
음성 연결 종료 표시는 기존 5초 권한 확인에서 받은 상태로 판단한다. 화면 단계 확인을 위해 승계 처리를 늦추지 않는다.
상대 PC의 세부 업로드 진행을 새로 수집하지 않으며, 받는 PC는 기존 요청 상태와 업로드 결과만 표시한다.
완료 문구는 잠깐 표시한 뒤 창만 닫는다. 진행창을 닫아도 실제 작업은 취소하지 않고,
창은 입력 잠금·grab·wait_window를 사용하지 않는다. 지난 작업의 늦은 표시가 새 작업 창을 바꾸지 않도록 구분한다.

## 관리자 명령

Discord의 서버 관리자 또는 서버 관리 권한이 필요하다. 슬래시 명령에서 동작 입력란에 값을 넣는다.

- `/보탐 관리자`: 접속한 담당자의 이름, 설치별 ID, 게임 서버·시즌, 권한 상태를 표시한다.
- `/보탐 나츠`: 목록에 표시된 담당자 이름으로 해당 PC를 호출한다. 봇만 연결되고 권한이 없어도 처리한다.
- 같은 이름이 여러 명이면 호출을 중단하고 ID로 구분하도록 안내한다. `/보탐 a1b2c3d4` 또는 기존 `/보탐 관리자 a1b2c3d4`, `/보탐 관리자a1b2c3d4`도 허용한다.
- ID는 기본 8자리이며 충돌하면 길게 표시한다. 이름이나 시즌 변경으로 ID가 바뀌지 않는다.
- 원격 호출은 추가 확인 없이 승계한다. 호출자의 음성채널이 우선이며, 없으면 대상 PC의 저장된 채널을 사용한다.
- 대상 PC가 10초 안에 요청을 수락하지 않으면 기존 담당자의 권한을 변경하지 않는다.
- 같은 명령을 여러 PC가 수신해도 최초 Discord 응답에 성공한 PC만 처리한다.
- `/보탐 접속`, `/초대`, `/대기`는 현재 담당자의 접속·권한 반납 경로를 이용한다.

## 송출 권한 없는 조회

봇 Gateway만 연결돼 있어도 `/보탐`, `/보탐 ?`, `/보탐텍스트`, `/이미지`, `/음성`, `/음성목록`에 응답한다.
권한이 없는 PC는 요청자만 볼 수 있는 응답으로 자신의 로컬 자료를 제공하고 응답 PC의 관리자 ID를 표시한다.
조회는 송출 중인 담당자를 우선하고, 나머지는 실제 봇 접속 시각이 최근인 순서로 요청한다. 주기적인 상태 갱신은 접속 순서를 바꾸지 않는다.
담당자 목록과 유지 중인 조회 담당자는 기존 5초 권한 확인 때 로컬 연결 상태에 저장한다. 정상 조회는 이 정보로 응답 PC를 선택하며 GitHub 읽기·쓰기나 GUI 요청 처리를 기다리지 않는다.
송출 중인 PC는 대기 없이 접수하고 바로 자신의 스케줄을 응답한다. 권한이 없는 조회 담당자는 짧게 송출 담당자에게 우선 기회를 주고 접수한다.
나머지 PC는 Discord의 접수·응답 상태를 확인하여 중복 처리를 종료한다. 조회 담당자가 응답하지 않거나 캐시가 만료됐을 때만 공유 기록의 SHA 비교로 재시도한다.
`/보탐 관리자`도 유효한 로컬 목록이 있으면 바로 응답하며, 없을 때 기존 조회 경로를 사용한다. Discord 서버 관리 권한 검사는 유지한다.
선택한 PC의 처리 준비 응답이 3초 안에 없으면 다음 PC로 바꾸고, 이전·새 담당자 이름과 재시도 안내를 요청자에게 표시한다.
모든 후보가 응답하지 않으면 관리자를 변경하고 다시 시도하도록 안내한다. 이는 조회 담당자 선택이며 음성 송출 권한 승계가 아니다.
재시도로 바뀐 조회 담당자는 이후 명령에서도 유지한다. 새 PC가 접속해도 유지하며, 송출 중인 담당자가 있으면 그 담당자를 최우선으로 한다.
변경된 조회 담당자가 목록에서 빠지거나 실행 세션이 바뀌면 유지 기록을 해제하고, 남은 PC 중 가장 최근 봇 접속자부터 다시 선택한다.
동시에 진행된 이전 조회가 나중에 끝나도 새 조회 담당자 유지 기록을 덮어쓰지 못하도록 별도 세대를 확인한다.
이미지 생성처럼 오래 걸리는 작업은 처리 준비 응답 후 진행한다. 3초는 최종 이미지 생성 완료 제한이 아니다.
정상 조회는 최초 Discord 접수에 성공한 PC만 처리한다. 재시도 경로는 실행 세션·요청 번호·후보 순서·응답 기한을 비교해 늦은 PC의 중복 응답을 막는다.
도움말은 항상 개인 응답이며, 현재 담당자의 스케줄 채널 전송·음성 버튼 동작은 유지한다.
권한 없는 음성 목록은 이름만 표시하며 재생 버튼을 제공하지 않는다.
이미지 생성은 기존 로컬 스케쥴복사 경로를 이용하므로 클립보드도 기존과 같이 갱신된다.
권한 없는 조회는 권한 획득·스케줄 변경·공용 채널 안내·메시지 정리·자동 송출을 수행하지 않는다.
관리자 명령의 Discord 서버 관리 권한 검사와 스케줄 변경·음성 송출의 담당자 검사는 유지한다.

## 승계와 스케줄

권한은 Discord 서버마다 한 명이며 게임 서버·시즌 일치 여부는 승계를 막지 않는다.
기존 담당자는 송출을 중단하고 스케줄 스냅샷을 업로드한다. 업로드 성공·실패는 승계를 막지 않는다.
마스터·일반 관리자 모두 같은 업로드 함수를 사용한다. 승계 스케줄은 서버 파일의 실제 내용과 비교하며,
내용이 같고 보스설정도 갱신할 필요가 없으면 업로드하지 않는다. 버전 번호가 같아도 실제 내용이 다르면
새 버전으로 업로드한다. 업로드 완료·생략·실패 결과는 기존 담당자의 상태 표시와 권한 기록에 그대로 남긴다.
기존 담당자의 응답·업로드를 최대 10초 기다린 뒤 새 담당자에게 권한을 넘긴다.
새 담당자는 자신의 로컬 스케줄을 사용하며 다운로드·적용·자동 동기화를 하지 않는다.
음성 입장은 별도로 최대 30초 확인한다. 실패하면 봇 연결을 유지하고 권한만 반납한다.
이전 담당자는 자동 복귀하지 않는다. 스케줄 가져오기와 동기화는 사용자가 기존 메뉴로 진행한다.
기존의 일반 시작 시 누락 프로필을 채우는 동작은 승계와 별개이며 이번 변경 대상이 아니다.

## 저장소·세션

기존 GitHub 데이터 저장소의 `data/handover/<Discord 서버 ID 해시>.json`을 사용한다.
Contents 쓰기 권한이 필요하다. 새 저장소나 별도 서버를 만들지 않는다.
조회 조정은 같은 저장소의 `data/handover/<Discord 서버 ID 해시>_queries.json`을 사용하며 권한 기록과 분리한다.
정상 조회에는 조회 조정 파일을 읽거나 쓰지 않는다. 재시도로 조회 담당자가 바뀔 때만 권한 기록에 조회 담당자 정보·별도 세대를 함께 공유하며, 시작 시 기존 조회 담당자 기록을 한 번 반영한다.
조회 기록에는 요청 번호·담당자 표시 정보·실행 세션·후보 순서·유지할 조회 담당자와 변경 세대를 저장한다. Discord interaction 토큰·스케줄·음성 데이터는 업로드하지 않는다.
조회 기록은 최대 32개이며 120초 지난 기록은 다음 조회 생성 때 정리한다.
프로토콜 2 기록에는 설치 ID, 실행 세션, 권한 세대, 요청, 담당자 표시 정보와 접속 상태가 들어간다.
토큰·Windows 사용자 이름·PC 이름은 공유하지 않는다.
SHA 비교 변경으로 동시에 요청된 승계를 직렬화하며, 오래된 작업은 새 권한 기록을 덮어쓰지 못한다.
접속 정보는 20초마다 갱신하고 60초 동안 갱신되지 않은 담당자는 목록에서 제외한다.
권한은 5초마다 확인한다. 마지막 확인 후 10초가 지나면 음성 패킷·채팅 송출을 차단한다.
권한 저장소 장애는 봇 로그인을 종료하지 않지만 권한 취득·갱신은 막는다.
음성 재시도와 Gateway 재시도는 별도 10회 제한으로 관리한다.
권한 상태 파일은 Windows에서 읽는 동안에도 원자적 교체를 허용한다. 일시적인 상태 포트 무응답은 기존 권한 유효기간 안에서 기다린다.
음성 연결의 시간 초과·취소 때 연결 객체와 등록 정보를 정리한다. 음성 재시도 한도에 도달하면 오류를 표시하고 권한을 반납하며 Gateway는 유지한다.
기존 프로세스는 관리자 ID·설정 경로·Application ID·Discord 서버·프로토콜이 일치할 때만 재사용한다.
구버전 연결이 모두 종료된 뒤, 남은 구버전 담당 기록은 디코 실행 버튼의 첫 확인으로 전환한다.
담당자 ID 파일을 다른 PC에 복사하지 않는다. 서로 다른 PC는 각자 고유한 ID를 사용한다.

## 사용자 수동 확인

1. 시작 직후 음성 입장 없이 봇만 연결되는지 확인한다.
2. 담당자 없음, 승계 예·아니오, 권한 반납, 연결 끊김 후 재연결을 확인한다.
3. 업로드 실패·지연, 기존 담당자 무응답에도 새 담당자가 입장하며 양쪽 Gateway가 유지되는지 확인한다.
4. 새 담당자의 로컬 스케줄·음성 설정이 변하지 않는지, 음성 입장 실패 시 권한만 반납하는지 확인한다.
5. 담당자가 없을 때 관리자 목록, `/보탐 나츠` 이름 호출·중복 이름 안내·ID 호출, 호출자 채널 우선·대상 기본 채널을 확인한다.
6. 일반 사용자의 관리자 명령 거절, 동시 요청과 명령 중복 응답 방지를 확인한다.
7. 권한 저장소 연결을 끊었을 때 10초 뒤 송출이 중단되고, 복구 시 현재 담당자만 재접속하는지 확인한다.
8. 이전 PC의 늦은 종료·재연결이 새 담당자의 음성 세션을 끊지 않는지 확인한다.
9. 음성 연결이 시간 초과되거나 취소된 뒤 다시 실행할 때 `Already connected to a voice channel`이 반복되지 않는지, 재시도 한도 후 오류 표시와 권한 반납을 확인한다.
10. 조회가 송출 중인 PC를 우선하는지, 모두 권한이 없으면 마지막 봇 접속 PC를 선택하는지 확인한다. 상태 갱신만으로 순서가 바뀌지 않아야 한다.
11. 첫 조회 담당자가 무응답일 때 3초 응답 기한 후 다음 담당자로 재요청하고 안내하는지, 모든 후보가 실패하면 관리자 변경·재시도 안내가 나오는지 확인한다.
12. 재시도 뒤 이전 PC의 늦은 응답이 중복 표시되지 않는지, 조회 담당자 변경으로 송출 권한이나 로컬 스케줄이 바뀌지 않는지 확인한다.
13. 재시도로 변경된 조회 담당자가 다음 명령에도 유지되는지, 송출 중인 담당자가 있으면 우선하는지, 유지 중인 PC가 끊기면 다시 선택하는지 확인한다.
14. 정상 `/보탐`·`/보탐텍스트`·`/음성목록` 조회 때 로그에 `query_direct`가 나오고 관리자 요청 파일이나 GitHub 조회 조정 쓰기가 생기지 않는지 확인한다.
