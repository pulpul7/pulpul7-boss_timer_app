## 결론과 확실성

## 권한 만료를 만드는 구조

1. `discord_connection_policy.py:12`의 `AUTHORITY_SECONDS = 10`으로 권한 유효시간을 정한다.
2. `discord_authority.py:15`의 `POLL_SECONDS = 5` 간격으로 확인을 예약한다.
3. 예약은 GUI의 `root.after`에서 시작되며, 실제 GitHub 요청은 별도 작업 스레드에서 수행한다. GUI가 오래 바쁘면 다음 작업 스레드의 시작도 늦어진다.
4. `discord_authority.py:371`에서 관리자 작업 잠금 아래 조회를 시작한다. `checked_at`은 GitHub 조회를 시작하기 전에 기록한다.
5. `discord_authority.py:304`는 성공 응답 처리 시각이 아니라 **조회 시작 시각 + 10초**로 로컬 권한을 저장한다. 오래된 응답이 권한을 부당하게 연장하지 않도록 하는 장치지만 응답 지연만큼 실제 남은 시간도 줄어든다.
6. `discord_authority.py:289`에서 로컬 상태 포트 조회 결과에 runtime ID가 없으면 갱신을 생략한다. 기존 권한을 즉시 취소하지는 않지만 원래 만료시각도 연장하지 않는다.
7. `discord_authority.py:385`의 접속 목록 갱신은 같은 관리자 잠금을 잡은 채 GitHub 재조회·쓰기를 수행한다. 이 쓰기가 느리면 다음 권한 확인이 밀릴 수 있다.
8. 접속 목록을 쓴 뒤 `discord_authority.py:387`에서 다시 관찰하더라도 **처음 기록한 checked_at을 그대로 사용**한다. 목록 쓰기에 걸린 시간은 새 유효시간이 되지 않는다.
9. `boss_timer_discord_bot.py:1386`의 감시 루프가 만료를 확인하면 재생·작업 큐를 중단하고 로컬 음성 연결을 정리한다. `:1339`의 패킷 송출 검사도 권한이 만료되면 패킷을 보내지 않는다.

## 첫 재접속이 늦어진 부분

권한 만료 시에는 이미 권한이 바뀐 다른 PC의 음성 연결을 끊지 않도록 `guarded_disconnect`가 서버에 보내는 퇴장 요청을 막을 수 있다. 이 경우 로컬 소켓은 정리되지만 Discord 쪽 이전 음성 상태는 남을 가능성이 있다.

권한이 곧바로 같은 세대에서 복구되면 일반 재접속 경로가 다시 입장을 요청한다. 이 경로는 초기 권한 입장 경로처럼 `_disconnect_stale_configured_voice_session`을 먼저 실행하지 않는다. 라이브러리는 입장 후 음성 상태/서버 정보를 받아 handshake를 완료해야 한다. 이전 서버측 상태와 새 로컬 상태가 맞지 않으면 여기서 대기가 길어질 가능성이 있다.

이번의 ‘첫 시도 시간 초과, 같은 세대 두 번째 성공’은 이 구조와 양립한다. 그러나 네트워크 지연이나 Discord 음성 서버의 응답 지연도 같은 기록을 만들 수 있다. **첫 실패를 잔존 세션 문제로 확정하지 않는다.** 실제 대기는 연결의 10~12초 제한 외에 취소·정리 시간도 포함하므로 로그상 약 15초가 소요된 것과 모순되지 않는다.

## 다른 폴더 시험에서 반드시 구분할 것

- 같은 Windows 사용자로 실행하면 폴더가 달라도 `%APPDATA%\BossTimer`를 공유한다.
- 동일 시즌·게임서버 프로필이면 `discord_bot.ini.connection.json`과 관리자 ID도 공유한다.
- 상태 포트는 기본 18765 하나이며 음성 전달 큐도 공통 경로다. 다른 게임서버 프로필이라고 포트/큐까지 자동 분리되는 것은 아니다.
- 같은 프로필·관리자·Discord 설정의 상태 응답은 GUI가 재사용할 수 있어 다른 폴더의 봇에 붙을 수 있다. 출처 폴더 자체를 상태 일치 조건으로 검사하지 않는다.
- 현재 코드의 단일 포트 배타 바인딩은 두 번째 봇의 Discord 로그인 전에 중복을 막는다. 이것이 다른 GUI의 공유 상태 갱신/반납/종료까지 모두 격리하는 것은 아니다.
- 다른 PC라면 로컬 AppData/포트는 별개지만 같은 Discord 서버의 원격 관리자 권한 기록은 공유한다. 같은 토큰과 같은 guild에서 구버전이 살아 있으면 새로운 권한 보호와 별개로 간섭할 수 있다.
- 현재 파일을 그대로 보존하며 조사했다. 별도 시험 배포 폴더, EXE, ZIP은 생성하지 않았다.

## 개선 우선순위

1. **배포본에서도 남는 최소 연결 진단 로그**를 먼저 갖춰야 한다. 권한 조회 시작/완료 시간, 마지막 성공 갱신 시각, 남은 유효시간, 상태 조회 실패, 관리자 잠금 대기, GitHub 응답 코드/실패 사유, 이벤트 루프·Tk 지연을 기록한다. 토큰·인증 헤더는 기록하지 않는다. 권한 만료가 왜 발생했는지 현재 누락된 증거를 확보하는 목적이다.
2. **권한 확인 시작을 Tk 처리 지연에서 분리**하고, 권한 확인이 접속 목록 쓰기/승계 보조 작업에 장시간 막히지 않도록 작업·잠금 범위를 검토한다. 짧은 유효시간 안에 재시도할 기회를 확보해야 한다.
3. **조회 실패 후 다음 정규 5초 확인만 기다리는 구조를 검토**한다. 단, 무조건 빠른 재시도는 GitHub API 제한을 더 악화시킬 수 있다. 제한 응답과 일시적 네트워크 오류를 구별해야 한다.
4. **동일 소유자·동일 runtime·동일 세대로 돌아온 재접속의 세션 정리**를 검토한다. 다른 관리자의 연결을 퇴장시키는 기존 문제를 재발시키지 않는 소유권 검증이 전제다.
5. **권한 유효시간만 무작정 늘리는 수정은 피한다.** 기존 관리자에서 새 관리자로 넘기는 대기시간도 10초여서, 기존 PC가 더 오래 송출하면 중복 송출이나 세션 간섭이 생길 수 있다. 권한 갱신·handover·패킷 보호를 함께 검증해야 한다.
6. **폴더별 실행 출처 식별/경합 진단과 실제 내장 버전 표시**를 보강하면 시험 결과를 구분하기 쉽다. AppData 격리 방식 변경은 기존 설정·서버 스케줄을 보존하는 별도 설계가 필요하다.

정상 간격만 가정하면 PC 하나는 권한 조회 약 720회/시간, 접속 목록 갱신을 위한 추가 조회·쓰기 각각 약 180회/시간을 수행할 수 있다. 접속 PC와 공유 토큰, 다른 자동 동기화 작업이 늘어나면 API 사용량도 합산된다. GitHub 공식 문서는 인증 방식별 기본 제한 외에 콘텐츠 생성에 일반적으로 시간당 500회 등의 보조 제한도 설명한다. 이는 위험 계산이며 **이번에 제한에 걸렸다는 증거는 아니다**.

## 비빌드 검증 결과와 한계

- 실제 배포 로그에서 사용자 시각과 일치하는 사건을 찾고 현재 읽기 전용 상태 조회와 대조했다.
- 권한 관리 모듈을 EXE에서 메모리로 읽어 현재 소스와 실행 코드 일치를 확인했다.
- 실제 권한 갱신 메서드와 GUI 상태 감시 메서드를 사용한 **메모리 검증 11건 통과**: 정상 유효시간, 응답 지연으로 줄어드는 시간, 접속 목록 쓰기 후 이전 기준시각 재사용, 상태 조회 실패 시 갱신 생략, 만료 뒤 같은 소유자의 갱신, 다른 runtime의 권한 차단, 상태 실패 3회 복구 요청, 응답 중인 봇의 음성 재접속 존중, 대기 상태 복구 억제, heartbeat 실패 2회 복구 요청, 큐 offset으로 호환 ack 인정.
- 가짜 시계/상태/복구 메서드로 확인했다. 실제 사용자 설정 쓰기, 파일 복사, 새 디렉터리 생성, Discord 로그인, 실제 음성 연결 끊기, 빌드는 수행하지 않았다.
- 상세 GUI 로그가 비활성인 배포본이라 19:06:47 이전 GitHub 요청/로컬 HTTP/GUI 지연 중 무엇이 늦었는지는 현재 자료로 구별할 수 없다.
- 네트워크 장애를 의도적으로 발생시키거나 실행 중인 봇을 재시작해 재현하지 않았다. 다른 장소의 PC 상태와 네트워크는 직접 관찰하지 않았다.
- 동작 소스·기존 배포·설정·스케줄·음성은 수정하지 않았다. 이 조사 문서만 추가했다.

## 추가 조사: 19:28 재접속

사용자가 추가로 알려준 19:28 재접속은 **19:07 권한 만료 사건과 구분해야 한다**. 공통 봇 로그 4143~4151에서 다음 기록을 확인했다.

| 시각 | 기록 | 의미 |
|---|---|---|
| 19:27:53 | `voice_reconnect_watchdog_attempt generation=120 attempt=1/10` | 음성 연결이 비정상임을 감시 루프가 감지하고 첫 복구 시도 |
| 19:28:03 | `WSServerHandshakeError`, HTTP `525` | `wss://japan13020.discord.media/?v=8`에 WebSocket 연결을 요청했으나 Cloudflare의 오류 응답을 받음 |
| 19:28:05 | `attempt=2/10` | 두 번째 시도 |

| 19:28:31 | `voice_reconnect_text_notice_sent` | 복구 안내 게시 |

첫 실패 응답에는 `Server: cloudflare`, `CF-RAY: a4537f287cf3c8ca-ICN`, HTTP Date `2026-10-04 10:28:00 GMT`가 기록되어 있다. 인증 토큰/음성 세션 토큰을 문서에 옮기지 않았다.

Cloudflare 공식 문서에서 525는 **Cloudflare와 원본 서버 사이의 TLS handshake 실패**를 의미한다. 따라서 이 재접속 실패에는 Discord 음성 endpoint 측 또는 Cloudflare에서 해당 endpoint로 이어지는 구간의 장애를 의심할 구체적인 근거가 있다. 이 오류를 이 PC의 GitHub 인증서 오류, 봇 토큰 오입력, 음성 송출 권한 누락으로 해석해서는 안 된다.

그러나 525는 **첫 재접속 실패의 원인**이다. 19:27:53보다 앞선 최초 음성 연결 종료의 WebSocket close code나 오류는 공통 로그에 없어 최초 끊김까지 같은 장애로 확정할 수는 없다. 이 구간에는 `lease_expired`, `voice_authority_stopped`, `discord_disconnected`, 프로세스 재시작 기록이 없다.

### 다른 관리자가 별도 봇을 사용하는 경우

- 봇 토큰/Application ID가 다르면 ‘동일 프로그램의 동일 연결 조건’ 비교가 아니다. Discord 서버·음성채널·할당 endpoint·PC 접속 경로를 함께 비교해야 한다.
- 봇이 다르다는 사실만으로 반드시 다른 endpoint를 사용한다고 단정할 수는 없다. 특히 같은 서버의 같은 음성채널에서 사용하는지 구분해야 한다. Discord는 음성 연결에 사용할 endpoint를 Voice Server Update로 제공한다.
- **우선 의심:** 문제 채널에 할당된 `japan13020.discord.media` 및 해당 Cloudflare→음성 서버 구간의 일시적 장애.
- **추가 확인 대상:** 문제 채널의 음성 지역 설정, 다른 관리자의 실제 채널/endpoint, 같은 봇 토큰을 사용하는 다른 PC/구버전 프로그램이 있는지.
- **현재 근거가 약한 후보:** 토큰·Application ID 불일치, 잘못된 서버/채널 ID, 필수 채널 접근 권한 누락. 이번 기록은 이 설정을 바꾸지 않고 같은 채널로 세 번째 연결에 성공했으며, 현재 코드의 Application ID 일치 검사도 별도로 존재한다. 동적으로 권한이 바뀌었을 가능성까지 완전히 배제하는 것은 아니다.
- **프로그램 개선 대상:** 일반 음성 연결에 `reconnect=False`를 지정하고 자체 감시 루프가 다시 연결한다. 이는 525 자체를 만드는 근거는 아니지만, 끊긴 세션의 복구 방식과 시간에 영향을 주므로 기존 소유권 보호와 함께 검토할 항목이다.
- 라이브러리의 연결 종료 이유/heartbeat 진단이 공통 봇 로그에 충분히 수집되지 않는다. 다음 발생 시 최초 끊김까지 구분하려면 음성 endpoint·close code·마지막 정상 응답·재접속 단계별 실패 정보를 남겨야 한다.

이번 추가 조사에서도 실행 중인 봇/채널 설정을 변경하거나 강제 재접속하지 않았고 빌드하지 않았다.
