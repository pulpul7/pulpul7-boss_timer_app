# GitHub 확인과 Discord 송출 분리 — 2026-10-04

소스 수정과 비빌드 검증 기록입니다. 실행 파일·ZIP·테스트 배포 폴더는 생성하지 않았고, 실행 중인 배포본과 사용자 설정·스케줄·음성 파일은 변경하지 않았습니다. 작업 시작 전에 변경되어 있던 `build_metadata.json`도 수정하지 않았습니다.

## 원인과 변경 결과

19:06:47의 `voice_authority_stopped reason=lease_expired`는 Discord의 봇 권한 만료가 아니라 프로그램의 10초 송출 승인 시간이 만료된 것입니다. 기존 GUI는 GitHub 조회 성공 때 승인을 갱신했습니다. 조회 지연·실패뿐 아니라 GitHub 작업과의 잠금 경합으로 갱신이 늦어져도 정상 송출이 중단될 수 있었습니다. 제공된 로그에는 당시 GitHub 오류 자체가 없으므로 어느 요청이 지연됐는지는 확정하지 않습니다.

19:28의 Discord 음성 WebSocket 525·TimeoutError는 별도 연결 오류입니다. 이번 변경으로 Discord 음성 서버나 네트워크 오류까지 제거되지는 않습니다. 당시 조사와 수정 전 구현은 [연결 중단 조사](discord_disconnect_investigation_2026-10-04.md)에 기록했습니다.

현재 구현은 GitHub를 담당자 변경의 영구 기록과 자료 업로드에만 사용합니다. 정상 송출 유지용 GitHub 주기 GET·PUT과 접속 목록 heartbeat PUT을 제거했습니다. Discord 승계 제어 채널의 이벤트는 변경 사실을 알리고, 실제 담당자 변경은 그때 GitHub의 최신 기록과 SHA를 검증합니다. 이벤트 자체가 송출 권한을 부여하지 않습니다.

| 상황 | GitHub 사용 | 기존 정상 송출 |
|---|---|---|
| 접속·설정·승계·조회 명령이 없는 정상 대기 | 송출 유지 목적 GET·PUT 없음 | 로컬 승인 유지 |
| 실제 봇 접속·Gateway 복구·담당자 이름 변경 | 현재 기록 확인, 실제 바뀐 접속 정보만 저장 | 세션에 맞춰 검증 |
| 업로드 요청 | 최신 버전·SHA·실제 내용 확인, 바뀐 자료만 저장 | 업로드 실패와 분리 |
| 관리자 목록·담당자 호출 | 요청 때 기록 조회와 Discord 응답 확인 | 조회 실패로 송출 중단하지 않음 |
| 승계 | 요청·종료 확인·새 담당 기록 저장; 진행 중에만 조회 | 실제 승계 요청으로만 종료 |
| GitHub 변경 알림 처리 실패 | 오류 안내; 사용자 선택 시 최신 상태부터 재검증 | 검증된 기존 승인을 취소하지 않음 |

기존 읽기 명령의 응답 담당자 failover도 명령이 발생했을 때만 GitHub를 사용합니다. 전체 앱의 모든 GitHub 요청을 없애거나 자료 동기화 기능 자체를 변경한 것은 아닙니다.

## 승계와 실패 처리

1. 새 관리자의 실제 봇 실행 세션, 공통 제어 채널, 현재 GitHub 담당 기록을 확인합니다. Discord 응답을 통해 실제 접속 관리자와 송출·입장 중인 봇을 확인합니다.
2. 승계 요청을 기록하고 이벤트를 보냅니다. 기존 담당은 자신의 요청 ID·실행 세션·세대가 일치하는 경우에만 송출을 중단합니다.
3. 기존 봇이 음성채널에서 실제로 나간 것을 Discord 상태로 확인한 뒤 종료 확인을 기록합니다. 업로드는 이 확인 뒤 별도 작업으로 실행하며 새 담당의 입장을 기다리게 하지 않습니다.
4. 새 담당은 요청과 이전 담당의 종료 증거가 모두 일치할 때만 입장합니다. 대기시간이 끝났다는 이유로 권한을 강제로 가져오지 않습니다.
5. 입장 또는 승계가 실패하면 가능한 범위에서 취소·반납을 기록하고 양쪽에 결과를 알립니다. 새 담당의 입장이 실패해 담당자가 비면 기존 담당에게도 재접속 선택을 표시합니다.
6. 실패 팝업에서 재시도를 선택하면 만료된 요청을 재사용하지 않고 현재 연결·담당자·자료 버전을 다시 확인하는 새 작업을 시작합니다. 재시도 안내는 연속 2회까지이며 그 뒤에는 설정 확인 후 새로 실행하도록 안내합니다. 원격 Discord 요청의 실패는 요청자에게 결과로 응답합니다.

이전 담당이 응답하지 않으면 시간 경과만으로 승계하지 않습니다. 이전 봇의 음성 입장 부재를 확인하고, GUI에서 이전 PC의 프로그램과 봇이 완전히 종료됐다는 사용자 확인을 받아야 합니다. 같은 PC의 자동 복구는 이전 프로세스 종료를 실제 확인한 세션과 동일한 담당 기록에 한해서 처리합니다.

GitHub 통신이 완전히 불가능하면 취소·반납 기록도 실패할 수 있습니다. 이때 성공으로 표시하지 않으며 로컬 상태를 임의로 새 담당에게 넘기지 않습니다. 후속 요청은 현재 기록과 실제 봇 상태를 다시 검증합니다. 작업 중간 실패에는 잠시 송출 담당자가 없는 상태가 생길 수 있습니다.

## 업로드와 API 제한

- 스케줄·보스 자료의 실제 내용이 같으면 파일 PUT을 생략합니다. 서버 목록도 변경이 없으면 저장하지 않습니다.
- 파일 저장 뒤 목록 갱신만 실패했다면, 재시도 시 파일 버전과 내용이 동일한 경우 목록 갱신만 마칩니다. 다른 관리자가 올린 최신 자료는 버전·SHA 검증으로 보호합니다.
- 변경이 없는 담당자 기록·조회 담당 기록도 PUT하지 않습니다.
- 403의 제한 응답과 429는 `Retry-After`·`X-RateLimit-Reset` 등을 반영해 해당 토큰 요청을 보류합니다. 제한 동안 즉시 재시도하거나 무인증 읽기로 우회하지 않습니다.
- GitHub 토큰·권한·자료 검증 오류는 실패 내용을 알리고 사용자 선택에 따라 재검증합니다. 이 오류가 정상 송출의 로컬 승인 갱신 경로로 들어가지 않습니다.
- API 제한 보류 상태는 프로세스 메모리에만 저장됩니다. 다른 PC·프로세스의 계정 전체 사용량까지 조정하지는 않습니다.

GitHub 제한 근거: [공식 REST API 제한 문서](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api).

## 적용 전에 필요한 설정

이 변경은 GUI와 봇을 모두 갱신해야 합니다. 구버전과 함께 운용할 수 없으므로 모든 관리자의 구버전 프로그램·봇을 종료한 뒤 교체해야 합니다. 기존 protocol 1·2 담당 기록은 GUI에서 전체 구버전 종료 확인을 받은 뒤 protocol 3으로 전환합니다. 해당 전환은 담당 기록만 대상으로 하며 설정·스케줄은 보존합니다.

모든 관리자는 같은 Discord 서버, 같은 GitHub 저장소·브랜치의 담당 기록, 같은 **안내채팅 채널**을 사용해야 합니다. 2026-10-05 수정에서 별도 승계 제어 ID 입력란을 제거하고 안내채팅 ID를 공용으로 사용합니다. 내부 `authority_control_channel_id`는 안내채팅 ID에 맞추어 저장하며 예전 별도 ID는 채널 선택에 사용하지 않습니다. 안내채팅 ID를 비우면 기존과 같이 서버의 `보탐매니저` 텍스트 채널을 찾습니다. 채널을 자동 생성하지 않습니다. 각 봇에 채널 보기·메시지 보내기·링크 첨부 권한이 필요합니다.

이미 로그인한 봇을 재사용할 때에는 인증된 로컬 승계 요청으로 현재 저장된 안내채팅 ID를 전달합니다. 설정을 파일에 저장해도 봇 메모리에는 시작 시 설정이 남아 별도 제어 ID가 비었다고 오류가 나던 경로를 수정했습니다. 실제 탐색된 채널 ID로 담당 기록을 비교하므로 자동 탐색에서도 빈 값과 실제 ID를 비교하지 않습니다. 담당자가 없는 idle 기록만 채널을 변경할 수 있으며 운영 중인 다른 담당자의 채널 기록을 임의로 바꾸지 않습니다.

각 봇의 Developer Portal에서 **Message Content Intent**를 활성화해야 합니다. 다른 봇의 제어 embed를 수신하는 데 필요합니다. 서로 다른 Discord Application과 실제 봇 사용자 ID를 구분해 처리하며, slash command 응답 담당자는 해당 Application 내에서 선택합니다. 안내채팅 채널에는 기존 안내와 함께 승계 제어 메시지가 표시됩니다. 제어 메시지에는 요청·세션 식별자와 연결 메타데이터만 보내고 토큰·스케줄 내용은 보내지 않습니다. 이벤트 메시지는 60초 후 자동 삭제를 요청합니다. 보탐 메시지 보관 개수에는 포함하지 않으며 보관 정리로 삭제하지 않습니다.

Intent 근거: [공식 Gateway 문서](https://docs.discord.com/developers/events/gateway).

안내채팅 채널이 없거나 권한·Intent가 잘못됐으면 승계 전 오류를 표시합니다. 명시한 채널 ID가 잘못된 경우에는 다른 채널로 자동 대체하지 않습니다. 이 작업에서 실제 채널이나 사용자 설정은 변경하지 않았습니다. 빌드·배포 교체는 사용자가 수동으로 진행합니다.

## 로컬 승인과 검증 범위

남아 있는 1초 확인은 localhost 상태 확인과 로컬 연결 상태 파일 갱신입니다. GitHub 요청이나 주기 Discord 메시지가 아닙니다. GitHub 작업 잠금을 획득하지 않는 별도 스레드에서 실행합니다. 10초 유효시간은 이제 이 PC의 GUI·봇 제어가 살아 있는지 확인하는 용도입니다. GUI 종료·로컬 상태 파일 오류·봇 세션 변경·Gateway 단절은 별도의 연결 문제로 처리합니다. 이 보호를 제거해 GUI가 사라진 봇이 무기한 송출하지 않게 하지는 않았습니다.

메모리 저장소·모의 localhost/Discord로 검증했습니다. 실제 GitHub 쓰기·Discord 접속·음성 재생은 수행하지 않았습니다.

- 구조 변경 테스트 46개: 정상 1시간 유지의 GitHub GET·PUT 0회, GitHub 잠금 경합 중 로컬 승인 유지, 세션 변경·로컬 만료, 종료 확인 없거나 오래된 승계 거부, 이전 프로세스 복구, 공통 채널·Intent·봇 ID 검증, 사용자 재시도와 제한 대기.
- 두 관리자 통합 검증: 업로드 지연·실패와 새 담당 송출 분리, 종료 증거 없으면 입장 금지, 공유 기록 유실 시 이중 송출 방지, 새 봇 입장 실패 시 반납·기존 담당 안내, 취소된 승계의 기존 담당 재개, 입장 직후 GitHub 저장 실패 시 실패한 로컬 송출부터 종료.
- GitHub 쓰기·스케줄 안전 테스트 42개: 중복 PUT 생략, 충돌·버전 보호, 부분 업로드 재시도, API 제한 보류.
- 기존 연결·서버 분리·채널·음성 출력 관련 95개도 실행했습니다. 실패 15개·오류 28개는 수정 전 HEAD 소스를 메모리에서 실행했을 때와 테스트 ID 및 최종 오류 내용이 모두 일치했습니다. 오래된 테스트의 모의 봇에 `connection_policy`가 없거나 현행 대기·명령 동작을 반영하지 못하는 문제 등이 있습니다. 기존 preflight·패치노트 테스트의 수정 전 실패도 초기 효율 개선 기록에 기재했습니다.

실제 두 PC와 실제 Discord 서버에서의 동시 운용은 아직 검증하지 않았습니다. 소스 테스트 통과를 실서버 배포 검증으로 표현하지 않습니다.
