# 공지 모듈 작업 순서

사용자 요청: 순서는 에이전트가 관리한다. 준비된 계획에 따라 단계별 구현/검증 후 이어간다.
EXE/ZIP 빌드, 배포 복사, GitHub 게시, 실제 디코 송출은 별도 지시 전 실행하지 않는다.
설정/스케줄/음성/사용자 변경을 보존한다.

1. **소스 구현/비빌드 검증 완료 — 독립 모듈 실행과 업데이트 연결**
   - 관리 화면/기록 로직을 업데이트 payload로 이동.
   - 본체에는 버튼, 업데이트 설치기, 최소 host 연결만 유지.
   - 다운로드 모듈 로드, 시작 검증, 실패 시 이전/내장 버전 복구.
   - 이전 실패 버전 자동 재설치 반복 방지, 수동 재시도 유지.
   - 수동 패키징 방법 준비. 실제 ZIP은 생성하지 않음.
   - `notice_runtime.py` → `notice_module/payload/main.py` 동적 로딩. 설정 데이터는 기존 `notice_data/` 보존.
   - 검증: 65개 중 64개 통과, Tcl 문제로 실제 화면 1개 건너뜀.
   - 실제 EXE/실제 GitHub Release 적용 검증은 6단계 사용자 테스트에 남겨둠.
2. **소스 구현/읽기 전용 실측 완료 — 실제 공지 수집**
   - 카페의 실제 응답 확인 → 고정 공지 식별 → 출처/제목/본문/수정 비교.
   - 클라이언트 독립 수집, 서버별 설정/조회 시간표 연결.
   - 오류/부분 조회를 공지 해제로 처리하지 않음.
   - `cafe_source.py` 공개 모바일 HTML 파서 / `notice_collector.py` 워커 연결.
   - 관리 창에 `수집한 공지 / 원문`, `지금 공지 수집` 추가.
   - 실측: 상단 7개, 상시 제외 3개, 대상 4개 본문 확인 성공 (CT9G 3개 + DEH7 1개).
   - 검증: 총 90개 중 89개 통과, Tcl 문제로 실제 창 1개 건너뜀.
   - 수집 결과는 원문 기록으로만 저장. 알림/TTS 이벤트를 생성하지 않음.
   - 연장 공지의 종료시각에 따른 동적 주기는 3단계 시간 추출과 함께 연결 예정.
3. **대기 — 정보 추출과 알림 생성**
   - 날짜/판매 구간/사용기한 분리, 모든 안내 유효기간 명시.
   - 기간 불명확은 보류. 이전권 전날·판매 시작·마감 안내 우선 구현.
   - 일반 1회성/참여 독려 전체 2회/이전권 별도 정책 적용.
4. **대기 — 음성 연결**
   - 최소 host API로 기존 보스 큐에 연동; 일반 안내 최하위 우선순위.
   - 차임벨 전 정지/일시정지, 만료·해제·수정 시 재개 거부.
   - 실제 송출은 사용자 확인 후 수행.
5. **대기 — 디코 명령과 질문 버튼**
   - `/공지`, 번호 선택 전문, 내용이 있는 질문만 버튼 표시.
   - `/중지` 및 실패 대응. 번호 목록의 사용자별 일관성.
6. **대기 — 통합 검증과 사용자 테스트 안내**
   - 신규 실행/미실행 기간/업데이트/서버 전환/만료/중단 시나리오.
   - 같은 서버 한 클라이언트만 송출하도록 배포 시 안내.
   - 수동 빌드/업로드 절차, 알려진 제약, 롤백 확인.

세부 정책은 `notice_management_plan.md`, 업데이트 규격은 `ai_module_updates.md` 참조.
기능이나 검증이 남아 있으면 전체 완료로 표시하지 않는다.

**다음 착수 지점: 3단계.** 수집 본문에서 점검 시간/판매 구간/사용기한을 추출하고, 명확한 유효기간을 가진 알림을 생성한다.
새 수집/분석/안내 로직은 반드시 `notice_module/payload/` 안에 작성한다. 본체에 공지 알고리즘을 추가하지 않는다.
