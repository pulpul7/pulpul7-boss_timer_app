# 공지 모듈 작업 순서

사용자 요청: 순서는 에이전트가 관리한다. 준비된 계획에 따라 단계별 구현/검증 후 이어간다.
EXE/ZIP 빌드, 배포 복사, GitHub 게시, 실제 디코 송출은 별도 지시 전 실행하지 않는다.
설정/스케줄/음성/사용자 변경을 보존한다.

1. **소스 구현/비빌드 검증 완료 — 독립 모듈 실행과 업데이트 연결**
   - 관리 화면/기록 로직을 업데이트 payload로 이동.
   - 본체에는 버튼, 업데이트 설치기, 최소 host 연결만 유지.
   - 다운로드 모듈 로드, 시작 검증, 실패 시 이전/내장 버전 복구.
   - 이전 실패 버전 자동 재설치 반복 방지, 수동 재시도 유지.
   - 수동 패키징 방법 준비. 실제 ZIP은 생성하지 않음.
   - `notice_runtime.py` → `notice_module/payload/main.py` 동적 로딩. 설정 데이터는 기존 `notice_data/` 보존.
   - 검증: 65개 중 64개 통과, Tcl 문제로 실제 화면 1개 건너뜀.
   - 실제 EXE/실제 GitHub Release 적용 검증은 6단계 사용자 테스트에 남겨둠.
2. **소스 구현/읽기 전용 실측 완료 — 실제 공지 수집**
   - 카페의 실제 응답 확인 → 고정 공지 식별 → 출처/제목/본문/수정 비교.
   - 클라이언트 독립 수집, 서버별 설정/조회 시간표 연결.
   - 오류/부분 조회를 공지 해제로 처리하지 않음.
   - `cafe_source.py` 공개 모바일 HTML 파서 / `notice_collector.py` 워커 연결.
   - 관리 창에 `수집한 공지 / 원문`, `지금 공지 수집` 추가.
   - 실측: 상단 7개, 상시 제외 3개, 대상 4개 본문 확인 성공 (CT9G 3개 + DEH7 1개).
   - 검증: 총 90개 중 89개 통과, Tcl 문제로 실제 창 1개 건너뜀.
   - 2단계에서는 원문 기록까지만 구현. 아래 3단계에서 기간별 알림 생성을 연결함. TTS는 미연결.
   - 연장 공지의 종료시각에 따른 동적 주기는 3단계 시간 추출과 함께 연결 예정.
3. **진행 중 — 정보 추출과 알림 생성 (1차 소스 구현 완료)**
   - `notice_analysis.py`: 점검 기간, 이전권 판매 회차/서버이전 기간, 클래스 변경권 구매·사용 기간 분리.
   - 점검 발견 1회, 이전권 전날 예고/판매 시작/마감 1시간·10분 전 알림 데이터를 생성. 모든 실행 후보에 유효기간 명시.
   - 관리 창에 추출 기간/근거 문장/보류 사유 표시. 수집과 분석 결과는 같은 서버 파일에 한 번에 저장.
   - 본문 조회 실패는 기존 기록 보존. 성공적으로 읽은 최신 본문에서 사라진 기간은 기존 알림도 보류하여 대기 중인 송출 권한 무효화.
   - 사용자 체크 해제/수동 유효기간/폐기는 재수집으로 되돌리지 않음. 의미 없는 본문 수정은 재안내하지 않음.
   - 제한: 명시된 텍스트 날짜·시간 구간만 분석. 이미지/점검 전/연도 불명/복수 점검 시간은 추측하지 않음.
   - 클래스 변경권 구매 안내 1회와 구매/사용 종료 24시간 이내 주요 보스 기회 안내 연결. 같은 공지 마감 안내는 합계 하루 2회/최소 60분 간격.
   - 기존 업데이트 payload에 포함되며 본체의 스케줄/설정 코드는 변경하지 않음.
   - 2026-09-14 비빌드 검증: 105개 중 103개 통과, Tcl 실행 환경 문제로 화면 검사 2개 건너뜀. 실카페 신규 조회/실제 음성/배포 빌드는 실행하지 않음.
   - 날짜/판매 구간/사용기한 분리, 모든 안내 유효기간 명시.
   - 2026-09-14 정책 변경: 기간 불명확은 날짜 안내만 보류하고, 공지별 발견 안내를 1회 생성. 실제 재생 성공 후 자동 폐기.
   - 발견 안내 유효기간은 최초 미확정 등록부터 24시간이며 행사 기간과 별개. 재수집으로 연장하지 않음.
   - 미확정 판매 회차가 여러 개여도 짧은 안내는 글당 1개. 이력 삭제/공지 재등록 후에도 최소 식별자로 재안내를 막음.
   - 원문/분석 근거는 보존. 나중에 기간이 확정되면 남아 있는 발견 안내를 취소하고 날짜별 알림으로 전환.
   - `notice_polling.py` 연결: 명확한 점검 연장 중 자동 조회 대기 → 종료 시 즉시 확인 → 1시간 동안 5분 간격 → 기존 시간표 복귀.
   - 설정된 조회 쉬는 시간/수집 꺼짐/서버별 설정 유지. 수동 조회는 연장 대기 중에도 가능하며 수집 꺼짐은 우회하지 않음.
   - 종료 시각 불명확/본문 조회 실패/같은 날짜의 연장 공지 간 시각 충돌은 기존 시간표 유지. 완료·취소·공지 해제는 연장 대기 해제.
   - 일반 공지·업데이트 발견 1회 알림 연결. 24시간 내 실제 재생 성공 후 자동 폐기하며 재수집·이력 삭제로 반복하지 않음.
   - 후속 검증: 127개 중 125개 통과, Tcl 환경 문제로 화면 검사 2개 제외. 실제 음성/카페 조회/빌드는 실행하지 않음.
   - `notice_opportunities.py`: 이전권 판매 중 주요 보스 직후 반복(최소 30분 간격, 하루 횟수 상한 없음), 참여 독려 전체 합계 하루 2회(18~23시/최소 60분 간격/대상까지 30분 초과).
   - 같은 보스 발생 ID에는 안내 1개만 선택하며 이전권 → 마감 → 참여 독려 순서. 2/3/4챕 일반 보스 제외. 절대자 또는 주요 보스, 발할라/월드보스 기회만 허용.
   - 알리미 관리에 `참여 독려 등록` 추가. 행사 시작 필수, 정책 및 오늘 완료 횟수 표시. 자동 대상 선정은 아래 2026-09-21 후속 작업에서 연결.
   - 재생 성공 시에만 횟수 기록. 재수집/재시작/이력 삭제로 제한을 초기화하지 않음. 최소 송출 기록은 30일 보관 후 폐기.
   - 종료된 판매/사용 기간은 안내 유효기간을 수동 연장하더라도 반복 안내하지 않음.
   - 비빌드 검증 142개 중 140개 통과, Tcl 환경 문제로 화면 검사 2개 제외. 실제 보스 이벤트 host 연결/TTS는 다음 단계.
   - 이벤트 아이템 획득/교환·조합/사용/삭제 기한을 분리. 종료 24시간 이내 주요 보스 기회에 공지별 합계 하루 2회 안내. 명시적 삭제 일시·사용 기한은 시작일을 만들지 않고 종료 시각만 기록.
   - 날짜만 있거나 `점검 전`/복수 아이템의 같은 종류 기한을 구분할 수 없으면 발견 1회 안내로 대체. 실제 공지의 다양한 표/이미지 형식 확대는 실측 후 별도 보완.
   - 서버이전 차수와 종료 기간이 명확하면 종료 15분 전 응원 안내 생성. `notice_seasons.py` 5문장 순환, 서버별 기준 차수/완료 차수 최소 기록으로 재시작·중복 공지·이력 삭제에도 같은 시즌 재안내 방지.
   - 이벤트별 `TTS 문장 보기 / 편집`: 자동 문장 비교, 여러 줄 편집, 저장/자동 문장 복원/취소. 재수집 시 사용자 문장 보존.
   - 원문 날짜/자동 문장 변경 시 사용자 문장은 보존하되 재확인 전 송출 보류. 오래 열린 편집창의 덮어쓰기 방지. 문장 편집으로 완료 알림 재방송·횟수 초기화하지 않음.
   - 후속 비빌드 검증 159개 중 157개 통과, Tcl 환경 문제로 화면 검사 2개 제외. 실제 음성 생성·송출·빌드 없음.
4. **진행 중 — 음성 연결 (로컬 미리듣기 구현)**
   - `안내 문구 기본 설정 · 모든 유형` 버튼으로 39개 상황을 공지 유무와 무관하게 사전 편집. 기존 개별 TTS 편집은 행/상세 내용 더블클릭 및 Enter로 유지.
   - `notice_templates.py`에 기본 문구/허용 치환 항목/조건 설명을 집중. 점검/연장/미확정/이전권 각 단계/클래스 구매·사용/아이템 각 기한/응원 5문장/수동·참여 독려 포함.
   - `notice_template_ui.py`: 서버별 전체 저장, 유형 간 편집 초안 유지, 선택 기본값 복원, 명시적 예시 시간으로 문장 확인·로컬 미리듣기, 미저장 종료 확인. 날짜/시간 자리표시자는 실제 분석값으로만 치환하고 객체 접근/서식 지정은 금지.
   - 서버별 `tts_templates` 변경분만 저장. 미완료 자동 문구 갱신/대기 음성 token 무효화, 개별 편집 유지, 완료 알림 재방송 금지, 폐기 이력 불변, 오래 열린 설정 창의 덮어쓰기 방지.
   - 기존 수집 알림은 저장된 분석에서 식별 가능한 경우에만 유형 정보를 보충. 분석이 없는 오래된 자료는 다음 정상 수집부터 연결하며 개별 문장 내용으로 추측하지 않음. 수동 등록 문장을 비우면 유형 기본값 사용으로 명시.
   - 기본 문구 기능 포함 비빌드 검증 244개 중 242개 통과, Tcl 초기화 문제로 화면 2개 제외. 실제 합성·송출·빌드 없음.
   - `discord_notice_output.py`: 봇 출력 전용 일시중단/재개 처리 추가. VoiceClient.pause로 슬롯을 점유하지 않고, 디코 재생 슬롯은 보스에게 넘기되 알리미 디코더 위치는 보관한다. 파일/TTS 합성/알림 판단 정책은 포함하지 않는다.
   - 봇의 일반 순차 재생 및 timed/composite 교체 지점에 알리미 선점 연결. 일반 보스 작업/큐/초읽기가 남으면 알리미 시작 거부. 출력 스레드 종료 확인 후에만 보스 출력 진행.
   - 중단 중 읽은 프레임은 보관하여 이어 읽고, 중단을 실제 EOF와 구분. 만료/취소/음성 연결 종료는 해당 알리미만 정리하며 다른 보스 출력에는 정지를 보내지 않는다.
   - 보스 종료 후 무조건 자동 재개하지 않음. 모듈에서 서버/문장 판본/유효기간을 다시 확인하고 재개를 요청해야 함. 아직 모듈↔봇 제어 요청/응답 연결은 미구현이므로 자동 안내는 활성화하지 않았다.
   - 봇에 이미 준비된 음성을 무음 상태로 등록하는 내부 API 추가. 일반 실행에서는 알리미 소스를 등록하거나 재생하지 않는다. 실제 Discord/FFmpeg/TTS 실행 없이 가짜 소스와 재생 클라이언트로 검증.
   - 2026-09-15 후속 비빌드 검증: 228개 중 226개 통과, Tcl 초기화 문제로 화면 검사 2개 제외. 배포 파일/ZIP 생성 및 실제 음성 송출 없음.
   - UI 가시성 개선: 선택 탭은 진한 파랑, 같은 색 3px 테두리로 내용 영역과 연결. 상단 제목 띠/표 머리글 대비 강화. 전역 ttk 테마 변경 없이 모듈 안에서만 적용하며 향후 UI 기준은 AGENTS.md에 기록.
   - 등록된 알림 표의 현재 상태 오른쪽 `음성 듣기` 열 추가. 제목 클릭은 선택 행 듣기, 행의 `▶ 듣기`는 해당 문장 로컬 미리듣기, `■ 정지`는 중단. 일반 행/상세 내용 더블클릭은 기존 TTS 편집창을 연다.
   - 목록/편집창은 미리듣기 인스턴스 하나를 공유해 중첩 재생 차단. 서버 변경/창 종료 중단, 최신 저장 문장 확인, 횟수/완료 기록과 분리.
   - 후속 음성 연결: 미리듣기를 기존 길이 기반 대기에서 새 LocalPlayer의 실제 종료 이벤트 방식으로 전환. 취소/실패는 성공으로 표시하지 않으며 프로세스 종료 확인 전 임시 파일을 지우거나 새 음성을 시작하지 않는다.

   - `notice_local_player.py` / `notice_local_transport.py`: 별도 숨김 WPF 로컬 플레이어와 비동기 TTS 준비 구현. 자동 출력에 연결하기 전의 어댑터이며 기본 실행/실제 송출에는 아직 연결하지 않음.

## 2026-09-29: 자동 Discord 송출 연결

- 본체 `NoticeHost.get_output_context`는 현재 서버·시즌·직접 실행한 봇 PID·실행별 비밀값으로 제한된 localhost 요청 함수를 제공한다. 인계 중/연결 미완료/다른 프로필에는 함수를 제공하지 않고 요청 직전에도 검사한다.

### 후속: 정기점검 종료시간 → 스케줄 입력 서버오픈

- `notice_server_open.py`가 서버별로 이미 수집한 정기점검 분석 기간을 조회한다. 입력창을 열 때 새 카페 조회/음성 실행/사용자 설정 저장을 하지 않는다. 판정 로직은 업데이트 가능한 모듈 안에 유지한다.
- 기존 `_get_schedule_default_server_open_datetime`의 날짜/10시 계산은 그대로 둔다. 스케줄 입력에서만 `아직 유효한 수동 수정값 → 공지에서 확인한 해당 주 종료시간 → 기존 기본값` 순으로 사용한다.
- 공지 게시시각이 아니라 **실제 현재시각이 점검 종료시각 이상**일 때부터 사용한다. 과거/미래 입력 참조시각만 바꿔서 적용 시점을 앞당길 수 없다. 예: 화요일에 수요일 07~11시 공지 수집 → 수요일 11시 이후 새로 여는 입력창부터 그날 11시 적용.
- 유효 범위는 해당 정기점검 종료부터 점검 시작+7일 미만. 차주 공지가 미리 올라와도 현재 주 값을 덮지 않는다. 다음 주에 새 정보가 없으면 기존 기본값으로 복귀한다. 작성 중인 입력창 값은 수집 시점에 강제 변경하지 않는다.
- 임시점검/기간 미확정/본문 조회 실패/취소는 사용하지 않는다. 확인된 정기점검 완료 기간 > 연장 기간 > 최초 기간 순으로 선택하며, 같은 우선순위 공지의 종료시각이 충돌하면 추측하지 않고 기본값을 사용한다.
- 음성 알림 완료·공지 해제와 별개로 저장된 점검 사실은 그 주 범위에서 조회할 수 있다. 알림 송출 스위치를 켤 필요가 없다. 원본 공지/스케줄/설정은 수정하지 않는다.
- 자동값을 적용했다고 수동 수정값으로 저장하지 않는다. 사용자가 자동값과 다른 10시 등을 직접 입력하면 기존 방식대로 수동값을 유지한다.
- 선택적 모듈 API `get_server_open_override`: 이전 모듈/API 없음/오류/인계 중에는 기존 기본값으로 안전하게 복귀. 본체 API 연결은 수동 빌드가 필요하며 이후 정보 판정 로직은 모듈 업데이트로 변경 가능하다.

### 후속: 임시점검 1회 등록 / 중요 대상 / 저녁 두 시간대

아래 규칙은 앞선 절대자·7/8챕 고정 선정 및 저녁 전체 목록 읽기 규칙을 대체한다.

- 중요 대상은 보스 설정의 `star` 체크. 별 체크가 없어도 **공성전 → 트리니트리그(트리니티 리그) → 방어전 → 점령전 → 지옥성체(지옥 성채) → 길던(길드던전)** 순으로 포함한다. 행사 우선순위가 먼저이고 같은 우선순위에서는 빠른 시각 순. 신청/입찰/대상 선택은 실제 행사로 오인하지 않는다.
- 본체 스냅샷에 별 체크·별 체크 명단과 실제 고정보스 일정도 포함한다. 새벽·점검 전 아침 자동 대상 역시 같은 중요 기준 사용. 단순히 절대자나 7/8챕이라는 이유만으로는 선정하지 않는다.
- 21:00~24:00의 확정된 중요 대상 중 대표 1개를 선정. 추가 대상이 있으면 `오늘 저녁 22시 공성전 외 주요보스들이 있습니다. 많은 참여 부탁드립니다.`, 하나면 `오늘 저녁 22시 프레이가 있습니다. 많은 참여 부탁드립니다.` 기본 문구 사용. 이미 지난 대상은 새 안내에 넣지 않는다.
- 수동 보스/길던 등록도 대표 후보로 통합하여 별도 반복 안내하지 않는다. 제목은 별 체크 보스명/지정 행사명과 일치해야 한다. 직접 쓴 TTS는 그 대상이 대표로 선정되었을 때 보존하여 사용. 원본 해제/수정은 준비된 안내를 즉시 차단한다.
- 저녁 **1차**: 18:00~19:00 미만에 1분 전 안내가 발생할 5챕 이상 보스 중 연속보스 우선, 없으면 가장 높은 챕터, 동률이면 빠른 시각. 연속 판단은 기존 rapid-chain과 같은 인접 60초 이내. 해당 보스의 실제 1분 전 안내 완료에만 연결. 5챕 이상 기회가 아예 없으면 18시 타이머 슬롯(18:02까지, 뒤늦은 몰아읽기 없음).
- 저녁 **2차**: 당일 20시 월드보스의 1분 전 안내가 실제 완료된 후. 시계가 19:59라는 이유만으로 완료를 추측하지 않는다. 각 시간대별 하루 1회이며 대상/문구 변경·재시작으로 반복하지 않는다.
- 공성전 당일에는 **12시 월드보스**의 1분 전 안내 완료 후 `오늘은 공성전이 있는 날입니다. 많은 참여 부탁드립니다.` 별도 1회. 저녁 2회와 독립. 공성전이 21~24시 밖에 있어도 당일 아직 남은 실제 공성전이면 정오 안내 대상. 문구 설정에 독립 체크/편집 유형 추가(전체 42유형).
- 저녁 두 슬롯의 횟수 장부는 별도로 구분하여 기존 새벽/아침 안내가 저녁 슬롯을 소모하지 않게 한다. 새벽/아침 기존 정책은 유지한다. 필요시 해당 유형 체크로 끌 수 있다.
- `participation_slot`은 모듈 내부 송출 정책. 준비/재개/완료 시 다시 검증하며 `scheduled_at` 원본 소수초·보스명·챕터·실제 완료 단계로 선택된 기회와 일치하는지 확인한다. 성공 재생만 횟수 기록. 시각 경과/불확실한 완료/서버 변경은 송출 허용 근거가 아니다.
- `notice_maintenance_import.py`: 수집된 상단 임시점검 중 미래 시작·종료가 확정된 경우 선택적 GUI host 명령으로 기존 임시점검 등록 경로 호출. 정기/연장/완료/취소/불명확/지난 일정 제외. 수집 꺼짐·점검 카테고리 해제도 준수한다.
- 서버별 공지 ID와 점검 시작시각으로 중복 등록 방지. 등록 전에 처리 의도를 저장하고 성공/이미 존재/충돌/실패 기록. 재수집·동일 공지 시간 수정·재시작·중복 게시글로 반복 등록하지 않는다. 중단된 pending/실패는 자동 재실행하지 않고 수집 내용 상세에 수동 확인 필요 표시. 이 기록은 음성 송출 장부와 별개다.
- GUI에서 서버/시즌/인계 상태 재확인. 이미 다른 미래 임시점검이 있으면 덮어쓰지 않고 충돌 처리. 같은 일정은 기존 항목 재사용. 저장 실패는 메모리 원복, 저장 성공 후 화면 갱신 실패는 중복 등록 사유로 삼지 않는다. GitHub 업로드는 하지 않는다.
- **연결 상태:** 임시점검 자동 스케줄 등록과 안내 대상/시간대/유형 설정/큐 허용 규칙까지 연결. 실제 알리미 자동 TTS 출력 transport와 본체의 1분 전 완료 기회 공급은 여전히 미연결이다. 이 단계에서 실제 18시/월드보스 뒤 TTS가 작동한다고 안내하면 안 된다. 다음 단계는 이 출력 연결이며 기존 인계 hold와 보스 우선 중단 장벽을 반드시 유지한다.

### 후속: 스케줄 변경 후 5초 사전 생성

- 앞선 시작 4초/10초 반복 등록 대신 **마지막 변경 후 5초 안정화** 뒤 대상 재검토와 음성 사전 생성을 수행한다. 스케줄 저장(추가·수정·생성·동기화)에서 선택적 host 알림 API로 즉시 무효화하며, 1초 간격 읽기 전용 스냅샷 비교로 저장 없는 갱신·서버 전환·음성 설정·날짜 변경도 감지한다. 변화 없는 화면 조회는 대기 시간을 다시 늘리지 않는다. 타이머/GUI 부하에 따른 실행 지연은 가능하다.

### 후속: 등록 알림별 재생 예정 표시

- 등록/이력 목록의 `사용` 바로 오른쪽에 `재생 예정 / 조건 (KST)` 열을 추가했다. 유효기간이나 행사 시작시간을 재생시간으로 혼동하지 않도록 실제 `_slot_plan`을 기준으로 표시한다.
- 저녁 1차·2차는 기존의 독립 이벤트 행을 유지한다. 같은 안내 문구라도 예를 들어 1차 `09/22 18:00 이후 · 대기열`, 2차 `09/22 19:59 · 월드보스 안내 후`처럼 별도 시각을 보여 준다. 보스가 선정된 1차는 그 보스의 1분 전 시각과 이름을 표시한다.
- 정해진 시각이 없는 주요 보스 후 반복 안내는 조건을, 일반 1회 안내는 유효 시작 이후 대기열임을 표시한다. 수동 참여 독려 원본은 별도 세 번째 송출로 보이지 않게 `대상 선정용 · 1차/2차 알림 참조`로 표시한다. 미확정/잘못된 계획은 시각을 추측하지 않는다.
- 상세 영역에도 재생 예정과 지연 가능성을 명시한다. 목록 가로 스크롤과 창 폭을 조정하고, 듣기/체크/더블클릭 동작을 새 열 위치에 맞췄다. 송출 시각/횟수/설정을 변경하는 작업은 아니다. 자동 송출 미연결 경고도 그대로 유지한다.

### 수정: 공지 수집의 스케줄 오분류 및 유효 알림 복구

- `finish_collection()`의 게시글 식별 정규식이 `schedule/15/...`를 카페 게시글 `schedule/15`로 오인했다. 정상적인 수집 완료 때 스케줄 알림을 `공지 해제`로 폐기하고 폐기 방지 키까지 제거하는 경로였다. 이 함수에서도 `schedule/` 출처를 명시적으로 제외하여 실제 카페 게시글과 분리한다. 수동 폐기한 스케줄 키도 이후 수집에서 보존한다.
- 다음 스케줄 동기화에서 현재 서버·시즌·날짜의 실제 후보와 일치하고, 원래/새 유효기간이 모두 남은 `공지 해제` 스케줄 알림만 복구한다. 사용자 폐기·만료·대상 삭제·별 해제·다른 서버/시즌 항목은 복구하지 않는다. 최신 스케줄로 문장을 다시 계산하므로 03:05에서 03:08로 변경한 스카디도 최신 시각을 반영한다.
- 직접 편집한 문장·유효기간·유형 스위치·실제 송출 횟수 장부는 유지한다. 복구 기록은 항목 상세에 표시하며 이후 문장 갱신에도 보존한다. 기존 파일을 별도 도구로 강제 덮어쓰지 않고, 수정된 모듈 재시작 후 정상 트랜잭션으로 처리한다.
- 앞으로는 폐기 전 사용 체크 상태도 기록한다. 과거 버그 기록에는 이 정보가 없으므로 승인된 오폐기 복구는 기본 사용 상태로 되돌리고, 폐기 전 해제 상태가 기록된 경우에는 해제를 유지한다. 카테고리/유형 송출 스위치는 자동으로 켜지 않는다.
