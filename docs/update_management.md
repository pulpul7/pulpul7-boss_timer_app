# 업데이트 관리

운영·개발 기준과 후속 보완 항목은 [UPDATE_POLICY.md](../UPDATE_POLICY.md)를 따른다.
프로그램에서는 `버전별 패치내역` 아래 `업데이트·복구 규칙` 버튼으로 볼 수 있다.

전체 업데이트와 웹 업데이트는 별도 경로다. 실행 파일과 배포 ZIP은 사용자가 수동으로 빌드한다.
2026-10-17 사용자의 명시적 승인에 따라 전체 업데이트 실행 연결을 활성화했다.

## 전체 업데이트

- 파일명: `bosstimer_update_v버전.zip` (예: `bosstimer_update_v6.3.1.zip`). 이전 `v` 없는 이름도 읽는다.
- 특정 배포 버전을 지정할 때는 빌드 프로세스에 `BOSS_TIMER_BUILD_VERSION=v6.3.1`을 설정한다.
  `release_version.resolve_release_version`이 형식을 검사한 뒤 Git 태그보다 우선하며 EXE 내장 메타데이터와 ZIP에 같은 버전을 사용한다. Git 태그를 만들거나 이동하지 않는다.
- `build_release.py`는 봇 → 본체 순서로 빌드하고 두 EXE와 `program_update.json`을 넣는다.
  리소스와 선언한 배포 기본설정은 GUI EXE에 포함된다. 같은 이름 ZIP은 덮어쓰지 않는다.
- 공식 GitHub Releases의 정식 배포만 사용한다. 알림 모듈·웹 ZIP, 초안, 사전 배포는 제외한다.
  버전은 숫자로 비교하며 `.fix`, `.fix2`도 순서대로 구분한다.
- 매일 한국시간 03:00 이후 하루 한 번 확인한다. 꺼져 있었다면 다음 실행 때 확인한다.
  소스 실행에서는 자동 확인·설치하지 않는다. UI에서 수동 확인과 적용도 가능하다.
- ZIP 전체 크기·GitHub SHA-256 → 필수 EXE·압축 경로·해제 용량 → 파일별 SHA-256을 검사한다.
  다운로드·검증 실패 때는 기존 프로그램을 종료하지 않는다. 검증한 파일은 재시도에 재사용한다.
- 수동 다운로드는 즉시 진행창을 열어 퍼센트와 받은/전체 MB를 표시한다. 이후 SHA-256 검증·압축 해제·재시작 준비를 별도 문구로 표시한다.
  완료·오류 때 진행창을 닫고 다음 작업으로 이어간다. 이 표시는 다운로드 스레드에서 Tk를 호출하지 않고 UI 타이머로 갱신한다.

## 적용·재시작 순서

1. 설치 폴더 쓰기 권한과 용량을 확인하고 `program_versions/<작업 ID>/`에 새 버전을 준비한다.
2. 공통 유지보수 차단을 설정한다. 봇 재접속·복구, 웹 시작·종료·업데이트·승계의 로컬 경로를 막는다.
   이미 진행 중인 웹 작업은 끝날 때까지 전체 업데이트를 보류한다. 긴 웹 작업이 봇 실행을 직렬화하지는 않는다.
3. 상태와 설정 저장 → 봇 정상 종료 → 실행 경로·생성 시각이 일치하는 잔여 봇 정리 → 담당 권한 반납.
4. 별도 업데이트 도우미가 준비됐는지 확인한 다음 본체의 정상 저장·종료 경로를 사용한다.
   웹은 기존 백그라운드 유지 경로로 분리하며 종료하지 않는다.
   이전 본체 종료 직전 경로 조회가 실패하면 같은 핸들의 종료 신호와 실제 종료 상태를 제한 시간 안에서 재확인한다.
   확인되지 않은 프로세스를 종료됐다고 가정하거나 강제로 본체를 종료하지 않는다.
5. 도우미가 이전 본체의 실제 종료를 확인하고 설정과 배포 적용 기록을 백업한다.
6. `program_active.json`을 새 버전으로 전환하고 새 본체만 실행한다.
7. 새 본체는 자료 이관 → 선언한 배포설정의 AppData 적용 → 일반 설정 로드 → 잔여 봇 재확인 순서로 준비한다.
8. 이전에 봇을 사용 중이었다면 새 폴더의 봇을 실행한다. 로컬 제어 응답·경로·실행 상태를 확인한다.
   Discord·인터넷 연결 성공 자체는 설치 성공 조건이 아니다. 준비 중 송출·임의 재접속은 막는다.
9. 본체가 준비 완료 신호를 보내면 도우미가 성공을 확정하고 차단을 해제한다.
10. 새 본체가 기존 웹 프로세스에 다시 연결한다. 이전 송출 중 상태였다면 권한을 재검증한다.
    다른 담당자가 있으면 송출을 빼앗지 않고 대기한다. 디코 복원 때문에 웹을 재시작하지 않는다.

기존 진입 EXE와 버전 폴더는 덮어쓰거나 자동 삭제하지 않는다. 기존 바로가기로도 활성 버전이 실행된다.
특히 살아 있는 웹이 사용하는 EXE·리소스 폴더는 보존한다. 웹 코드·페이지 변경은 별도 웹 업데이트 때 반영한다.

이전 웹 담당자로 복구할 때는 현재 웹을 대기로 바꾸기 전에 이전 PC가 온라인이고 원래 실행 세션인지 확인한다.
종료·재시작한 이전 PC에는 복구를 시도하지 않으며 현재 웹 제어 상태를 유지한다. 같은 생략 로그는 반복 출력하지 않고,
대상이 다시 유효해지면 재검증한다. 공개 성공 여부는 별도의 실제 웹/DDNS 응답으로 확인한다.

확인창·봇 복구·웹 작업 때문에 자동 적용이 보류되면 최대 20분 동안 30초 간격으로 다시 확인한다.
보류 후에도 검증한 파일은 남아 있으므로 수동 적용으로 이어갈 수 있다.

## 실패·복구와 설정 보호

- 실제 종료·준비 완료 신호를 기준으로 진행한다. PID만 보고 종료하지 않으며, 확인 권한이 없으면 중단한다.
- 실행 실패·시간 초과 시 새 버전 폴더의 시험 실행 프로세스만 정리하고 이전 포인터·설정을 복원한다.
  웹 로그인 세션·비밀번호·인증서·공개 리소스·실행 중 웹 프로세스는 복원 대상으로 삼지 않는다.
- 설정 백업에는 배포 적용 기록, 선언한 색상·글꼴 기본값을 포함한다. 사용자 음성과 기존 백업은 보존한다.
  복원 전에 모든 설정 백업의 SHA-256을 확인하며, 손상된 백업으로 현재 설정을 덮어쓰지 않는다.
  과거 Discord 요청·송출 대기열을 복원하여 다시 실행하지 않는다.
- 같은 실패 버전은 자동 재설치하지 않는다. 수동 재시도 또는 다음 버전에서 진행한다.
- 중간에 전원이 꺼지면 다음 시작 시 유지보수 기록을 보고 이어서 처리하거나 이전 버전으로 복원한다.
  기록이 손상되면 설정을 읽기 전에 중단해 기존 값을 보존한다.
- GUI 저장과 비동기 알람 저장은 읽은 시점의 배포 적용 기록을 함께 확인한다.
  그 이후 새 배포가 적용됐다면 이전 메모리 값으로 저장하지 않는다.
- 유지보수 중 웹의 배포 색상·기본 글꼴 크기 저장은 잠시 막는다. 평소에는 매번 최신 파일을 읽는다.

## 스케줄 자료 동기화

스케줄의 `동기화`는 아래 전체/웹 프로그램 업데이트와 별개인 운영 자료 다운로드다.
자료 버전이 높다고 내용까지 최신이라고 간주하지 않는다. 서버 목록과 실제 파일의 버전·해시를 대조하고,
로컬보다 오래된 버전·빈 스케줄·현재 앞으로의 일정이 있는데 과거 일정만 있는 자료는 적용하지 않는다.
버전 불일치는 서버 자료를 확인한 뒤 재시도하며, 의도적인 이전 자료 복원은 스케줄 `복구`를 사용한다.
덮어쓰기 확인은 스케줄 창 중앙에 표시하고 진행창은 잠시 숨겨 질문을 가리지 않는다.
다운로드 대기는 창 닫기/Escape로 취소할 수 있고 최대 120초 후 종료한다. 늦게 완료된 다운로드는 적용하지 않는다.
실제 자료 적용과 확인 응답 대기는 다운로드 시간 제한으로 강제 중단하지 않는다.
`schedule_sync_failed`는 단계·오류 종류·코드 위치만 남기며 자격증명이나 내려받은 자료를 기록하지 않는다.

## Discord 명령

`/보탐`의 `동작` 입력칸에 `업데이트 전체 비밀번호`를 입력한다.
비밀번호와 Discord 서버 관리자/서버 관리 권한을 확인하며 비밀번호를 GUI 요청에 기록하지 않는다.
대상은 현재 송출 담당 PC → 웹 담당 PC → 유일하게 연결된 PC 순서로 결정한다.
대상이 불분명하거나 `program_update_protocol=1`을 지원하지 않으면 실행하지 않는다.

대상 PC에서 다운로드·검증을 마친 뒤 결과를 요청자에게만 보낸다.
봇의 안내 전달 완료 확인이 대상 PC에 도착해야 재시작을 예약한다.
전달 확인이 없거나 실행 세션이 바뀌면 자동 재시작을 보류한다.
이 안내는 검증·적용 예약 결과이며 최종 시작 성공 여부는 로컬 업데이트 기록으로 확인한다.

## 웹 업데이트

- `/웹서버 업데이트 비밀번호`, `/보탐 업데이트 웹서버 비밀번호`, GUI의 `수동 웹 업데이트`는 기존 경로를 사용한다.
- 본체와 Discord 봇은 재시작하지 않는다. 같은 API 형식의 정적 파일은 지원되는 웹 프로세스에 무중단 반영한다.
  작업 ID·실행 세션·파일 버전의 적용 응답 후 활성 버전을 확정하며, 일반 적용에서 웹 승계·공개 재진단·인증서 준비를 반복하지 않는다.
- 구형 웹이 무중단 적용 기능을 제공하지 않으면 처음 한 번 웹만 재시작한다. 새 본체를 실행해도 이미 떠 있는 구형 웹의 Python 코드는 자동으로 바뀌지 않는다.
- 파일/API 호환성 검사 실패 시 기존 웹을 유지하고 프로그램 업데이트를 안내한다. 적용·복구 응답 확인 실패 자체로 강제 재시작하지 않는다.
- `web_live_assets.py`가 불변 파일/ETag 묶음과 이전 묶음을 보유한다. HTTP·HTTPS는 같은 묶음을 참조하며, 웹 담당자·로그인·푸시·운영 스케줄은 재생성하지 않는다.
- 아직 웹 ZIP을 읽지는 않는다. 공식 저장소 `web_assets/`의 `index.html`, `style.css`, `schedule.js`,
  `login.html`, `login.js`, `metadata.json`을 사용한다.
- `bosstimer_web_update_버전.zip`은 향후 웹 ZIP 경로를 연결할 때 사용할 예정 이름이다.
  현재는 이 이름의 ZIP을 올려도 웹 업데이트에 사용되지 않는다.

### 열린 사용자 화면 갱신

`/웹서버 갱신`은 현재 웹 담당 PC의 웹 프로세스에 갱신 신호를 전달한다. Discord 서버 관리자/서버 관리 권한이 필요하며
비밀번호는 요구하지 않는다. 기존 실행·종료·업데이트 명령과 별개이고 파일 다운로드나 서버 재시작은 하지 않는다.
대상 실행 세션과 갱신 프로토콜 지원 여부를 확인하고, 웹 프로세스의 동일 작업 ID 수신 응답 후 전달 완료를 알린다.
이 응답은 모든 브라우저의 갱신 완료 확인은 아니다. 유지보수 잠금 중에는 요청을 차단한다.

새 화면 코드를 읽은 페이지는 기존 15초 상태 확인에서 명령 신호나 웹 파일 버전 변경을 감지해 자동 갱신한다.
숨긴 화면은 다시 열었을 때 갱신한다. 현재 탭·날짜·스크롤을 복원하고 개인 설정·로그인은 유지한다.
저장하지 못한 보스 선택이 있으면 자동 이동을 보류한다. 오디오는 브라우저 정책에 따라 다시 재생 조작이 필요할 수 있다.
F5·모바일 새로고침·명령 갱신이 몰리면 HTTP/HTTPS 공통 대기열에서 0.25초 간격으로 문서 제공을 시작한다.
대기 페이지는 남은 시간을 계산해 자동 재요청하므로 서버 작업 스레드를 대기 상태로 점유하지 않는다.
이는 화면 시작 요청의 분산이며 모든 리소스 다운로드 완료까지 하나씩 직렬 실행하는 방식은 아니다.

첫 도입에는 변경된 본체·봇과 웹 프로세스 코드가 필요하다. 살아 있는 구형 웹 프로세스의 Python 코드는
정적 웹 업데이트만으로 바뀌지 않으며 갱신 명령이 이를 강제 재시작하지 않는다.
이미 열린 구형 JavaScript에는 자동 갱신 로직이 없으므로 최초 한 번 사용자 새로고침이 필요하다.

### 배포 EXE의 웹 시작 확인

단일 EXE에서는 실행을 요청해 얻은 실행기 PID와 Python 웹 작업의 PID가 다를 수 있다.
`web_worker_identity.SpawnedWorkerIdentity`는 Windows에서 직접 자식 관계·같은 실행파일 경로·생성 시각을 확인한 작업만 승인한다.
실행 세션·프로토콜·포트 검사는 그대로 적용하고, 프로세스 트리 확인은 최초 승인 때 수행한다.
이후에는 승인한 PID의 경로·생성 시각과 실행기의 생존 상태를 재확인한다.
종료 요청과 대기는 기존 실행기 핸들을 유지한다. 무관한 PID를 채택하거나 이름만 보고 종료하지 않는다.

`worker_status_identity_verified/rejected`는 실행기/작업 PID를 기록한다.
웹 프로세스 자체의 준비 실패는 HTTPS 준비 실패와 구분해 표시한다.
이 변경은 본체의 Python 제어 코드이므로 정적 웹 파일 ZIP으로 반영할 수 없고 본체 재빌드가 필요하다.
소스 회귀 검사와 실제 배포 EXE 확인은 별개다.

## 알림 모듈

`Update_AI_v버전.zip`은 알림 모듈 전용이다. 이름만 바꿔 전체 업데이트에 사용할 수 없다.
기존 자동 확인 설정·배포 목록·설치 이력·다음 실행 적용·실패 복구 기능은 유지한다.
전체 업데이트에도 알림 모듈이 본체 EXE에 내장되어 포함된다. 더 높은 별도 설치 모듈이 있으면 그 모듈이 우선할 수 있다.
이번 내장 코드를 사용하게 하려면 배포설정의 `알리미 실행 코드 · 이번 배포본 사용`을 선택해 선언한다.
개인 설정·문구를 바꾸는 선택과는 별개다. 적용 우선순위와 시작·복구 범위는 [알림 모듈 업데이트](ai_module_updates.md)를 참고한다.

## 검증 범위

비빌드 검증은 가짜 실행파일 바이트·임시 설정·가짜 프로세스·가짜 다운로드로 수행한다.
실제 EXE 업데이트, GitHub 업로드, Discord 연결, 현재 프로그램 종료·재시작은 수행하지 않는다.
첫 적용에는 이 업데이트 코드를 포함한 본체와 봇을 사용자가 한 번 수동 빌드·배포해야 한다.
