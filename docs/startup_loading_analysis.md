# 첫 실행 로딩 분석과 진행 표시 구상

2026-10-03 최초 분석과 후속 구현 기록. 앱 실행·테스트·빌드는 사용자가 진행한다.
아직 실제 실행시간을 측정하지 않았으므로 단축할 초 수는 확정할 수 없다.

## 현재 반영된 변경

- `startup_runtime.py`가 GUI의 무거운 import 전에 사용자·Windows 세션별 named mutex를 확보한다.
  같은 사용자의 일반/관리자 실행과 다른 폴더의 실행도 같은 GUI로 취급한다. 중복 실행은 설정을
  읽지 않고 종료하며 named event와 창 속성으로 기존 창을 복원하고 앞으로 가져온다.
  최소화된 창과 초기 로딩창도 복원하며, 기존 모달 창이 있으면 그 창을 활성화한다.
  보조 스케줄러와 Discord 봇은 GUI 실행 차단 대상에서 제외한다.
- 프로세스 종료 시 Windows가 mutex를 정리하므로 PID 파일이나 오래된 실행 표시가 남지 않는다.
  중복 실행 요청은 `ShowWindowAsync`와 비동기 창 배치로 처리해 초기화 중인 UI를 기다리지 않는다.
  [Microsoft 창 활성화 API](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow),
  [동기화 객체 보안](https://learn.microsoft.com/en-us/windows/win32/sync/synchronization-object-security-and-access-rights).
- 초기 로딩창은 별도 스레드의 Windows 창과 메시지 루프로 동작한다. Tk 객체를 다른 스레드에서
  건드리지 않고, import·파일 준비 중에도 단계·경과 시간·막대 애니메이션을 표시한다.
  새 EXE나 보조 프로세스를 실행하지 않는다. 7단계 표시는 시간 기반 퍼센트가 아니다.
  창을 닫아 숨겨도 초기화는 계속되며 다시 실행하면 로딩창을 복원한다.
- 첫 시즌 설정이 필요한 경우에는 구성된 메인 창을 먼저 표시한 후 기존 중앙 Tk 팝업을 연다.
  프로필 접근 실패 시 로딩창을 닫고 기존 접근 오류 팝업을 표시한다.
- `boss_timer_gui.spec`에 `assets/startup_loading.png`를 사용하는 PyInstaller Splash를 추가했다.
  EXE 압축 해제 중에도 한국어 시작 안내가 보이며 Python 진입 후 단계별 로딩창으로 전환한다.
  [PyInstaller Splash 대상](https://pyinstaller.org/en/stable/spec-files.html#the-splash-target).
  부트로더 압축 해제 이전 및 UAC 승인창은 Python에서 제어하지 않는다. 중복 EXE도 Python 진입
  전에는 부트로더 준비를 거치지만 GUI·설정 초기화와 봇 자동 실행은 한 번만 진행한다.
- 설치된 TTS 엔진은 경로·버전·manifest/패키지 수정 정보가 같으면 재사용한다.
  frozen import의 선행 로딩을 제거하고 설치 완료 시에만 강제 재로딩한다.
- TTS 캐시 manifest에 마지막 정리 완료 설정을 기록한다. 같은 설정으로 재실행하면 전체
  폴더 순회와 manifest 재저장을 생략한다. 예전 manifest 또는 음성 설정 변경 시에는 기존
  정리를 수행한다. 실제 사용할 파일의 존재 여부와 설정별 캐시 키 검사는 유지한다.
- 같은 프로필 준비 작업 안에서 성공한 접근 검사를 `seed_profile`과 `ensure_profile_defaults`가
  공유한다. 없는 폴더의 검사 결과는 재사용하지 않으므로 새로 생성된 프로필도 검증한다.
  권한 복구·경로 검증·자료 보존은 유지하며 다음 실행/다른 작업까지 검증을 캐시하지 않는다.
- 서버 선택 표시의 연속 중복 호출과 불필요한 150ms/1200ms 재호출을 제거했다.
  시작 초읽기 호스트 준비는 기존 비동기 함수를 사용한다. 음성 준비의 메인 호스트 중복 호출도
  제거했다. 기록/스케줄의 필수 의존성이나 첫 알림 기준은 변경하지 않았다.
- 음성 사전 로드 목록은 집합으로 중복을 제거한다. 보관 파일 이름이 이미 현재 형식인 경우에는
  JSON 전체 읽기·스케줄 역직렬화를 생략한다. 구형 보관 이름의 기존 정리는 유지한다.
- 준비 완료 시 기존 진단 로그에 `startup_ready total_seconds=... stages=...`를 기록한다.
  상세 로그가 꺼진 배포본에서도 `%APPDATA%/BossTimer/startup_timing.json`에 마지막 성공한
  시작의 단계별 시간 요약을 저장한다. 기존 설정 파일이나 음성 캐시는 변경하지 않는다.
  로그의 프로그램 불러오기 시간은 Python 진입부터이며 EXE 압축 해제 시간은 포함하지 않는다.

아래는 변경 전 분석과 당시 구상이다. 부가 기록·화면 초기화의 대규모 비동기 재구성은
의존성 위험이 있어 적용하지 않았고, 실제 단계별 소요 시간에 따라 후속 개선할 수 있다.

## 현재 작업 순서

| 구간 | 현재 작업 | 화면과 실행 특성 |
| --- | --- | --- |
| EXE 시작 | PyInstaller 단일 EXE의 내장 리소스 압축 해제 | Python 코드 실행 전. 소스 실행에는 해당하지 않는다. |
| 모듈 불러오기 | GUI 의존 모듈, TTS 모듈 설정 | `main()`과 Tk 창 생성보다 먼저 수행된다. |
| 사용자 자료 확인 | 구형 데이터 이관 여부, 현재 시즌·서버 선택, 프로필 권한과 기본설정 확인 | `BossTimerApp.__init__` 앞부분에서 동기 처리한다. |
| 설정·기록 읽기 | 환경설정, 시즌 이력, 보스·고정보스·알림, 기록표와 평균 캐시 | 메인 화면을 만들기 전에 읽고 정규화한다. |
| 음성·스케줄 준비 | TTS 엔진 설정, 음성 작업 스레드, 음성 길이 캐시, 로컬 스케줄·GitHub 캐시 | 일부는 비동기지만 초기화 순서에 포함된다. |
| 화면 구성 | 시즌 확인, 필요한 첫 설정 안내, 배경·아이콘·그래프 | 생성자를 마친 후 `mainloop()`가 시작된다. |
| 화면 이후 | 180ms 음성 호스트, 350ms 필요한 스케줄 가져오기, 420ms 초읽기 호스트, 600ms 공통 TTS, 700ms 봇 연결, 3.5초 보관 이름 정리, 12초 업데이트 모듈 | 예약 시간이 지나면 Tk 콜백으로 시작한다. UI 콜백에서 파일 검사·프로세스 시작을 하는 부분은 잠깐 화면 처리를 막을 수 있다. |

PyInstaller의 EXE 압축 해제와 프로그램 내부 초기화는 별도로 구분해야 한다.
현재 `boss_timer_gui.spec`는 `EXE`에 바이너리·데이터를 함께 넣는 단일 파일 구성이다.
이 방식은 실행할 때 리소스를 임시 폴더에 풀기 때문에 시작 비용이 있다.
[PyInstaller 실행 방식](https://pyinstaller.org/en/stable/operating-mode.html#how-the-one-file-program-works)

## 확인된 최적화 후보

1. **TTS 설정·모듈 불러오기 중복**
   `edge_tts_voice.py`는 모듈 끝에서 `configure_edge_tts_module()`을 호출하고,
   GUI 생성자도 같은 함수를 다시 호출한다. 설치 모듈 경로에서는 `sys.modules`에서
   `edge_tts` 항목을 제거한 후 다시 import한다. 경로·모듈 버전이 같으면 재사용하고,
   설치·업데이트·경로 변경 때만 다시 불러오는 방안을 우선 검토할 수 있다.
   소스 실행의 개발용 fallback은 Python 모듈 캐시를 사용할 수 있으므로 실제 재로딩 비용은 다를 수 있다.

2. **현재 프로필 전체 접근 확인 중복**
   `_migrate_flat_server_profile_to_season_profile()`은 `seed_profile()` 다음에
   `ensure_profile_defaults()`를 호출한다. 두 함수 모두 `ensure_profile_access()`를 부른다.
   이 검사는 하위 디렉터리를 전부 순회하고 각 파일을 열어 한 바이트를 읽는다.
   같은 초기화 안에서 검증 결과를 공유하고, 정상 실행 시 필수 설정 파일을 먼저 확인하는 방안을 검토할 수 있다.
   전체 점검·복구는 최초 이관·권한 오류·명시적 복구 때 수행하는 방향이지만,
   경로·링크 검사와 PermissionError 처리, 사용자 자료 보존은 유지해야 한다.
   최근 사용된 `season_18/9`는 읽기 전용 집계 시 파일 22개였다. 이 PC에서 이것만으로
   긴 로딩이 발생한다고 단정할 근거는 없다. 최초 관리자 실행 때는 상속 복구를 위해
   각 경로에 `icacls`를 실행하므로 정상 재실행과 비용이 다를 수 있다.

3. **서버 선택 표시 반복**
   화면 구성 직후 `_sync_github_server_combo_to_loaded_meta()`를 연속 두 번 부르고,
   150ms·1200ms 후에도 예약한다. 동일 자료를 대상으로 하는 즉시 중복 호출은 정리 후보이다.
   창을 만든 후 필요한 시점의 한 번과 자료가 실제 갱신된 뒤의 갱신으로 구분하는 방향을 검토한다.

4. **초기 화면 전에 읽는 부가 자료**
   기록표·평균 캐시·배경 영상 캐시는 시작 시 읽는다. 각 파일 크기와 정규화 비용을 측정한 뒤,
   스케줄 계산에 즉시 필요한 값과 창을 열 때만 필요한 값을 분리할 수 있다.
   평균 캐시와 보스 지표의 의존성이 있으므로 일괄 지연 로딩을 적용하면 안 된다.

5. **시작 직후 음성 호스트 준비**
   메인 음성 호스트는 여러 음성 폴더를 검사하고 사전 로드 목록을 만든 뒤 프로세스를 시작한다.
   시작 콜백에서 하는 파일 검사·준비만 안전하게 비동기로 옮길 수 있는지 검토한다.
   첫 알림의 지연·초기 잡음을 줄이기 위한 준비 자체는 필요하며, 임박한 알림을 놓치지 않아야 한다.
   공통 TTS 사전 생성과 음성 길이 캐시는 이미 별도 작업으로 준비하는 경로가 있다.

자료 이관·TTS 캐시 복사·배경·wav 기본 파일 준비에는 기존 완료 표시나 버전 확인이 있다.
매번 모든 음성 파일을 복사하는 구조로 판단해서는 안 된다. 시작 시 구형 봇 종료 함수도 현재는 바로 반환한다.
업그레이드 설정 초기화 함수는 `False`를 반환하므로 그 아래 재준비 분기는 현재 동작하지 않는다.

## 시작 진행 표시 구상

- 먼저 `import 완료`, `프로필 확인`, `설정 읽기`, `기록·스케줄 읽기`, `TTS 준비`, `화면 구성`의
  시작·완료 시각을 `perf_counter()`로 기록해 병목을 확인한다. 실행시간 기록만 먼저 적용할 수 있다.
- Tk가 준비되면 부모 중앙에 `보스전 타이머 시작 중`이라는 작은 진행창을 표시한다.
  현재 단계, `단계 3/6`, 경과 시간과 움직이는 막대를 표시한다. 측정 근거 없이 완료 시간을 예측하거나
  실제 파일 진행률과 다른 퍼센트를 보여주지 않는다.
- 현재 생성자는 `mainloop()` 전에 동기 작업을 처리하므로 창만 추가하면 계속 움직이는 진행 표시가 어렵다.
  Tk 객체·화면 생성은 메인 스레드에 두고, 파일 읽기·검사는 별도 스레드에서 결과를 GUI 큐에 전달한다.
  단계 전환은 `after`로 이어 실행하고, 애니메이션을 위해 `root.update()`나 별도 sleep을 넣지 않는다.
- 필수 설정·스케줄과 첫 알림에 필요한 준비가 끝나면 메인 화면을 사용하게 한다.
  Discord 로그인·업데이트·불필요한 부가 준비를 화면 사용의 필수 조건으로 만들지 않는다.
- 필수 설정 접근 실패는 현재의 중앙 오류창으로 알리고 부분 초기화된 상태로 실행하지 않는다.
- EXE 압축 해제·Python import 전에 보이는 안내가 필요하면 Tk 진행창과 별개로
  PyInstaller의 시작 splash를 검토해야 한다. 지금은 빌드 구성도 바꾸지 않는다.
  [PyInstaller splash 기능](https://pyinstaller.org/en/stable/usage.html#splash-screen-experimental)

진행 표시 단계 분리는 초기화 의존성을 바꾸는 작업이므로, 병목 측정 후 별도 변경으로 진행하는 것이 적절하다.
이번 연결·승계 진행창은 이러한 초기화 재구성과 독립적이다.
