# GitHub 반복 쓰기 감소 — 2026-10-04

> 이 문서는 주기만 늘렸던 초기 수정의 기록입니다. 이후 구조 변경으로 아래의 5초 조회·120초 쓰기·180초 목록 만료는 제거되었습니다. 현재 구현과 적용 조건은 [GitHub·송출 분리 기록](github_voice_separation_2026-10-04.md)을 기준으로 확인하세요.

소스 수정 기록이다. EXE·ZIP·시험 배포본은 생성하지 않았으며 기존 배포본, 설정, 스케줄, 음성 파일을 변경하지 않았다. GUI와 봇은 수정된 공통 모듈을 함께 포함하도록 사용자가 수동 빌드한다.

## 확인한 기존 요청

5초 주기의 `DiscordAuthority._poll()`은 GitHub **읽기(GET)**다. 업로드 버튼을 누르지 않아도 관리자 접속 상태를 공유하는 `_presence()`는 정상 상태에서 20초마다 **쓰기(PUT)**를 수행했다. 권한·접속 목록은 스케줄과 별도의 공유 기록이므로 스케줄 업로드와 무관하게 요청이 발생한다.

| 정상 상태, 관리자 1명 | 수정 전 | 수정 후 |
|---|---:|---:|
| 권한 기본 읽기 주기 | 5초 | 5초 |
| 접속 상태 쓰기 주기, 새 버전끼리 | 20초 | 120초 |
| 접속 상태 쓰기 수, 시간당 | 약 180회 | 약 30회 |
| 구버전 관리자와 함께 접속한 새 클라이언트의 쓰기 주기 | 20초 | 30초 |
| 로컬 송출 권한 유효시간 / 인계 제한시간 | 10초 / 10초 | 10초 / 10초 |

시간당 수치는 접속·설정 변경, 명령, 인계, 충돌 재시도 없는 정상 상태 기준이다. 접속 상태 쓰기는 약 83% 감소하며, 기본 권한 읽기는 시간당 약 720회 남는다. 접속 상태를 실제 저장할 때의 SHA 확인 등 추가 읽기는 별도다. 구버전 클라이언트 자체의 요청 빈도는 이 소스 수정으로 줄어들지 않는다.

GitHub는 일반 인증 REST 요청에 시간당 5,000회, 콘텐츠 생성 요청에 일반적으로 분당 80회·시간당 500회 등의 제한을 안내한다. 일부 엔드포인트의 한도는 더 낮고 추가 제한이 있을 수 있다. 예를 들어 기존 클라이언트 3명이 각각 시간당 180회씩 쓰면 합계 540회여서 일반적인 콘텐츠 생성 기준을 넘을 가능성이 있다. 실제 계정·요청의 제한 적용 범위는 응답 헤더가 기준이며, 이번 접속 중단 당시 제한에 걸렸다는 로그 증거는 없다.

출처: [GitHub REST API rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api), [Contents API](https://docs.github.com/en/rest/repos/contents#create-or-update-file-contents).

## 수정 내용

- `discord_authority.py`: 접속 상태의 정상 쓰기를 120초 주기로 줄인다. 접속·실행 세션·담당자 정보 변경은 즉시 기록한다. 오프라인 상태가 계속 같으면 반복 저장하지 않는다. 로컬 HTTP 상태 조회가 실패하여 `runtime_id`가 없으면 이를 오프라인으로 저장하지 않는다.
- 새 클라이언트의 접속 목록 유효시간은 180초다. 광고 필드와 해당 `seen` 시각을 함께 확인하여 구버전으로 되돌린 클라이언트가 계속 새 버전으로 인식되지 않게 한다. 살아 있는 구버전 관리자가 감지되면 새 클라이언트는 30초 주기로 기록하여 구버전의 60초 유효시간과 호환한다.
- `AuthorityRecord.mutate()`와 `QueryLedger.mutate()`는 실제 변경이 없으면 PUT을 생략한다. 변경이 있으면 기존 SHA 검사와 충돌 시 재조회·병합을 유지한다. 권한 반납, 조회 담당자 정리, 이미 열린 요청 등 반복 처리가 불필요한 커밋을 만들지 않는다.
- 스케줄·보스설정 업로드는 이미 필요한 SHA 조회 응답의 실제 내용 해시를 비교한다. 버전만 바뀌고 내용은 같으면 해당 파일을 쓰지 않는다. 둘 다 같으면 서버 목록도 쓰지 않는다. 실제로 변경된 파일과 서버 목록만 기록한다.
- 부분 업로드 후 재시도에서 파일의 버전과 내용이 업로드하려는 자료와 정확히 같으면 파일 재쓰기를 생략하고 서버 목록 갱신을 마친다. 서버 파일과 목록의 버전이 다르면서 이 조건을 충족하지 않으면 덮어쓰기를 중단한다.
- 서버 관리 화면에서 추가·삭제·목록 변경이 없으면 목록 파일과 버전을 다시 쓰지 않는다. 권한 부족·요청 제한 403에 대한 삭제·목록 갱신의 즉시 재시도를 제거했다.
- `github_request_policy.py`: 403의 제한 헤더·본문과 429를 식별한다. `Retry-After`와 `X-RateLimit-Reset`까지 해당 토큰의 GitHub 데이터 읽기·쓰기를 보류한다. 별도 대기 안내가 없으면 60초를 기다리고, 반복적인 2차 제한은 최대 900초까지 대기를 늘린다. 제한 응답 후 무인증 읽기로 우회하지 않는다. 일반 권한 오류의 공개 파일 읽기는 유지한다.
- 대기 기록은 프로세스 메모리에만 저장하며 토큰 문자열을 보관하지 않는다. 같은 토큰으로 여러 저장소에 접근해도 대기를 공유한다. 다른 프로세스·PC·다른 토큰 사이의 계정 전체 할당량을 조정하는 기능은 아니다.
- 패치내역은 `UNRELEASED_NOTES`에 추가했다. 배포 버전 번호는 변경하지 않았다.

## 영향과 남은 제한

관리자 목록에서 갑자기 종료된 새 클라이언트의 발견은 마지막 기록 후 최대 180초까지 늦어질 수 있다. 이 목록 유효시간은 **로컬 음성 송출 권한의 10초 유효시간과 다르다**. 이중 송출을 막는 기존 검사와 인계 제한시간은 그대로다.

GitHub 요청 제한으로 읽기가 보류되거나 읽기가 지연·실패하면 기존 송출 권한이 만료될 수 있다. 5초 읽기를 크게 늘리거나 GitHub 확인과 음성 유지를 분리하려면 관리자 간 권한 조정 구조를 별도로 바꿔야 한다. 이번 수정은 쓰기 낭비를 줄이며, 19:07 권한 만료와 19:28 Discord 음성 연결 실패의 원인이 해결됐다고 단정하지 않는다. 당시 조사 기록은 `discord_disconnect_investigation_2026-10-04.md`에 있다.

## 비빌드 검증

실제 GitHub나 Discord에 연결하지 않고 메모리 저장소·가짜 HTTP 응답으로 다음을 검증한다: 1시간 쓰기 횟수, 구버전 공존과 다운그레이드, 상태 조회 실패, 즉시 상태 변경, 변경 없는 기록, SHA 충돌 병합, 실제 내용 중복 업로드, 변경 파일만 저장, 부분 업로드 재시도, 최신 서버 자료 보호, 인계 만료, 요청 제한 대기·증가·해제 및 무인증 우회 방지.

`test_github_write_efficiency`와 기존 `test_github_schedule_safety` 합계 45개가 통과했다. 수정한 Python 파일의 AST 구문 검증도 통과했다. 큰 GUI 파일을 읽는 검증은 16MB 스택의 작업 스레드에서 실행했다.

추가로 실행한 기존 테스트에는 수정 전 HEAD 소스에서도 재현되는 실패가 있다. `test_discord_start_preflight`의 3개 테스트에서 5개 오류는 가짜 앱 객체에 `_start_discord_bot_runtime`·`_query_discord_bot_status_port`가 없는 문제이고, `test_app_patch_notes`의 1개 실패는 이미 존재하던 미배포 내역의 '버전 미확정' 문구를 허용하지 않는 오래된 기대값이다. 이번 수정으로 전체 테스트가 모두 통과했다고 주장하지 않는다.
